# PLAYBOOK — 紙面から演目構成の下書きを作る変換規則（正本）

- 作成: 2026-08-12（設計メモ `show-creative-ideas/2026-07-30_種火から演目構成_設計メモ.md` の
  段階0.5として、変換規則をこのファイルへ移した）
- 対象: Claude Code・Codexなど、このMCPサーバーを使うすべてのAIクライアント
- 位置づけ: **変換規則はこのファイルが正本。** 設計メモは設計の経緯・理由を残す背景資料。
  両者が食い違ったらこのファイルを直し、本人に報告する。

## 0. 一言でいうと

本人がスクラップブックで保存・書き出した「紙面JSON」を、一本の演目の設計図の種として扱い、
AIが **ビート表（物語層）→ シーン下書き（舞台化層）** の二段で変換する。
作るのは完成品ではなく「出典まで遡れる、粗い構成のたたき台」。採用の判断は常に本人がする。

## 1. 入力 — 紙面JSON（`shosai-scrapbook-page` v1）

shosai-app のスクラップブックの「この紙面をJSONで書き出す」ボタンが出力する。

| フィールド | 意味 | 変換での使い方 |
|---|---|---|
| `title` / `pageNote` | 紙面の題・ページ全体のメモ | ショーの premise（方向づけ） |
| `items[].kind: "seed"` | 貼った付箋（最大12枚） | 各ビートの視覚的な核 |
| `items[].kind: "combined"` | 2〜3枚を組んだアイデア | **「転」の候補**。山（energy 4-5）に置く |
| `items[].text` / `note` | 本文と本人のメモ | ビートの action / visibleRule の素材 |
| `items[].recipe` | 種火の生成レシピ | 変形の出どころの説明 |
| `items[].sources` / `bookSources` / `apparatusSources` | 出典（作品DB / 自炊本 / 装置調査） | `seedIds` から遡る先 |

守ること:

- **紙面に無いものは入力に無い。** 流した（捨てた）種火は渡されていない。捨てた判断も尊重し、
  似たテーマを勝手に補充しない。
- どれを選び、どう組んだかという本人の判断が、すでに構成の半分である。付箋の取捨選択を
  AIがやり直さない。

## 2. 第一段 — 紙面 → ビート表（物語層）

- **1付箋=1ビートにしない。** 付箋は「核」であって場面数の指定ではない。
  **6〜9ビート**に収まるよう、近い種火は束ね、足りない継ぎ目は role だけの
  **空きビート**として正直に空ける（紙面に無いテーマで埋めない）。
- 各ビートは次を必ず持つ。感情形容だけのビートは作らない。
  - `action` — 舞台上で起きる行為
  - `visibleRule` — 観客が一度見て分かる規則
  - `change` — 何が変わるか
  - `energy` — 1〜5
  - `seedIds` — そのビートの元になった付箋のid（複数可）。種火→蔵書/作品まで遡れるので、
    「この場面の出どころ」を稽古場で語れる。空きビートは空配列。
- `combined`（組んだアイデア）があれば、その衝突を山（energy 4-5）の位置に置くことを既定とする。
  2つの規則がぶつかる所がドラマの折り目。
- **エネルギー曲線のテンプレは10種から2つをAIが推薦し、それぞれ理由を一行つける。決めるのは本人。**
  テンプレの正本は `stage-sketch.js` 冒頭の `BEAT_TEMPLATES`（id・role列・energy列を持つ）:
  1. `classic-circus` 古典サーカス・プログラム型
  2. `two-part-variety` 二部制ヴァラエティ・ビル型
  3. `three-act` 三幕構成
  4. `freytag` フライタークのピラミッド
  5. `kishotenketsu` 起承転結
  6. `rondo` ロンド形式 A–B–A–C–A–D–A'
  7. `theme-variations` 主題と変奏
  8. `canon-accumulation` カノン／アキュムレーション型
  9. `cycle-spiral` 循環／螺旋ドラマトゥルギー
  10. `single-focus-agres` 単一フォーカス／アグレ・ドラマトゥルギー

## 3. 第二段 — ビート表 → シーン下書き（舞台化層）

このMCPのツールで **新しいショーの下書き**として作る（既存ショーに触れない）。

主なツール: `stage_sketch_get_guide`（最初に読む）／ `stage_sketch_create_project_draft` ／
`stage_sketch_add_scenes` ／ `stage_sketch_update_scene` ／ `stage_sketch_inspect_project` ／
`stage_sketch_prepare_import`

決めごと:

- シーンの `note` に「行為/規則/変化」を書く（現MCPの流儀のまま）。ビートとの対応を
  `studyBeatId` で結ぶ。
- **配置は粗くてよい。** 意図が読める程度（中央/袖/奥、密集/散開）。座標の精密さは本人の領分。
- 演者は紙面から読める**最小人数**で。人数・会場などの制約は、本人が依頼時に一行で足せる。
- 照明はビートの energy から最小限。既定表（lightKind は `hang`=吊り / `ss`=サイドスポット /
  `front`=前明かり / `floor`=転がし）:

  | energy | 既定の照明 |
  |---|---|
  | 1〜2（静） | `hang` 1本 |
  | 3 | `front` 基本 |
  | 4〜5（山） | `ss` または `front`＋`floor` |

  これは出発点であり、規則の見え方（例: 影を主役にするなら front を消して floor）を優先してよい。
- **動線はAIが引かない。** シーンの並びだけ作り、本人が舞台スケッチの
  「次のシーンとの差から動線を引く」で起こす。動きの解釈・曲げは本人の仕事。

## 4. 受け取り — 本人の採用フロー

1. AIは新しいショーとして下書きを作り、`stage_sketch_inspect_project` で参照切れ・
   安全警告を点検してから `stage_sketch_prepare_import` で読み込み用JSONを準備する。
2. 本人は stage.html の「読み込む」で開く。気に入らなければ捨てるだけ。
3. 一部のシーンだけ既存ショーへ移したくなったら、それが「提案レビュー層」を作る
   タイミング（部分採用・差分表示）。**最初から作らない。欲しくなるまで待つ。**

## 5. やらないこと（境界）

- 完成した演目を出さない。ビート表と粗い配置まで。「直す余白」が仕様。
- 動線・姿勢の細部・美術の色をAIが決めない。
- 安全（吊り・高所・火気）をAIが保証したように見せない。警告どまり。
- 紙面に無いテーマを勝手に持ち込まない。足りなければ空きビートとして正直に空ける。
- ブラウザのlocalStorageを直接操作しない。本人が「読み込む」を選ぶまで現在のショーへ反映されない。

## 6. 変換の実例（実在の種火で）

紙面に次の2枚が貼られ、組まれていたとする。

- A「四拍に収まる言葉だけで道具を渡す。音が余ったら身体を一度止める。」（蔵書: 言語学的ラップの世界）
- B「床の影だけが、演者より一拍早くディアボロの技を成功させる。」（手書き種火）

ビート表の断片:

```json
{ "id": "b03", "title": "四拍の受け渡し", "role": "規則提示",
  "action": "二人が四拍で道具を渡す。言葉が余った側だけ静止する。",
  "visibleRule": "拍に収まらない発話は、身体の停止として現れる",
  "change": "観客が拍を数え始める", "energy": 2, "seedIds": ["book-seed-042"] },
{ "id": "b05", "title": "影が先に成功する", "role": "転",
  "action": "受け渡しの最中、床の影だけが一拍早く技を終える。",
  "visibleRule": "本体と影のどちらが規則に従っているか分からなくなる",
  "change": "拍の主導権が人から影へ移る", "energy": 4, "seedIds": ["A×Bの組み"] }
```

そこから落ちるシーン: b03=演者2人が中央で1.2m間隔・照明は `hang` 1本、
b05=同じ配置のまま `front` を消して `floor` を足す（影を主役にする照明）。
b03→b05 の移動はほぼ無いので動線は生まれない——構成の変化が「移動」ではなく
「照明と規則」で起きることが、配置データからも読める。
