**反論1・2は採用します。反論3については、試し表示を必須にする提案を撤回します。** 全体ルックの連続クリックで比較できるよう、毎回の適用結果を直前の明かりに依存させない設計にします。

以下は実装用の設計案です。ファイル変更はしていません。配置の角度と色のコントラストは計算しましたが、配置・ルック・UIの実描画は未検証です。

**3点への回答**

**反論1：`requires` は初日から持つ。ただし「実舞台で必要な最低設備」とは区別する。**

最小形式は次です。

```json
{
  "requires": {
    "required": [
      { "group": "front.center.l", "minCount": 1, "kind": "fixed" },
      { "group": "front.center.r", "minCount": 1, "kind": "fixed" }
    ],
    "supporting": []
  }
}
```

- `required`：欠けると、この見本の割当規則が成立しない。
- `supporting`：欠けても主題は残るが、補助的な光が変わる。
- 灯数は重複しない灯体IDで数える。左右の要件を同じ1灯で満たさない。
- 「条件を満たす／補助が不足／必須が不足」は**データ上の構成判定**。見え方の再現保証ではない。

適用対応の判定は別です。初版では、登録されたフルリグ3種とその配置契約への一致を確認します。任意rigでは条件を満たしていても「この仕込みへの適用は初版では未対応」。未対応を機材不足と表示してはいけません。

書き出しは「この見本で使用する配置：中央用の前明かり左右各1」とします。「実舞台で最低2灯必要」とは書きません。

**反論2：内部は配置グループ、表示は使い道。ただし対応はプリセットが明示する。**

| 表示する使い道 | 初版の内部対象 | 注意 |
|---|---|---|
| 顔 | `front.center.*`、`front.area.*` | 基本は現在点いている灯だけ変更 |
| 体の横 | `ss.low.*`、`ss.high.*` | 低段・高段を詳細で区別 |
| 奥からの輪郭 | `b3` | 任意の「輪郭を作っていそうな灯」は推測しない |
| 背景 | `cyc.floor`、`cyc.top` | 色変更では必要に応じて点灯も明示 |
| 床 | 各ルックが指定する `b1/b2/b3` の灯体 | 共通の「床グループ」は作らない |
| 空間の光 | 各ルックが指定するバトン・床置き等 | 初版の部分変更からは外す |

したがって、**配置グループ×属性を基本単位にし、点灯中などの明示フィルターを許す**案です。用途タグだけから対象灯を検索しません。

**反論3：即commitでよい。比較にUndoは毎回必要ない。**

- 全体A→全体B：直接Bをクリック。Bが全体置換ならAは残らない。
- B→直前のA：Undoを1回。
- 部分変更A→部分変更B：異なる対象なら累積、同じ属性なら後勝ち。
- 同じ結果になる再クリック：履歴を増やさない。
- キュー番号と名前は既存表示を使い、適用toastにも対象番号を出す。

ただし、**「見本を当てる→＋新規」では、元のキューも既に変更済みです。** 元を残す操作順は「＋新規→見本」。これは既存の新規キュー機能で成立するため、別の保存モデルは増やしません。

大量に比較した後で原案に戻る用途まで、100件上限のUndoだけで保証はしません。原案を残して比較するときは、先に新規キューを作る操作を案内します。

**A. フルリグ3種の配置**

すべて**仮想仕込みの初期値**です。実在劇場の常設設備や吊込条件を表すものではありません。

座標は `u=0：下手、1：上手`、`v=0：最奥、1：舞台前端`。高さ・距離はm、広がりは円錐の全角です。`l/r` はそれぞれ下手側／上手側を表します。

`U(n,a,b)` は両端を含む等間隔のn点。以下の複数座標は1点につき1灯を生成します。

**前明かりの狙いと配置**

中央専用の左右1組を確保します。それ以外を面の明かりに使います。

| サイズ | 中央専用の狙い | 面の明かりの狙い `(u,v)` |
|---|---|---|
| 小 | `(0.5,0.75)` | 奥列：`(0.2,0.4),(0.5,0.4),(0.8,0.4)` |
| 中 | 同上 | 前列：`(0.2,0.75),(0.8,0.75)`＋小の奥列3点 |
| 大 | 同上 | 前列：`(0.2,0.75),(0.8,0.75)`＋奥列：`u=[0.14,0.32,0.5,0.68,0.86], v=0.4` |

各狙いの高さは **1.2m**。人物の自動追従ではなく、仕込み時の共通狙いです。

狙いを `(q.u,q.v)` とすると、左右の `front` 灯体位置は次のとおりです。

- 左から：`u=q.u−0.12`
- 右から：`u=q.u＋0.12`
- `ahead,h` は下表。

| サイズ | 前列 `v=0.75` の `ahead,h` | 奥列 `v=0.4` の `ahead,h` |
|---|---|---|
| 小 8×7×6 | `2.5, 5.557` | `1.5, 6.980` |
| 中 12×9×8 | `3.5, 7.128` | `2.0, 8.739` |
| 大 18×12×12 | `4.5, 9.005` | `2.5, 11.138` |

高さの式は `h=1.2+√((0.12W)²+(ahead+(1−q.v)D)²)`。狙い点から見た仰角を45°にしています。表は小数第3位へ丸めた表示値で、生成時は式の値を使います。

**左右の振り角は約9.6〜16.1°で、水平・垂直とも45°の仕込みではありません。** 現行 `front.u` が舞台幅内に制限されるためです。45°前後の上方からの前明かりと、左右にも振る考え方はETCの解説を参照しました。[ETC：Lighting Angles](https://blog.etcconnect.com/stage-lighting-design-part-5?hs_amp=true)

客席側の灯体高が舞台のHを超える値は、現行 `front` の座標契約で表現できます。架空の客席吊位置としての値です。

| 配置グループ | 灯数 小／中／大 | kind | mountに入れる座標・値 | 広がり 小／中／大 |
|---|---:|---|---|---:|

**C. JSONの完全例と適用契約**

これは新設するプリセット形式です。既存アプリにそのまま読み込める形式ではありません。

共通ルールを先に固定します。

- `mode:"replace"`：対象cueの既知の照明属性を初期化してから、`assignments` を適用する。
- 初期状態は全灯off・level0、各灯の共通狙い、静止、終点値なし、ゴボなし、点滅なし、カッターoff、グループなし。
- `periodSec=8,offsetSec=0,glare=1`。ゴボの回転・角度・ぼけは0。
- `beamDeg:null`：固定灯はrigの角度を使用。cycでは角度による帯制御をしない。
- `path.a.zone` は、同じJSON内の `zones` を解決して実座標へ置き換える。
- rigの角度・バーンドア・cycの長さと到達高さは変更しない。
- 未知フィールドは保持。既知属性だけを初期化する。新しい描画属性を増やしたら、この初期化契約も更新する。

**適用関数**

```ts
applyPreset({

  coverage,
  assignments,
  changes,
  nextProvenance

```

返り値の契約：

| 項目 | 内容 |
|---|---|
| `coverage` | 必須／補助の要件別に必要数・該当ID・不足数。対応判定とは分ける |
| `assignments` | assignment ID、配置グループ、灯体ID、解決した狙い、実効角度 |
| `changes` | 灯体IDまたはグループID、属性パス、変更前後、設定／削除の別 |
| `nextProvenance` | 最後にその属性を書いたプリセットID・版・assignment ID・適用ID |
| 非適用時 | 状態と理由のみ返し、cue・rig・履歴を変更しない |

全体置換で消灯した灯や消去したグループも `changes` に含めます。ID生成は `applicationId` とassignment IDから決定し、乱数・現在時刻・`state.seq` を純関数内で使いません。

今回読んだ `drawFront3D()` は1767行付近です。直接参照だけでなく、呼び出す関数の隠れた参照も外します。[現行描画](</Users/arata/Library/Mobile Documents/com~apple~CloudDocs/claude code files/show-creative-ideas/shosai-app/docs/light-rig-design-2026-09-11/prototype/app.js:1767>)

境界は次の2段がよいです。

```ts
buildLightingFrame(input) -> frame
drawFront3DFrame(ctx, frame, viewport, resources) -> void
```

`frame` には評価済みの光源、狙い、着地点、実効角度、濃度、ゴボ角度、カッター等を入れます。`resources` は人物描画器、ゴボ資源、中間Canvas・キャッシュ。履歴やUI状態を含めません。

特に以下も引数化の対象です。

- `litFactorOf()`、`phaseOf()`、`beamOf()` の時間とcue。
- `goboProfile()`／ゴボマスク生成の `state.play.t`。
- `paintBlackout()` の `state.dim`。
- `backlitPieces()` のrig・pieces・cue・時刻・表示条件。
- `borderPieces()` のrig・curtains・表示条件。

**サムネイルの描画規約**

- 正面パース、視点は現在の `seat`。
- 現在の会場・rig・pieces・curtains・levelCurveを使用。
- 選択なし、ハンドル・番号・名前・グリッド・軌道・説明文字なし。
- 光と人物は表示。サムネイルは作業灯なしの観客表示として `blackout=true,dim=100`。
- これは作業灯を表示している主画面との完全一致を意味しない。見本欄に「作業灯なし」と短く示す。
- 画像生成は読み取りだけで行い、`state.play.t` 等を差し替えない。

キャッシュキーはこの入力と描画版から作ります。部分変更では元cueも含めます。表示中から1件ずつ生成し、主画面の操作を優先。動くカードの同時再生はしません。

**E. 305px右パネルの寸法案**

既存の `.panel` の枠1px・padding8pxを継承すると、内幅は **287px** です。スクロールバー相当の15pxを見込み、格子は幅272pxで設計します。実際のバー幅で調整する余地は残します。

高さは `枠2＋画像74＋余白6＋名前38＋間隔4＋タグ16＋下8＝148px`。長い名前は意味のまとまりで2行にし、省略した場合は全文を読める手段を残します。

絞り込みは固定2行です。

| 行 | 内容 | 寸法 |
|---|---|---|
| 1 | すべて／顔／体／床／背景 | 各50×26px、間隔6px、合計274px |
| 2 | すべて／静止／動き | 各60×26px、間隔6px、合計192px |

2行目の「すべて」は動き条件だけを解除します。用途と動きはAND検索。ジャンル・気分・色のチップは初版では増やさず、名前検索で拾います。部分変更6件の表示中は動き行を隠します。

カード文字には不透明のmilkを使い、選択はbrass枠とチェック印、手動調整ありはrust-inkの文字を併用します。背景は `--desk-2:#201b16`。既存スクリプトでの色値計算は次のとおりでした。

- milk：**13.88:1**
- brass：**4.62:1**
- rust-ink：**4.89:1**

これは指定した不透明色どうしの計算結果です。実画面の収まり・フォーカス表示・スクロール時の行高は未検証です。

格子自体をスクロール領域にせず、既存の縦スクロール容器の中へ固定行高の格子を置きます。カードはクリック後も見本タブに残し、調整タブへ自動移動しません。
