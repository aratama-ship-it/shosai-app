codex
**方向は賛成です。ただし「充実した仮想仕込みで見本を試す入口」として設計し、既存仕込みへの自動変換と自由な層合成は初版から外すことを推します。** A〜Gを一度に成立させようとすると、見本を選ぶ機能より、灯体の割当・合成・参照管理の方が大きくなります。

HANDOFF §4と関連コードを読みました。ファイル変更はしていません。以下の数量・工程・UI寸法は提案で、性能や実舞台での再現性を実測したものではありません。

**1. フルリグ構成：灯数より「同時に違う役割を担えること」を強くする**

**案**

表Aの内訳は出発点に使えます。ただし合計は訂正が必要です。

| | 小 | 中 | 大 |
|---|---:|---:|---:|
| 通常灯体 | 36 | 50 | 66 |
| ホリゾントのモデル | 上下2列 | 上下2列 | 上下2列 |
| データ上の灯体要素数 | **38** | **52** | **68** |

「最強」は**表現用の充実した仮想仕込み**と位置づけます。配置には舞台としての筋を通し、実在劇場の常設数や調達上限は名乗らない、という境界です。

- バトン3本の全ムービングは採用。ただし、全灯を毎回点ける必要はありません。
- 前明かりは灯数だけでなく、複数の演技エリアへ左右から当てられる割当にする。
- SSは奥行きに3灯並べるだけでは不足。**低い位置から体を拾う光と、上体を拾う光**を区別する。高さは人体に関係するため、劇場高に比例させない。
- 床置きはまず奥端・両端へ。中央の演技空間へ自動配置しない。床を空けたいサーカス演目では、使わない選択が重要です。
- 吊高の `0.85〜0.9H` は仮想配置の初期値には使えますが、実劇場の推定式にはしない。前明かりも単純比例より、狙う場所に対する角度を保つ。
- 会場はプリセットIDで対応づける。現在の12×8×8を、知らないうちに中劇場12×9×8へ変更しない。

**根拠**

日本の劇場にシーリング・フロント・複数のサスペンション・上下ホリゾントという構成はあります。守山文化小劇場の公式設備表でも確認できます。一方、その資料には吊物ごとの高さ・重量条件があり、舞台寸法だけで仕込みを決められません。表Aを「日本の劇場として無理がない上限」と断定する根拠は不足しています。[守山文化小劇場・公式設備表](https://www.bunka758.or.jp/facility/moriyama/files/pdf/moriyama_syoumei_setubi_2025.pdf)

また、ホリゾントの1列は実機1灯に対応しません。書き出しで「38灯必要」と伝えると誤解を作ります。

**捨てた案**

「現実の上限を全国共通で決める」「灯数が多いほど表現力が高い」。同じ場所・同じ向きの灯を増やしても、顔を見せながら別の光を動かす自由は増えません。

**本人に決めてもらう点**

末尾の質問①。実在の設備に近づける度合いです。

**2. ロール方式：採用。ただしロール記述と灯体への確定割当を両方持つ**

**案**

**プリセットはロールで書き、適用結果は灯体IDで確定**します。

B案の `front / b1 / b2…` は、厳密には役割ではなく配置グループです。以下を分けます。

- **配置**：客席天井、客席左右、前・中・奥バトン、左右袖、床、上下ホリゾント。
- **使い道**：顔、輪郭、床の区画、背景、空間の光線。
- **割当規則**：左右一対、中央集中、面を覆う、交差、順番。

`b1/b2/b3` は残します。`battens` は全バトンを選ぶ略記として追加できますが、奥行きの違いを消してはいけません。フルリグ生成時にIDとの対応表を作り、後からラベル文字列で推測しない方式にします。

既存8種への縮退適用は後段です。必要条件を「必須／補助」に分け、結果を次の3状態にします。

- 構成条件を満たす。
- 補助的な光が欠ける。
- 主題が成立しない。

最後の状態を「一部再現」として扱わないことが重要です。

**根拠**

均等配置だけでは、次のように破綻します。

| 意図 | 均等に散らすと起きること |
|---|---|
| 中央の一人を浮かせる | 全面へ広がり、主役が消える |
| 左右から顔を拾う | エリアごとに片側の光しか来ない |
| 左右対称の交差 | 奇数灯・左右不足で構図が変わる |
| 全面を覆う | 光の中心は均等でも、楕円の間に隙間が残る |
| 順に走る光 | 配列順と舞台上の並び順が違うと順序が飛ぶ |

固定灯への動きの割当も不可です。さらに現行の固定灯は広がりがrig側にあるため、同じロール名でもムービングと同じ処理はできません。

**捨てた案**

灯体IDだけで見本を記述する方式と、欠けたロールを自動的に別位置の灯で代替する方式。前者はサイズ展開に弱く、後者は意図を変えます。

**本人に決めてもらう点**

初版の縮退適用は見送る提案です。質問①で「手持ち設備への近さ」が最優先なら、優先順位を逆にします。

**3. 層：8分類は検索用には使えるが、合成規則にはならない**

**案**

「全体の見本」と「部分変更」を一覧の入口で分けます。

| 操作 | 合成規則 |
|---|---|
| 全体の見本を選ぶ | 対象キューの明かりを、その見本の完成状態へ置換。未使用灯は消灯 |
| 部分変更を選ぶ | 明示した灯体・属性だけ変更 |
| 同じ属性を再変更 | 後勝ち。変更対象をプレビューで表示 |
| 別の灯体の光 | 描画上で重なる |
| 同じ灯体へ異なる狙いを要求 | 混ぜず、置換または別灯への明示割当 |

8分類は整理タグとして十分です。ただし「動き」「効果」は顔・横・背景にも付くため、8個の排他的な層にはしません。

初版のチップは「背景：夕焼け」「輪郭：青／手動調整あり」という**由来表示**まで。オン・オフや削除で以前の状態へ戻る編集可能なレイヤーを名乗るなら、別途、元状態と操作順を保持する必要があります。

**根拠**

1灯には、ある瞬間の色・強さ・方向が一つしかありません。「中央を照らす」と「左右へ動かす」を同じ灯体へ加えても、二つの光にはなりません。

また、現在のデータでは次が結びついています。

- 狙い面と軌道。
- 動きとグループの所属・順序・遅れ。
- 強さと終点値・点滅。
- 広がりと終点値。

属性を無条件に浅く上書きすると、古い点滅やグループ設定が残ります。全体ルックはこれらを明示的に初期化し、部分変更は変更範囲を契約にする必要があります。

**捨てた案**

色の平均、強さの加算、競合ごとの質問。「重ねたら何になるか」が予測できず、試すテンポも失います。

**本人に決めてもらう点**

初版は「全体の見本＋部分変更」で進める提案。Photoshopのように層を自由に外せる体験は、今回の必須条件にはしません。

**4. 大量を雑音にしない：色違いより、違う構図を増やす**

**案**

初版は**完成ルック24個＋部分変更6個**を目安にします。最初の画面には性格の離れた6個を出し、残りは用途から探せるようにする。30〜40個への拡張は妥当ですが、色違いを別ルックとして水増ししません。

名前は「何をどう見せるか」を主語にします。

- 「中央の一人だけ」
- 「二人を別々の色で」
- 「全員の顔を見せる」
- 「体の輪郭を見せる」
- 「床に細い通り道」
- 「背景だけ夕焼け」
- 「奥から光が開く」

タグは「一人／二人／全員」「顔／体／床／背景／空中」「止まる／ゆっくり／はっきり動く」。ジャンル・気分・色は補助にします。「幻想的」だけでは、どこがどう変わるか伝わりません。

バリエーションも基本ルックごとの設計にします。顔の白を保って背景だけ色替えするなど、**色の関係を守る配色候補**が有効です。

**根拠：参考製品から採るもの**

| 参考 | 採る仕組み | 採らない仕組み |
|---|---|---|
| ETC Eos | 再利用する設定と、適用後の実値を区別する | 見本更新が既存キューへ自動伝播する既定 |
| Capture | 明かりの状態を保存して往復比較する | 卓・DMXを前提とした入口 |
| Lightroom | 適用前プレビュー、効果量の調整 | すべての明かりを同じ比率で変える万能つまみ |
| Figma | 共通定義と個別変更の区別 | ライブラリ更新によるショー全体の自動変更 |

Eosは参照値と実値の違い、Captureは静止・動画スナップショット、LightroomはプレビューとAmount、Figmaはスタイル変更の参照先への反映を公式に説明しています。[ETC](https://blog.etcconnect.com/2017/03/control-locked-absolute-palettes)、[Capture](https://www.capture.se/Manual/en-UK/2023/SnapshotsTab.html)、[Lightroomプレビュー](https://helpx.adobe.com/lightroom-classic/desktop/process-and-develop-photos/apply-presets.html)、[Amount](https://helpx.adobe.com/lightroom/web/edit-photos/use-presets/apply-presets.html)、[Figma](https://help.figma.com/hc/en-us/articles/360039238753-Styles-in-Figma-Design)

VectorworksではShowcaseの「名前付き単一フレーム記録」とVisionとの録画交換を確認できました。これは比較状態の保存の参考になりますが、「演出的な大量プリセットが標準搭載されている」根拠にはしません。[公式資料](https://app-help.vectorworks.net/2026/eng/VW2026_Guide/LightingDesign2/The_Showcase_palette.htm)

**捨てた案**

12色相×強さ×広がり×動きを一律に掛ける方式。独白の顔まで回転・点滅させれば、元のルックの意味が壊れます。

**本人に決めてもらう点**

質問③。最初に充実させる見本の方向です。

**5. サムネイル：実描画を使う。ただし毎回描き直さない**

**案**

**データから生成した静止画像をキャッシュする**方式を推します。「静止画を手作業で管理しない」は賛成ですが、「静止画像を持たない」は不要です。

1. 3サイズの標準状態を事前生成し、一覧の初期表示に使う。
2. 現在のrig・シーンに合わせる画像は、表示中のカードから順に生成。
3. 一覧は静止。選択した1件だけ、主画面で動きを再生。
4. 動きの代表時刻をプリセットに持たせる。全件を時刻0にすると、交差前・消灯中など同じ絵になる。
5. キャッシュキーにプリセット版、割当結果、寸法、セット・演者、視点、描画設定、強さのカーブ、時刻、画像サイズ、描画版を含める。
6. 表示外の仕事は取り消し、メモリには上限を設ける。

**根拠**

現行 `drawFront3D()` は `state`、選択状態、再生時刻、表示設定を参照します。**関数を小さいCanvasへ呼ぶだけでは独立したサムネイル描画になりません。** 描画用の入力を取り出し、編集中状態を変更せず描く境界が先に必要です。[描画コード](</Users/arata/Library/Mobile Documents/com~apple~CloudDocs/claude code files/show-creative-ideas/shosai-app/docs/light-rig-design-2026-09-11/prototype/app.js:1683>)

負荷は灯数だけでなく、ゴボ、ぼかし、光の重なり、描画面積に依存します。120×68・画素密度2倍・40枚のRGBA画素だけなら約5MiBですが、中間Canvas等は別です。実時間はSafariを含めて測定が必要です。

**捨てた案**

数十枚の常時アニメーション、実際と違う美しい宣材画像、主画面の `state` を一時的に差し替えて生成する方式。

**本人に決めてもらう点**

追加質問なし。正面図で区別しにくい床の構図は、選択時に既存の平面図で確認する設計とします。

**6. LX cueとの整合：試すことと採用することを分ける**

**案**

入口の動作を二段に分けます。

- **空の照明設計**：「ビジュアルから作る」で会場対応のフルリグを用意。
- **既存の照明設計**：フルリグへの切替は別の照明案として開始。既存rigをその場で置き換えない。

ギャラリーでは、クリックで**試し表示**。「見本を試しています／対象：LX cue 1-1-2」を明示し、採用時に次のどちらかを実行します。

- 「このキューに使う」：編集中キューへ1回のcommit。
- 「新規キューにする」：新しいキューを作り編集へ入る。

未登録の下書きなら、その下書きへ反映。見本を選ぶたびに新規キューは増やしません。試し表示中にシーンやキューを移ったら試し表示を終了し、変更対象がすり替わらないようにします。

**根拠**

現行の仕込み選択はrigを丸ごと作り直します。旧キューの灯体IDを新rigへ割り当て直す処理はその経路にありません。これをF案のボタンへ直結すると、**他シーンを含む既存キューの明かりが表示できなくなる可能性があります。** 防止策は別案への分岐で、検証は未実施です。[仕込み選択処理](</Users/arata/Library/Mobile Documents/com~apple~CloudDocs/claude code files/show-creative-ideas/shosai-app/docs/light-rig-design-2026-09-11/prototype/app.js:3640>)

また、`lxSyncEditing()` はcommit時に各シーンの編集対象へ書き戻します。試し表示を `sc.cue` に入れ、commitだけ避ける設計では不十分です。プレビュー専用の状態が必要です。

既存「光の動き」は**言葉と動きの定義を揃え、データを直ちに統合しない**。今回読んだ `stage-light-motion.js` の `PRESETS` は往復・扇・交差・円・順にの**5種**で、点滅は含まれていません。両モジュールは速度の秒数も異なるため、名前だけ合わせても同じ動きにはなりません。[現在の定義](</Users/arata/Library/Mobile Documents/com~apple~CloudDocs/claude code files/show-creative-ideas/shosai-app/stage-light-motion.js:18>)

**捨てた案**

クリック即commitを唯一の操作にする方式、自動的に新規キューを量産する方式、既存モジュールの保存データを一括移行する方式。

**本人に決めてもらう点**

質問②。試した見本を採用するときの既定の行き先です。

**7. 演者参照：番号ではなくID。最初は位置を写し取る**

**案**

見本の「主役」「相手役」を、適用時に実在する演者IDへ結びつけます。配列の何番目かを意味する `performer{n}` は使いません。

初版は**適用時の狙い位置をキューへ固定**し、出典として演者ID・シーンID・狙った部位を保持します。「演者の現在位置へ合わせ直す」は明示操作にする。

将来の追従機能では、参照先の消失時に最後の有効位置で止め、「対象が見つからない」と表示します。中央や別の演者へ勝手に向け直しません。

`aerial` は人物参照と分け、名前付きの空間位置にします。高さは床からの実寸とし、会場変更で範囲外になっても黙って上限へ丸めない。

**根拠**

人物の身長と床から浮いている高さは別物です。試作の演者データには `hM:1.68` のような値があり、これをそのまま空中の狙い高さとして読むべきではありません。姿勢から胸や顔の位置を得るには、描画側との座標契約が必要です。

また、固定灯がシーンごとに演者へ向きを変えると、実際には仕込み替えが必要な絵を作ります。固定灯は共通の演技エリアを担当させ、追従はムービングに限定する方が伝わります。

**捨てた案**

演者の順番参照、姿勢から未定義の高さを推測、人物移動で保存済みキューを無条件に更新。

**本人に決めてもらう点**

質問③で空中芸が優先なら、人物の高度・狙う部位の契約を初週へ繰り上げます。

**8. 最初の2週間：3仕込み・24ルック・6部分変更に絞る**

**案**

| 期間 | 作るもの |
|---|---|
| 1週目前半 | 3サイズのフルリグ、配置グループ対応表、固定灯の共通狙い、必須条件、JSONと純関数の適用処理 |
| 1週目後半 | 性格の離れた6ルック、試し表示、現在／新規キューへの採用、Undo |
| 2週目前半 | 完成ルック24個まで拡張、部分変更6個、検索・用途絞り込み・画像キャッシュ |
| 2週目後半 | 3サイズでの比較、既存キュー保持、書出・再読込、Safariでの表示・操作・性能確認 |

24ルックのうち、動く見本はまず3個程度。空中・客席向け描画はHANDOFFで再設計課題になっているため、完成扱いにせず別枠で検証します。

右パネルは「見本／調整」。見本内で「全体／部分変更」を切り替えます。UI寸法の初期案は、カード最小幅144px、間隔8px、名前14px、補足12px、主要操作高36px。配色・書体は既存を継承し、実幅とコントラストの確認後に確定します。

初版から外すのは、任意rigへの縮退、自由なレイヤー編集、演者への連続追従、全カード動画、千件の自動生成、本体統合です。

**根拠**

「3仕込み×24ルック」で既に72通りあります。さらに異なる演者・幕・セット・手動調整が入ります。2週間は工数仮説ですが、まず6個で比較体験を成立させる順序なら、数を増やす前に問題を発見できます。

E案の純関数は採用。ただし返すものに `coverage` だけでなく、**確定した灯体割当・変更属性・由来**が必要です。現在の `cueJson()` は `lights/groups` だけを写すため、由来をcueへ追加するだけでは保持されません。

書き出しは灯数より先に、例えば「中央の一人を暖色で残し、周囲を暗く、奥の青い輪郭をゆっくり開く」と意図を出します。その後に仮想配置の内訳を添え、ホリゾントは「上下各1列」と表記します。

**捨てた案**

初週から40個を書き切ること、全層共通の広がりつまみ。固定灯の広がりとホリゾントの到達高さは現状rig側なので、キューの調整として一括変更できません。

**本人に決めてもらう点**

質問①〜③の回答で、見本の内容と採用導線を確定します。数量そのものは実装側の検証で調整可能です。

**9. 本人に確認するのは、この3問**

**案・本人に決めてもらう点**

1. **「最強」は、持ち込みを含む充実した仮想仕込みで自由に考えるものにしてよいですか。それとも、一般的な劇場の常設設備に近い案を得ることを優先しますか。**  
   推奨は前者。今回の「ビジュアルから作る」という入口に合います。

2. **気に入った見本を採用するとき、基本は「いま編集中のキューを変える」ですか、それとも「別の候補として新規キューに残す」ですか。**

**2. ロール方式：採用。ただしロール記述と灯体への確定割当を両方持つ**

**案**

**プリセットはロールで書き、適用結果は灯体IDで確定**します。

B案の `front / b1 / b2…` は、厳密には役割ではなく配置グループです。以下を分けます。

- **配置**：客席天井、客席左右、前・中・奥バトン、左右袖、床、上下ホリゾント。
- **使い道**：顔、輪郭、床の区画、背景、空間の光線。
- **割当規則**：左右一対、中央集中、面を覆う、交差、順番。

`b1/b2/b3` は残します。`battens` は全バトンを選ぶ略記として追加できますが、奥行きの違いを消してはいけません。フルリグ生成時にIDとの対応表を作り、後からラベル文字列で推測しない方式にします。

既存8種への縮退適用は後段です。必要条件を「必須／補助」に分け、結果を次の3状態にします。

- 補助的な光が欠ける。
- 主題が成立しない。

**根拠**

| 意図 | 均等に散らすと起きること |
|---|---|
| 中央の一人を浮かせる | 全面へ広がり、主役が消える |
| 左右から顔を拾う | エリアごとに片側の光しか来ない |
| 左右対称の交差 | 奇数灯・左右不足で構図が変わる |
| 全面を覆う | 光の中心は均等でも、楕円の間に隙間が残る |
| 順に走る光 | 配列順と舞台上の並び順が違うと順序が飛ぶ |

24ルックのうち、動く見本はまず3個程度。空中・客席向け描画はHANDOFFで再設計課題になっているため、完成扱いにせず別枠で検証します。

**捨てた案**

**9. 本人に確認するのは、この3問**

**案・本人に決めてもらう点**

1. **「最強」は、持ち込みを含む充実した仮想仕込みで自由に考えるものにしてよいですか。それとも、一般的な劇場の常設設備に近い案を得ることを優先しますか。**  
   推奨は前者。今回の「ビジュアルから作る」という入口に合います。

2. **気に入った見本を採用するとき、基本は「いま編集中のキューを変える」ですか、それとも「別の候補として新規キューに残す」ですか。**  
   推奨は試し表示を共通にし、前者を主操作、後者を隣に置く形です。

3. **最初の見本を最も充実させたいのは、地上の身体・道具を見せる明かり、空中芸を見せる明かり、舞台全体の色と光の構図のうち、どれですか。**  
   仮の推奨は地上の身体・道具。空中芸を選ぶ場合は、既知の描画課題と高さの扱いを先に解きます。

**根拠**

この3点で、設備への忠実さ、保存操作、初版の主要依存関係が変わります。

**捨てた案**

好みの色、正式名称、灯数の細部などを先に聞くこと。それらは比較できる見本を作ってから調整できます。
