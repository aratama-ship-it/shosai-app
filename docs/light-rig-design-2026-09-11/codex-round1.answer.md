## 結論

**Aの「共通の灯体配置／シーンごとの動き」は採用できます。ただし、動きと組の設計、保存の境界、旧機能との共存方法は組み直すべきです。**

最も大きな問題は、Claude案が「灯体を置く」という本人の訂正には対応した一方、動きの内部構造には前回の「光をまとめて生成する」設計を残していることです。**一灯ごとの軌道が基本で、扇・交差・順には、それらを組み合わせる操作**として扱う方が、一灯ずつ直せるアプリになります。

以下、**確認事実**は現行コード・資料から、**提案・判断**は今回の設計レビューとして記します。ファイルは一切変更していません。

## 1. Claude案A〜Fの批評

| 案 | 判断 | 主な修正点 |
|---|---|---|
| A：データ | 二層構造は妥当 | 灯体種類の分類、色の所有者、組と個別設定の優先関係が未整理 |
| B：画面 | 二つの編集モードは妥当 | 全灯を置き終えてから動かす一本道にはしない |
| C：描画 | 専用キャンバスに賛成 | 座標・投影の契約まで独自にすると、本体と位置が食い違う |

| E：旧機能 | 旧モーダルの一律非表示に反対 | データが残っていても、開けなければ利用者には消失と同じ |

### 1-a. 二層構造と既存データとの整合

**確認事実：既存照明について、前提の座標説明に一つ訂正があります。**

現行コードでは、灯体の出どころは `piece.beam.u/v/h`、狙う点は `piece.u/v` と `beam.toH` です。`piece.u/v` を灯体位置として新設計へ読み替えると逆になります。[既存の光源・照射先の処理](</Users/arata/Library/Mobile Documents/com~apple~CloudDocs/claude code files/show-creative-ideas/shosai-app/stage-sketch.js:8801>)

**提案：二層構造は維持し、既存の `sets/pieces` には重複登録しない。**

既存も「共通の登録情報」と「シーン内の状態」を分けています。その思想とは整合します。ただし、新しいrigでは**設置位置まで共通**にするため、既存の「各シーンで置く駒」と同じものではありません。

最小の責任分担は次です。

| 所有者 | 持つもの |
|---|---|
| `project.lightRig` | 灯体ID・番号・名前・取り付け位置・トラス |
| `scene.lightRigCue` | 各灯の点灯状態・色・見た目の強さ・静止先または軌道・時間設定 |
| cue内の `groups` | メンバーの順序、共通周期、同期や対称の関係 |
| 書き出し時のスナップショット | その時点のrig・cue・会場寸法・版 |

修正すべき点は五つあります。

- **`moving／spot／wash` を同列に置かない。** 動くかどうかと、光の広がり方が混ざっています。初回は「ムービング」を中心にし、必要なら「動かせる／固定」と「細い／広い」を別属性にします。
- **光の色はシーン側へ置く。** 灯体一覧の識別色と照射色も別です。rigに照射色しかないと、一場面の色変更が全場面へ波及します。
- **未設定と消灯を区別する。** cueがない灯を勝手に点灯させない。未設定は一覧で分かり、再生では発光しない扱いがよいです。
- **組と個別設定の所有権を決める。** 組に属する間、周期・時間差・対称関係は組が持ち、各灯は軌道の位置・広さを持つ。組から外すときは、現在の有効設定を個別設定へ展開します。
- **最初は前シーンからの暗黙継承をしない。** シーン複製はできても、並べ替えによって動きが変わる設計にはしません。

現行の読み込み処理はフィールドを明示して再構築します。新しい項目を保存側に足すだけでは不十分で、正規化・読み込み・複製・Undoまで対象です。[シーン正規化](</Users/arata/Library/Mobile Documents/com~apple~CloudDocs/claude code files/show-creative-ideas/shosai-app/stage-sketch.js:4715>)

### 1-b. 「概略位置」の最小表現

**判断：段数・高さだけでは図を安定して描けません。説明用の段数と、描画用の位置を分けます。**

| 取り付け | 保存する最小情報 | 表示例 |
|---|---|---|
| トラス | 固定ID、奥行き `v`、概略高さ、灯体の横位置 `u` | 奥から2列目／高さ約5m／中央より上手 |
| 床 | `u,v`、床置きという取り付け区分 | 下手奥／床置き |
| 横 | 上手・下手、奥行き `v`、概略高さ | 上手／奥寄り／高さ約2m |

「奥から何段目」は奥行き順から導出する表示にします。**トラスを一本追加しただけで、既存トラスの描画位置が動く設計は不可**です。IDと座標を保持し、表示上の順番だけ変えます。

`side:"L"|"R"` は誰から見た左右か不明です。画面・書き出しには「上手／下手」と客席方向を常時示し、内部値も意味が分かる名称にします。

床置きの光源を床面ちょうどに置くと、床への光線が床面上を走ります。光源の高さを概略で補うなら、その値は**実測ではなく描画上の仮定**とします。

この情報で照明担当者が十分に読めるかは未検証です。ただし、番号付き平面図・高さ・同じ番号の動き説明まであれば、検討用の最小候補にはなります。

### 1-c. `direction` は一つの列挙値にしない

`lr／ud／cw` は、軌道の軸と進行方向を混ぜています。

**提案：灯体の首の動きではなく、舞台上の「当たる先」で説明します。**

| 項目 | 最小の語彙 |
|---|---|
| 当てる面 | 床／奥壁 |
| 往復する範囲 | A点〜B点。床なら上手下手・奥手前・斜め |
| 最初の進み方 | Aへ／Bへ |
| 円の回り方 | 時計回り／反時計回り。基準ビューを併記 |
| 開始位置 | 軌道上の開始点をドラッグ |

例えば、横に置いた灯体でも、

> 上手の灯体から、床の下手奥Aと上手奥Bの間を往復。Aから開始。

なら、灯体の設置方向に依存せず意味が保てます。

「中央から開始」だけでは、次にどちらへ動くか決まりません。**開始位置と最初の矢印を一緒に表示**します。内部では位相にまとめ、`start` と `phase` を独立した正本として二重保存しない方がよいです。

## 2. 画面の流れ

### 二段階のウィザードではなく、往復できる二つの編集モード

**提案：名称は「配置〈ショー共通〉」「動き〈現在のシーン〉」。**

本人の作業は、次のように往復するはずです。

> 一灯置く → 当てて動かす → 位置を直す → 複製する → 二灯の関係を作る

全灯配置を完了しないと②へ進めない構造は、この試行錯誤を妨げます。どちらのモードでも同じ灯体の選択とプレビューを維持します。

入口も、プリセットの一選択肢に見える並びより、照明パネル内の独立した主要操作「照明を組む」が適切です。

### 平面図と正面図は同時表示、編集責任は分担する

**提案：大きな平面図＋補助の正面図＋灯体一覧・設定欄。**

二つの図を同じ大きさで常に編集可能にすると、設定欄まで含めて操作対象が小さくなります。

- 平面図：横位置・奥行き、床上の軌道を編集。
- 正面図：高さと光線の見え方を確認。高さ変更は選択対象のハンドルで行う。
- 奥壁を狙う場合：正面図を主編集面へ切り替える。
- 一方で選んだ灯体は、もう一方でも強調する。

トラス灯の高さはトラスから継承します。灯体を正面図で上へドラッグした結果、いつの間にかトラスから外れる動作にはしません。

### 配置を速くする具体策

1. トラス追加後、そのトラスを選択状態にする。
2. 「灯体を置く」で、トラス上をクリックするたびに追加。
3. トラスへの吸着先を確定前に強調する。
4. 置いた灯体を複製でき、複数選択後に等間隔へ並べられる。
5. トラス上のドラッグは横移動に限定し、別トラスへの移動は明示する。

クリック配置を基本にし、ドラッグは微調整へ使います。毎回パレットから長距離ドラッグする必要はありません。灯体番号は移動や並べ替えで変えません。

### 会場エディタから流用するもの

**確認事実：** 会場エディタは専用状態・キャンバスを持ち、保存後にイベントを通して本体の会場を更新します。開閉時のフォーカス復帰、選択モード、スナップ処理もあります。[保存処理](</Users/arata/Library/Mobile Documents/com~apple~CloudDocs/claude code files/show-creative-ideas/shosai-app/stage-venue-editor.js:1566>)

**採るもの：** 広い作業面、選択の明示、スナップの予告、状態メッセージ、フォーカス復帰、本体へ反映する境界。

**そのまま採らないもの：** 保存先。会場ライブラリに保存する仕組みを、照明rigの別ライブラリへコピーする必要はありません。

照明画面では「適用」でrigとcueをまとめて反映し、「閉じる」と「変更を破棄」を区別する設計を勧めます。モーダル内のUndoも必要です。保存時にはショー全体を古いコピーで置き換えず、対象の照明データを反映します。

## 3. 描画と再生

### 幾何は「3Dの位置を計算してから投影する」

**確認事実：** 本体の奥行きは `v=0` が最奥、`v=1` が最前です。[座標変換](</Users/arata/Library/Mobile Documents/com~apple~CloudDocs/claude code files/show-creative-ideas/shosai-app/stage-sketch.js:6604>)

**提案：** 新画面もこの契約を共有します。幅をW、奥行きをD、高さをhとすると、内部計算の一例は次です。

```text
灯体位置 S = ((u − 0.5)W, vD, h)

床の照射先   T(t) = ((u(t) − 0.5)W, v(t)D, 0)
奥壁の照射先 T(t) = ((u(t) − 0.5)W, 0, h(t))

表示する光線 = S から T(t) まで
```

軌道生成は画面座標を扱わず、平面図・正面図が同じ `S,T(t)` を投影します。

円も物理寸法の空間で作ります。幅と奥行きが違う会場で、正規化した `u,v` に同じ半径を足すだけでは、床上の円になりません。

**床・奥壁への照射に限定すれば、パン／チルトなしで成立します。** ただし、空中の演者や客席上空へ向ける動きは別です。その場合は「狙う空間点」と「光が最終的に当たる面」を分離する必要があります。既存コードにも、この区別を扱う `beamLanding` がありますが、新画面へ無条件に流用する対象ではありません。

### 一灯の軌道と、組の構成を分ける

| 表示上の型 | 内部で必要なもの |
|---|---|
| 往復 | 一灯のA〜B軌道 |
| 円 | 一灯の中心・半径・回転方向 |
| 扇 | 複数灯の開閉する軌道配置＋共通の進行 |
| 交差 | 選んだ二灯の照射先を入れ替える軌道配置 |
| 順に | メンバー順と時間差 |

UIには本人の希望どおり五つの型を残せます。ただし、扇・交差・順にを一灯から選んだ場合は、**相手や組を選ぶ操作へつなぐ**べきです。架空の二灯目を発生させてはいけません。

「向かい合わせ」を半周期ずらすだけで実装するのも不十分です。直線往復では対称に見えても、円では同じ回転方向の反対位置になります。

- 一緒に：共通の時間進行。
- 向かい合わせ：定めた軸に対して軌道を鏡映。
- 順に：明示したメンバー順で遅らせる。

ETC公式資料でも、速度、位相差、方向、同期は別属性です。採るのはこの責任分離で、卓のパラメータ編集画面をそのまま持ち込む必要はありません。[ETC公式：Table Effects](https://www.etcconnect.com/webdocs/Controls/HOG/HTML/en/sect-table_effects.htm)

なお、正面図で線が交差しても、奥行きが違えば空間内で交差しているとは限りません。「交差」はまず**指定した見え方・照射先の入れ替わり**として説明します。

### `stage-light-motion.js` の再利用境界

| 部分 | 判断 |
|---|---|
| 三角波・周期・剰余による位相計算 | 再利用 |
| 時刻を引数にして同じ結果を描く構造 | 維持 |
| プレビュー・動画・PNGが同じ描画を使う方針 | 維持 |
| 言語を呼び出し側から渡す方針 | 維持 |
| `normalize` | 新rig用には新設。旧データ用は残す |
| `phaseAt` | 個別周期・開始位置・N灯の順序に対応して再設計 |
| `beamGeometry`・`rangeGuide` | 固定の仮位置・画面比率を除き、作り直す |
| `drawFrame` | 描画の構成は参考にし、実座標と投影へ置換 |
| 動画の形式選択・Blob生成 | 再利用候補。ただし描画関数の差し替えと終了処理を整備 |
| 3コマPNG | 合成の仕組みを再利用し、時刻選択とラベルを変更 |

**確認事実：** 現在の `phaseAt` は二灯目以降を同じオフセットで処理します。読み取りのみの数値確認でも、4灯相当に問い合わせると二灯目以降が同位相でした。N灯へは本数制限を外すだけでは対応できません。[現行モジュール](</Users/arata/Library/Mobile Documents/com~apple~CloudDocs/claude code files/show-creative-ideas/shosai-app/stage-light-motion.js:76>)

録画についても、コメントの「固定ステップ」と実装は区別が必要です。現在はタイマー間隔が一定で、描画時刻は実経過時間です。また記録された成功範囲はmacOSのアプリ内Chromiumによる単体ページで、非表示時のフレーム欠落も記載されています。[検証記録](</Users/arata/Library/Mobile Documents/com~apple~CloudDocs/claude code files/show-creative-ideas/shosai-app/docs/light-ui-brainstorm-2026-09-11/export-test/RESULTS.md:5>)

## 4. 既存との整合と書き出し

### 旧パネルと新rigを、無条件に一枚へ重ねない

**判断：同じショーに共存できますが、合成すると「追加の灯体」なのか「同じ灯体の別表現」なのか判別できません。**

初回は次の境界が妥当です。

- 既存の舞台図：従来の照明表示を維持。
- 新しい照明図：新rigを対象に、灯体番号・配置・動きを出す。
- 両方渡す場合：別図として見出しを分け、対応関係は未設定と示す。

「旧データ優先／新データ優先」を黙って決めても解決しません。将来の統合には、本人が同じ灯体を対応付ける操作が必要です。

### `scene.lightMotion` は「入口の統合、意味の保存」

**推奨：一律非表示にせず、段階的に吸収します。**

新規作業の入口は「照明を組む」へ寄せます。旧データがあるシーンには「以前の光の動き案を開く」を残します。

移す場合は、

> この動きを、選んだ灯体へ割り当てる

という明示操作にします。旧データには実位置も灯体IDもないため、自動移行でそれらを確定できません。移行後も旧案を比較でき、編集入口だけを隠して取り出せなくする事態を避けます。

### 書き出しは「一文＋灯ごとの対応表」

複数灯の異なる動きを一文だけに押し込むと、図との対応が失われます。

最小セットは、**動画・配置図付き3コマPNG・テキスト**です。テキストにはシーンの要約一文と、灯体ごとの短い行を含めます。

> L03：奥から2列目、中央。床の下手奥〜上手奥を4秒で1往復。下手側から開始。

動画・図・文章で同じ番号、版、出力時点を使います。異なる周期の灯がある場合、3コマを一律に「始め・折り返し・戻り」と呼ばず、「0秒・2秒・4秒」など実時刻で示します。動画も安易に「ループ」と呼びません。

注意書きは、今回の目的に合わせて変更します。

> 灯体の概略配置と動きの案。機種・回路・DMX・照度・設置安全性は未検討。

「灯体位置は示しません」という旧文言は、新機能では誤りです。

1. **最初に作りたい場面では、光の先を床・奥壁に置ければ足りますか。それとも、空中の演者や客席上空へ向ける動きが必要ですか。**  
   狙い点と照射面を分離する必要があるかが変わります。

2. **灯体の設置位置はショー全体で固定ですか。それとも、転換中に床置き灯などを移す場面がありますか。**  
   共通rigだけで足りるか、シーン側に設置位置の変更を持つかが変わります。

3. **一つのシーンには一つの動きを設定できればよいですか。それとも同じシーン内で「静止→往復→消灯」のように切り替えたいですか。**  
   cueが一状態で足りるか、シーン内の時間列が必要かが変わります。

次の一手は、この3点を受けて、**一灯の設定と組の設定が衝突しないデータ例を一つ作り、それを使って配置→個別調整→書き出しの操作を詰めること**です。
