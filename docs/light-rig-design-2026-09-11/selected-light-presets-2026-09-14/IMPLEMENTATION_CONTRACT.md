# 選択灯「型」— 実装契約（提案）

Status: **proposal only**. これは選択灯プリセットの試作・実装判断をそろえるための契約であり、舞台スケッチ本体、保存済みプロジェクト、ベータ、公開物を変更する許可ではない。

関連する画面提案: [DECISION.html](./DECISION.html)
人が読む版: [IMPLEMENTATION_CONTRACT.html](./IMPLEMENTATION_CONTRACT.html)

## 0. 接続しない既存機能

| 既存 | 現在の意味 | 今回との関係 |
| --- | --- | --- |
| `scene.lightMotion` | 灯体・DMX・パン/チルトを持たない、シーン単位の光の動き案 | **変更・流用しない** |
| 本体の `LIGHT_PRESETS` / `lightGroup` | 舞台図にライト駒を新しく作り、組として扱う | **変更・流用しない** |
| `docs/light-rig-design-2026-09-11/prototype/light-presets.js` | 仮想仕込み向けの純関数試作 | 参考実装。`src` / `srcm` を本体保存形式とはみなさない |

今回の型は、選択済みの照明フィクスチャに対して実値を一括で書く、試作側の**選択灯属性パッチ**である。本体に選択灯フィクスチャの正規データ形式が未確定のため、最初の実装は試作の cue モデルだけで完結させる。

## 1. 不変条件

1. 適用後は各灯の実値だけが正本。プリセット定義への生きた参照や自動追従は持たない。
2. 一回の適用、seed の再抽選、範囲の確定は、それぞれ Undo 一回で戻る原子的操作。
3. 変更しない属性、未知属性、非対象灯はそのまま保持する。
4. 同じ正規化済み入力、fixture ID、順序、seed、`pathVersion`、時刻なら同じ結果になる。
5. 非対応灯は黙って変えない。適用前に対象数と除外理由を返す。
6. `scene.lightMotion` と本体の `lightGroup` に書き込まない。

## 2. 型の属性担当範囲

型は「積み上がる効果」ではない。UI上は一度に一つの型を選び、適用結果は値として残る。属性担当範囲が異なる結果は値として共存しうるが、複数の“稼働中プリセット”として表示・評価しない。

| 家族 | 書いてよい属性 | 保持する属性 | 対応 |
| --- | --- | --- | --- |
| 狙い | `path.kind=still`、狙い点 | 色、強さ、ビーム、ゴボ、点滅 | 狙いを変えられる灯 |
| 範囲 | 狙い点、`beamDeg`、任意の `level` | 色、ゴボ、点滅 | 狙いを変えられる灯 |
| 動き | `path`、`periodSec`、`offsetSec`、動きグループ | 色、強さ、ビーム、ゴボ、点滅 | ムービング灯 |
| 配り方 | `color` または `level` | 狙い、動き、ビーム、ゴボ | 対象属性を持つ灯 |
| 演出 | カードごとに明記した上記属性だけ | それ以外 | カードごとに判定 |
| 点滅 | `strobe` / shutter 相当の時間・位相 | 狙い、色、動き、ビーム、ゴボ | 点滅属性を持つ灯 |

`強さもそろえる` は範囲型だけの明示オプションで、既定は ON。OFF なら `level` を絶対に書かない。

## 3. 試作 cue の最小契約

本体の永続化形式ではない。試作の一灯は既存の `lights[fixtureId]` を保ったまま、次のような属性を**必要な範囲だけ**更新する。

```js
{
  on: true,
  level: 65,
  color: "#f2ead6",
  beamDeg: 18,
  path: { kind: "still", a: { u: 0.5, v: 0.6, hM: 0 } },
  periodSec: 8,
  offsetSec: 0,
  strobe: null,
  // 由来は表示用の任意メタデータ。値の正本ではない。
  presetMeta: {
    lastAppliedByScope: {
      motion: { id: "motion.wander.stage", seed: 2841, pathVersion: 1 }
    }
  }
}
```

- `presetMeta` は未知キーを破棄しない正規化にする。存在しない旧 cue も有効。
- 手動調整後も値は残す。`lastAppliedByScope` は「始点」を示すだけで、適用値を復元・上書きする根拠にはしない。
- UIの「調整あり」は、各担当範囲の適用直後の値スナップショットとの比較で表示する。比較対象は型が担当する属性だけで、値を復元・上書きする根拠にはしない。再調整で開くモーダルには、選択中のうち変化した灯数と担当属性名だけを表示し、灯名・前後値・復元操作は出さない。属性名は保存キーでなく、型に対応する短い表示語（例: `periodSec` は動き型では `速さ`、`show.curtain` の `path` は `光の並び`）へ変換する。将来の本体保存形式に試作の `src` / `srcm` を固定しない。

## 4. 再現できるランダム移動

### 保存する入力

```js
{
  kind: "wander",
  seed: 2841,                 // uint32。再生中に変えない
  pathVersion: 1,             // アルゴリズム変更で旧キューの見た目を変えない
  regionIds: ["stage"],      // audience版は ["stage", "audience:<id>"]
  loopSec: 10,
  irregularity: 0.55,         // 0..1
  phaseNorm: 0.33,            // 灯ごとの差。0..1
  fixtureRank: 2              // 正規化済みの対象順
}
```

### 描画・再生の規則

- `positionAt(motion, timeMs, fixtureRank, regions)` は純関数にする。
- 毎フレーム `Math.random()` を呼ばない。ランダム源は seed と fixture rank から導く。
- seed から 3〜5 個の制御点、周期、方向、位相を生成し、閉じた滑らかなループへ補間する。制御点も補間後の点も、許可 region 内へ投影または再サンプルする。
- `別のばらつき` は新しい seed を確定し、一回の適用操作として履歴へ積む。再生・リロード・再描画では seed を変えない。
- `pathVersion` が未知なら描画しないのではなく、既知の安全な静止位置にフォールバックし、UIで「新しい形式の動きを編集できません」と明示する。

これは図上の動きの再現性の契約である。照射可能範囲、現場の設備・演者・観客の安全を判定するものではない。

## 5. 範囲と客席領域

### 領域データ

既定の5種は保存名だけで再現する。

```js
"stage:full" | "stage:left" | "stage:right" | "stage:front" | "stage:back"
```

指定範囲は v1 では矩形とする。舞台図のドラッグから正規化された座標を保存する。

```js
{ kind: "rect", u0: 0.18, v0: 0.30, u1: 0.72, v1: 0.70 }
```

- 正規化時に端点順をそろえ、`0..1` に clamp し、最小幅・最小奥行きを検査する。
- ポリゴンUIはこの契約の対象外。将来追加する場合は `kind: "polygon", points: [...]` を別バージョンとして追加し、自己交差検査と移行テストを先に置く。
- 客席領域は `audience:<id>` という明示的な図上マスクがあるときだけ選べる。マスクがなければ audience 型は disabled にし、理由を表示する。

### 点の配り方

1. 対象 fixture を既定の物理的な下手→上手順で安定ソートする（同値は fixture ID）。
2. 領域内に同数の静止狙い点を、同じ入力なら同じ並びになる均等格子で作る。
3. 横型は点も左→右、奥行型は奥→手前へ安定ソートし、同じ index を結ぶ。
4. `選んだ順` を明示したときだけ、正規化済みの選択順を使う。

「最短マッチング」は将来の追加候補。v1 の安定ソートは、再現性・説明可能性・Undo差分を優先する。

## 6. 適用トランザクション

```text
preflight(selection, fixture capabilities, region)
  -> supported IDs / skipped IDs + concrete reasons
buildPatch(preset, choices, normalized selection)
  -> immutable next cue, changed attribute list
normalize(next cue)
  -> no-op なら履歴も保存もしない
checkpoint()                    // 一回だけ
write next cue
render + persist + announce
```

- スライダーや領域ハンドルの `input` は画面上のドラフトだけ。確定時に一回だけこのトランザクションを通す。
- 選択全体に変化がない場合は `checkpoint()` を呼ばない。
- 混在選択では、対象と除外を適用前に出す。例: `ムービング6灯に適用・固定2灯はそのまま`。
- 失敗時は元 cue を変更しない。部分適用をする場合も、除外一覧と変更一覧を同じ結果に含める。

## 7. 実装順と受け入れ基準

### P0 — 試作の純関数（隔離試作を実装済み、未接続）

1. 32型を `id`、担当属性、対応条件、既定値として宣言する。
2. `applySelectedLightPreset()` を DOM・描画なしの純関数で作る。
3. wander、範囲、点滅の入力を正規化する。
4. 以下の単体試験を先に通す。

実装物は `selected-light-presets-engine.js` と `selected-light-presets-engine.test.mjs`。既存試作の共有ファイルと本体には接続していない。

### P1 — 試作UI（隔離試作へ接続済み）

1. 既存の試作の「調整」側で、2灯以上の選択時だけ `型から選ぶ（32）` を出し、検索・カテゴリ付きモーダルへ接続した。既存の `見本｜調整` は変更しない。
2. 点滅はモーダルの静的な型名・説明としてのみ表示し、モーダルを開いた時点では自動点滅しない。
3. 適用は `applySelectedLightPreset()` の結果を cue へ差し替え、既存 `commit()` を一回だけ呼ぶ。試作ブラウザで6灯への適用と一手Undoを確認済み。
4. `motion.wander.stage` はこの試作の描画時だけ固定seedを解釈する。`motion.wander.stageAudience` は客席マスク未接続のため、理由を表示して無効にする。

### P2 — 本体接続の判断ゲート（別承認が必要）

本体の `Project > Scene > Piece` と JSON I/O に、選択可能なフィクスチャID・能力・cue属性をどう対応させるかを所有者が決める。その前に本体コードや保存形式を変更しない。

### 必須テスト

| # | 確認 | 合格条件 |
| --- | --- | --- |
| 1 | 同じ seed | 同じ時刻・同じ灯順で同じ位置 |
| 2 | seed変更 | 少なくとも一灯の経路パラメータが異なる |
| 3 | 領域境界 | サンプル点が全て許可領域内 |
| 4 | 灯順 | 同じ fixture ID集合なら入力配列順に依存しない |
| 5 | 範囲6種 | 全体・左右・前後・指定範囲が正規化される |
| 6 | 混在選択 | 非対応灯は不変で理由を返す |
| 7 | 属性保全 | 担当外属性と未知キーが深等価 |
| 8 | Undo | 一括適用とseed再抽選が各一回で完全復元 |
| 9 | no-op | 履歴、保存、toastを増やさない |
| 10 | save/load | 旧cue、未知キー、未知 `pathVersion` を壊さない |

## 8. 未決の所有者判断

- 本体で「選択灯フィクスチャ」を何のIDと能力で表すか。
- 客席マスクを誰がどの図面から作成・確認するか。
- 点滅の現場上限・安全手順を、スケッチ機能の外でどのように扱うか。
- 矩形指定範囲を最初のリリースで十分とするか、ポリゴンを先に必要とするか。

この4点はデータ互換性または現場責任の範囲を変えるため、P2 前に所有者判断が必要である。
