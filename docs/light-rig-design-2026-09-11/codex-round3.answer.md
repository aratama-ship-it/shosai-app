# 結論

Claude案Aの核である、**狙いを灯体のパン／チルトではなく3D空間上の点として持つ方針は妥当**です。

ただし、次の二点は変更します。

1. `surface`によって座標の意味を変えない。床・奥壁・空中のどれでも、点は常に `{u, v, hM}` とする。
2. 空中の光を「その点で止まる光」と描かない。空中点は光が通る狙い点であり、光線はその先へ薄く延びる。

空中の水平移動はMVPとして十分な可能性がありますが、データ構造まで水平面へ固定してはいけません。線のA・Bは最初から完全な3D点にし、円には軌道面を明示します。

# 1. 空中の狙い点の設計批評

## 確認事実

現在の試作は、同じ `path` 内の `v`を次の二つの意味で使っています。

- 床：舞台の奥行き
- 奥壁：高さの割合

[rig-engine.js](</Users/arata/Library/Mobile Documents/com~apple~CloudDocs/claude code files/show-creative-ideas/shosai-app/docs/light-rig-design-2026-09-11/prototype/rig-engine.js:95>)

この方式へ空中を追加すると、`v`が場面によって奥行きにも高さにもなり、3D表示や演者追尾へ進む際に再変換が必要になります。

ETCのAugment3dには、灯体へパン／チルト値を直接指定する方法とは別に、空間上のXYZ位置へ光を向ける「XYZ Programming」があります。画面上の点へ向けるClick-To-Focusや、床上の位置に顔・胸の高さを加えるFocus Heightも用意されています。[ETC公式：Augment3d Terms](https://www.etcconnect.com/WebDocs/Controls/EosFamilyOnlineHelp/en/Content/20_Augment3d/Augment3d_Terms.htm)、[Working with Fixtures](https://www.etcconnect.com/WebDocs/Controls/EosFamilyOnlineHelp/en/Content/20_Augment3d/03_Fixtures_in_Augment3d/Working_with_Fixtures_in_Augment3d.htm)

これは、今回の「実現方法ではなく、どこへ光を向けたいかを渡す」方針と整合します。

## 確定案：点の意味を統一する

`surface`は幾何の変換方法ではなく、UI上の拘束条件として扱います。名称も `targetKind` または `aimArea`へ変える方がよいです。

```js
aim: {
  targetKind: "floor" | "backWall" | "air",
  path:
    { kind: "still", point: Point3 }
  | { kind: "line", a: Point3, b: Point3, start: "a" | "b" }
  | {
      kind: "circle",
      center: Point3,
      radiusM: 1.5,
      plane: { kind: "horizontal" },
      direction: "cw" | "ccw",
      startAngle: 0
    }
}

Point3 = {
  u: 0..1,
  v: 0..1,
  hM: 高さm
}
```

各点の意味は常に同じです。

- `u`：下手から上手
- `v`：奥から手前
- `hM`：床からの高さm

UIが次の制約をかけます。

| 当てる場所 | UIが固定する値 |
|---|---|
| 床 | `hM = 0` |
| 奥の壁 | `v = 0` |
| 空中 | MVPでは自由な`u,v,hM`。往復のA・Bは同じ高さに連動 |
| 空中の円 | MVPでは水平面 |

現在のデータは読み込み時に変換できます。

```text
floor: {u, v} → {u, v, hM:0}
back:  {u, v:高さ割合} → {u, v:0, hM:高さ割合×会場高さ}
```

旧形式を新形式として解釈せず、バージョン付きの正規化処理で一度だけ変換します。

## 空中を水平面へ拘束するのは足りるか

### 判断

**MVPの操作制約としては採用できます。データ構造の上限にはしません。**

空中演者を静止して狙う、同じ高さで左右へ追う、同じ高さの周囲を回す、という用途は表現できます。

一方で、次の動きは表現できません。

- 演者の上から下へなぞる
- 上昇・下降する演者を追う
- エアリアルフープを正面から囲むような縦の円
- 斜めに上昇する軌道
- 灯体側から見たパン／チルトの円運動

ETCの卓では、円運動はパンとチルトへ波形を組み合わせて作られます。その結果が舞台空間の水平円になるとは限りません。[ETC公式：Table Effects](https://www.etcconnect.com/webdocs/Controls/HOG/HTML/en/sect-table_effects.htm)

サーカスで縦円や斜め軌道がどの程度頻出するかは、今回確認した資料だけでは断定できません。ただし、空中演者の上下移動を考えると、将来必要になる可能性は高いと判断します。

そのため、円には最初から次を持たせます。

```js
plane: { kind: "horizontal" }
```

将来は互換性を保ったまま、

```js
plane: { kind: "frontVertical" }
plane: { kind: "sideVertical" }
plane: { kind: "custom", normal: {...}, up: {...} }
```

を足せます。MVPのUIには`水平`しか出しません。

線のA・Bは初めから別々の3D点にします。MVPでは高さを連動させますが、将来その連動を解除すれば、斜め・上下移動をデータ移行なしで扱えます。

## 狙い点方式は空中でも成立するか

成立します。ただし、このアプリが分からないものを明記する必要があります。

3D狙い点から灯体方向は、

```text
direction = normalize(target − fixture)
```

で求められます。しかし現在は灯体型番、取り付け方向、パン／チルト範囲を持ちません。そのため、次は判定できません。

- 実際の灯体がその点へ届くか
- 首がどちら向きに回るか
- パンの境界をまたいで急反転しないか
- 舞台装置や人で遮られないか
- 光が対象へ十分な明るさで届くか

ETCの3D機能も、実機との対応には灯体位置・向きやプロファイル上のパン／チルト情報を使います。[ETC公式：Fixtures in Augment3d](https://www.etcconnect.com/WebDocs/Controls/EosFamilyOnlineHelp/en/Content/20_Augment3d/03_Fixtures_in_Augment3d/Fixtures_in_Augment3d.htm)

したがって、書き出しでは「空中点へ当てる」より次の言い方が正確です。

> L12：奥から2列目のトラス・下手寄り。舞台中央、奥壁から約3.0m、高さ約4.0mの空中点を通す。

`高さ4mの中央`だけでは奥行きがありません。最低でも次を含めます。

- 灯体番号
- 灯体のおおよその場所
- 下手／中央／上手
- 奥壁からのおおよその距離
- 床からの高さ
- 静止または軌道
- 実際の対象があれば、その説明

初回は自由点なので、最後は任意メモを足せるようにします。

```text
狙いの補足：空中ブランコの演者の胴体付近
```

これは演者とのデータ連携ではなく、照明担当者へ意味を渡す文章です。

# 2. 空中を足したときの描画

## 最も重要な区別

**空中の光は、空中点で物理的に止まりません。**

対象となる演者や器具がまだ3Dモデルとして接続されていない場合、その点に描く輪は「光が溜まっている表現」ではなく、狙いを示す編集記号です。

次の三種類を、色だけでなく形でも分けます。

| 狙い | 記号 | 光線 |
|---|---|---|
| 床 | 塗りのある楕円・光溜まり | 灯体から床まで |
| 奥壁 | 壁面に接した楕円 | 灯体から壁まで |
| 空中 | 中抜きの二重丸＋十字 | 灯体から狙い点まで濃く、その先を細い破線で延長 |

空中点から床へ、細い鉛直の補助線を下ろします。これにより、光溜まりと空中の編集点を取り違えません。

## 平面図

平面図では、空中点の`u,v`を直接編集します。

最小表示は次です。

- 中抜き二重丸
- 中央の十字
- `空中 4.0m`
- 選択時だけ床への投影位置を薄い点で表示
- 灯体から狙い点への線
- 選択灯だけA・B・開始矢印を表示

高さは記号の横に必ず表示します。

```text
A　空中 4.0m
B　空中 4.0m
```

20灯すべての高さを常時表示すると読めなくなるため、未選択灯は`空中`を示す小さな上向き記号だけにします。

現在の試作では、奥壁を狙う灯の平面表示が、灯体のX位置から奥へ真っすぐ引かれており、実際の狙い点のX位置を使っていません。空中対応時には床・奥壁・空中を別々に描くより、**すべて世界座標の光源Sと狙い点Tを投影する一本の処理**へ統合するべきです。[app.js](</Users/arata/Library/Mobile Documents/com~apple~CloudDocs/claude code files/show-creative-ideas/shosai-app/docs/light-rig-design-2026-09-11/prototype/app.js:220>)

## 正面図

正面図では`u,hM`を直接編集します。

- 左右：狙い点の横位置
- 上下：高さ
- 空中点から床へ鉛直破線
- 高さの寸法
- 奥行きはラベルで補う

```text
高さ 4.0m
奥壁から 3.0m
```

正面図では奥行きが重なるため、選択していない空中点へ詳細ラベルを出しません。

## 側面図

側面図では`v,hM`を直接編集します。

- 左右：奥行き
- 上下：高さ
- 空中点から床へ鉛直破線
- 横位置はラベルで補う

```text
高さ 4.0m
中央線から下手へ 1.2m
```

空中点を編集している間は、正面・下手側面・上手側面のタブを手動で探させず、次の二つを主にします。

```text
正面：左右と高さ
側面：奥行きと高さ
```

下手を見る／上手を見るの違いは横置き灯の配置には意味がありますが、空中の狙い点編集では左右反転による混乱が増えます。空中編集用には向きを固定した`側面（下手側から）`を既定にし、客席と奥壁の表示を常時残す方がよいです。

## 空中のドラッグ

一つの点を二つの図で編集します。

- 平面図でドラッグ：`u,v`だけ変更。高さを維持
- 正面図でドラッグ：`u,hM`だけ変更。奥行きを維持
- 側面図でドラッグ：`v,hM`だけ変更。横位置を維持

同じ座標を二つの図から編集できるため、変更していない軸を逆投影で求め直してはいけません。

# 3. 下手と上手のコピー

## コピーの意味

これは「左右を永久に連動する機能」ではなく、**選択した灯体から反対側へ新しい灯体を作る一回の操作**とします。

初回から連動関係を作ると、片側だけ後で変更したい場合の解除規則が増えます。

## 位置の変換

現在の矩形舞台座標では、次でよいです。

| 対象 | 変換 |
|---|---|
| トラス上 | 同じ`trussId`、`u → 1−u` |
| 床 | `u → 1−u`、`v`は維持 |
| 横 | `side`を下手↔上手、`v,h`は維持 |
| トラス自体 | コピーしない |
| 中央線上 | コピー対象外 |

将来、不整形な実在会場へ進んだ場合は、正確には`u`の反転ではなく舞台中央面に対する世界座標Xの鏡映です。現在の正規化された矩形舞台では両者が一致します。

## コピーするもの

配置だけをコピーする場合：

- 取り付け方法
- トラス所属
- 横位置・奥行き・高さ
- 灯体の分類
- 任意名

任意名はそのままコピーします。名前に含まれる「下手」「上手」を自動で書き換えません。自由文の意味を誤って変える可能性があるためです。コピー後は新しい灯体を選択し、名前欄をすぐ編集できる状態にします。

## コピーしないもの

- `id`
- 灯体番号
- 組への所属
- 元灯体との永続的な左右リンク
- 他シーンのcue
- 削除済み・無効な参照

灯体番号は現在の最大番号の次から、新しい連番を割り当てます。

```text
L03 → L21
L04 → L22
L07 → L23
```

欠番へ自動で詰めると、既存の図や会話で使った番号が再利用される可能性があります。番号の再利用はしません。

## 動きをコピーする場合

製品版では次の二択が妥当です。

```text
［配置だけコピー］
［配置と現在のシーンの動きをコピー］
```

現在シーンの動きをコピーする場合は、次も鏡映します。

- 静止先の`u`
- A・Bの`u`
- 円の中心
- 開始位置
- 水平円の回転方向

鏡像として同じ瞬間を再現するには、水平円の時計回り／反時計回りも反転させる必要があります。線ではA・Bの名前と開始側を維持したまま、各点の位置を鏡映します。

組は自動コピーしません。コピー後に次を出します。

```text
下手から上手へ4灯コピーしました。
［元に戻す］［コピーした灯で組をつくる］
```

`コピーした灯で組をつくる`を選んだ後に、組の動き方を選びます。元灯とコピー灯を勝手に`鏡のように動く`へ結びません。

元の組全体を選択していた場合に、新しい組を複製する機能は将来追加できます。組の一部だけを選んだ場合は、元の組構造をコピーしません。

## 反対側に既存灯がある場合

位置が近いという理由だけで、既存灯を同じ灯体とみなしません。

コピー実行前に予告を表示します。

```text
8灯を下手から上手へコピーします。
3灯は既存の灯体と重なります。

［重なる3灯を飛ばしてコピー］
［重なっても追加］
［やめる］
```

`置き換える`は初回には入れません。既存灯の全シーンcueまで消す危険があるためです。

重なり判定の候補は次です。

- トラス：同じトラスで、鏡映後の横位置が近い
- 床：鏡映後の床位置が近い
- 横：反対側で奥行きと高さが近い

閾値は概略図のための候補判定であり、「同一灯」と断定するものではありません。

## 操作の置き場所

左一覧の固定ツールバーに、複数選択用の`操作`メニューを置きます。

```text
操作
├ 複製
├ 反対側へコピー
├ 等間隔に並べる
└ 削除
```

右設定欄には置きません。この操作は一灯の属性ではなく、選択集合へ働くためです。

方向が混在する選択では実行前に方向を選ばせます。

```text
［下手から上手へ］
［上手から下手へ］
```

Undoでは、生成された灯体とその現在シーンのcueを一回でまとめて戻します。

# 4. 20灯以上の一覧UI

## 196pxは狭い

20〜40灯という件数自体はスクロールで扱えます。しかし196pxでは、次を同時に読めません。

- `L21`
- 任意名
- 取り付け場所
- 未設定／消灯／点灯／動き
- 組番号と順番

折り畳み見出しと絞り込みを足すと、さらに窮屈になります。

## 確定寸法

1440×900ではモーダルを **1320×860px**へ広げます。

```text
左一覧 248px
中央   716px
右設定 300px
列間   12px×2
左右余白 16px×2
```

```css
grid-template-columns: 248px minmax(620px, 1fr) 300px;
```

画面幅が足りない場合は、左一覧を196pxへ潰すのではなく、折り畳める248pxのドロワーにします。

行高は38〜40pxです。860pxの画面なら、一覧内におよそ14〜16灯を同時表示できます。40灯すべてを一画面へ詰めるより、場所見出し、検索、選択の維持が重要です。

## 一覧の唯一の階層

**階層は取り付け場所に固定します。組は階層にしません。**

```text
⌄ 奥から1列目のトラス　8灯・未設定2
  L01　中央ムービング　動き　組1・1番
  L02　中央ムービング　動き　組1・2番

⌄ 奥から2列目のトラス　8灯・未設定4
  L09　上手寄り　　　　未設定

⌄ 床　4灯
⌄ 下手側　2灯
⌄ 上手側　2灯
```

取り付け場所はショー共通で安定しています。組はシーンごとに変わるため、それを一覧階層にすると、シーン送りのたびに灯体行が大きく移動します。

組は各行の小さな文字で表示します。

```text
組2・3番
```

この表示をクリックすると組全体を選択します。右設定欄に、組員を順番付きで一覧表示します。

## 並び順

見出し：

1. トラスを奥から手前
2. 床
3. 下手側
4. 上手側
5. 取り付け不明

各見出し内：

- 灯体番号順

横位置順にすると、灯体をドラッグした直後に一覧行が移動します。番号順なら作業位置を失いません。

## 折り畳み

- 折り畳み状態はモード切替・シーン送りで維持
- 選択灯の見出しは自動で開く
- 折り畳み中の選択数を見出しに表示
- 未設定灯がある見出しには件数を表示
- フィルター変更で勝手に全見出しを開閉しない

## 絞り込みと検索

```text
［番号・名前で検索］
［すべて］［未設定］［消灯］［点灯］［動きあり］
```

20〜40灯が主要規模になったため、検索は初回から入れる方を推します。実装負荷が比較的小さく、灯体番号を指定されたときの移動量を大きく減らせます。

`点灯`は静止灯だけ、`動きあり`は移動灯だけに分けます。

## 選択

PC一覧の一般的な扱いに寄せます。

- クリック：一灯を選択
- `Shift`クリック：連続範囲
- `⌘`／`Ctrl`クリック：追加・解除
- 見出しのチェック：その場所の表示中の灯を選択
- `表示中をすべて選ぶ`：絞り込み結果だけ選択

フィルターで選択灯が隠れても、選択自体は解除しません。

```text
8灯を選択中（2灯は絞り込みで非表示）
```

と表示します。

一括操作は一覧上部へ固定します。

```text
［表示中をすべて選ぶ］［操作 ▾］
```

# 5. 将来の3Dとリアルタイムへの逃げ道

## 現状評価

### そのまま使える部分

- `project.lightRig`とシーンcueの二層
- 固定IDによる灯体参照
- 灯体位置を世界座標へ変換する関数
- 時刻を渡して狙い点を求める純関数
- 再生と書き出しが同じ幾何を使う考え方

### 変更が必要な部分

- 面ごとに座標の意味が変わる`surfacePoint`
- `surface`に依存する円計算
- モーダル専用の再生時刻
- 3D対象を参照できない狙い点
- cueの形式バージョンがないこと

## 今入れる最小の備え

### 1. スキーマのバージョン

```js
project.lightRig.version = 1
scene.lightRigCue.version = 1
```

未知の将来フィールドを読み込み時にゼロや既定値へ潰さないようにします。

### 2. すべての狙い点を同じPoint3へする

```js
{u, v, hM}
```

床・壁は入力制約です。描画関数内の特殊な座標解釈にしません。

### 3. 狙いの種類を判別可能な形にする

現在：

```js
aim: {
  kind: "point",
  targetKind: "air",
  path: ...
}
```

将来：

```js
aim: {
  kind: "entity",
  entityId: "...",
  anchor: "bodyCenter",
  offset: {xM:0, yM:0, zM:0.2},
  fallbackPoint: {...}
}
```

`entity`用の空フィールドを今から保存する必要はありません。`kind:"point"`という判別子だけで逃げ道を作れます。

ETCのAugment3dにも、移動するScenic Element MovableへFocus Paletteを関連付け、XYZオフセットを保ちながら追従させる仕組みがあります。これは将来の「演者または空中器具のアンカー＋相対オフセット」に近い考え方です。[ETC公式リリースノート](https://www.etcconnect.com/workarea/DownloadAsset.aspx?id=10737518944)

### 4. 共通の時刻から評価する

内部APIを次の形にします。

```js
evaluateLightCue(sceneCue, fixtureId, tMs, sceneContext)
```

現在は固定したcue設定と繰り返し軌道を評価します。将来は同じ入口で、演者位置と照明の時間列を評価できます。

灯体モジュール内部で`performance.now()`を直接読む構造にはしません。本体側の共通シーン時計から`tMs`を渡します。

### 5. timelineの空配列は入れない

将来用として`timeline:[]`を今から保存すると、意味が決まっていないフィールドが正本に残ります。今はcue全体にバージョンを付け、評価関数を一本化するだけで足ります。

## 1シーン1状態から時間軸への移行

現在のcueを次のようにまとめておくと移行が容易です。

```js
scene.lightRigCue = {
  version: 1,
  state: {
    lights: {...},
    groups: [...]
  }
}
```

将来のv2では、

```js
scene.lightRigCue = {
  version: 2,
  timeline: {
    durationMs: ...,
    segments: [
      { atMs: 0, state: {...} }
    ]
  }
}
```

へ変換できます。

移行時はv1の状態を`0ms`の一つ目の状態として置き、シーン終了まで維持します。現在の往復・円のループは、その状態内の手続き的な動きとして残せます。

これなら既存シーンの意味を変えず、後から同一シーン内へ、

```text
0秒：静止
3秒：演者を追う
8秒：消灯
```

を追加できます。

## 「適用して閉じる」は将来も使えるか

3D表示が増えても、必ずしも編集方式を変える必要はありません。

- 正本：本体へ最後に適用したrig/cue
- 編集中：モーダル内のdraft
- 3Dプレビュー：draftと現在の演者状態を組み合わせて描く

という構成なら、演者と照明をリアルタイム表示しながら、適用までは正本を変更しない方式を維持できます。

将来、本体のメイン3D画面上で直接灯体を編集するようになった時点で、即時反映へ変えるかを再検討すれば足ります。
