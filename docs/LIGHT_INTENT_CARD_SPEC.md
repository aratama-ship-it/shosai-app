# Stage Sketch 光の意図カード仕様

## 0. 結論

「光の意図カード」は、照明機材を置く前に、**この場面で光が観客の知覚に何を起こすべきか**を記録する、シーン単位の小さな設計カードである。

既存の照明駒・照明プリセットは「何を、どこへ置くか」を扱う。一方、このカードは次の4点を扱う。

1. 何を起こしたいか
2. 観客にどこを見てほしいか
3. 演者・背景・空間をどう見せ分けるか
4. いつ、どのように変化させるか

カードは照明図、キューシート、回路図、安全確認書の代わりにはならない。Stage Sketchの「演出意図を視覚とことばで共有するスケッチ」という役割を補強する機能として実装する。

## 1. 文書の状態

- 本文書は、2026-08-09に作成した仕様を、同日のローカル実装結果へ合わせて更新したものである。
- Phase 1のカードUI・保存・Undo／Redoと、Phase 3のMCPスキーマ・項目別差分までローカル実装済み。

## 2. なぜ必要か

### 2.1 現在できていること

現行Stage Sketchには、次の機能がすでにある。

- 平面図と正面図
- シーンごとの説明、背景、ビート、稽古情報
- 照明駒と照明種別
- 複数灯をまとめて置く照明プリセット
- JSONの書き出し・読み込み
- AI編集案を、差分確認と明示承認を経て適用するための設計

### 2.2 実装前に不足していたこと

照明駒やプリセットを置けば「配置」は残るが、次は必ずしも残らない。

- なぜその光が必要なのか
- 観客の視線をどこへ導きたいのか
- 顔を見せたいのか、輪郭だけを見せたいのか
- 背景を消したいのか、演者から分離したいのか
- 動作、台詞、音、時間のどこで変化するのか

この意図がないまま配置だけを保存すると、別の会場や別の照明担当者へ渡す際に、灯体の再現が目的になりやすい。光の意図カードは、会場や機材が変わっても保持したい「演出上の目的」を先に残す。

## 3. 設計原則

### 3.1 「機材」より先に「知覚」を書く

最初の入力欄で灯体名、回路、DMX、角度、照度を求めない。まず、観客から何がどう見えるべきかを書く。

### 3.2 「雰囲気」だけで終わらせない

「幻想的」「暗い」「暖かい」だけでは、実装時の判断材料が足りない。必ず、対象、観客の視線、見せ分け、変化の契機を一緒に残す。

### 3.3 シーンメモへ混ぜない

既存の `scene.note` は場面全体の説明である。光の意図は独立した `scene.lightingIntent` として扱い、場面メモを上書きしない。

### 3.4 配置と意図を一方向に固定しない

- 照明駒・プリセット: 具体化の候補
- 光の意図カード: 具体化の理由

一つの意図から複数の配置案を試せるようにする。プリセットを選んだから意図が自動確定する設計にはしない。

### 3.5 安全判断を偽装しない

カードに書かれた配置案や実装メモは、会場承認、機材適合、電源、吊り込み、荷重、防火、視認性、安全を保証しない。システム上も `not-assessed` 以外の安全認定を与えない。

## 4. 対象ユーザーと利用場面

### 主な利用者

- 演出家、ショー制作者、出演者
- 美術・照明・音響を含む初期打合せの参加者
- 稽古段階で舞台の見え方を比較するチーム

### 主な利用場面

1. シーンを作った直後に、光の目的だけを短く残す。
2. 平面図・正面図を見ながら、演者・背景・空間の関係を言語化する。
3. 照明プリセットを試す前後で、意図に合っているかを比較する。
4. 別会場や別チームへ渡す時に、配置ではなく目的も共有する。
5. AIへ変更を依頼する時に、何を守るべきかを差分として確認する。

## 5. 体験の核

操作感は、設定画面へ数値を入力する感覚ではなく、**稽古場で照明担当者へ「この瞬間、観客にはこう見えてほしい」と伝える感覚**を目指す。

カードを開いた時の順序は次のとおりとする。

> 意図 → 視線 → 見せ分け → 変化 → 実装候補

技術語を知っている人にも使えるが、知らない人でも最初の4項目を完成できることを優先する。

## 6. MVPの入力項目

### 6.1 必須4項目

| 表示ラベル | 保存キー | 入力 | 目的 |
| --- | --- | --- | --- |
| 何を起こしたい？ | `objective` | 160字以内 | 光によって起こしたい演出上の変化 |
| 観客はどこを見る？ | `audienceFocus` | 160字以内 | 視線の対象と、見せたくない対象 |
| 人・背景・空間をどう見せる？ | `layers` | 3レイヤー | 演者、背景、空間の役割分担 |
| いつ、どう変わる？ | `transition` | 選択＋160字以内 | 変化の契機、変化の種類、体感速度 |

### 6.2 レイヤー入力

各レイヤーは「状態」と「短い補足」を持つ。

| レイヤー | 状態の候補 | 例 |
| --- | --- | --- |
| 演者 | `reveal` / `soften` / `conceal` / `silhouette` / `separate` / `transform` / `unspecified` | 顔は出さず、身体の輪郭だけを残す |
| 背景 | 同上 | 背景は沈め、奥行きだけを感じさせる |
| 空間 | 同上 | 舞台全体ではなく、細い通路だけを開く |

状態名は内部値であり、画面では日本語で表示する。

### 6.3 変化の入力

`transition` は次を持つ。

- `triggerType`: `scene-start` / `action` / `line` / `music` / `time` / `manual` / `unknown`
- `triggerNote`: 何を合図にするか
- `change`: `hold` / `fade-in` / `fade-out` / `snap` / `crossfade` / `blackout` / `unknown`
- `tempo`: `instant` / `quick` / `breathe` / `slow` / `hold` / `unspecified`

ここでの `tempo` は観客が感じる変化の速さであり、秒数や卓データではない。

### 6.4 任意項目

- `mood`: 雰囲気や質感。80字以内。
- `referenceNote`: 写真、書籍、過去作品などの参照理由。200字以内。
- `implementationNote`: 灯体、方向、色などの具体化候補。300字以内。
- `sourceRefs`: 参照元。最大8件。

`implementationNote` は、採用済みの技術指示ではなく「要照明担当者確認」の候補として表示する。

## 7. 推奨JSON

シーン直下に、任意の `lightingIntent` を一つ持たせる。

```json
{
  "id": "scene_example",
  "kind": "scene",
  "title": "ひとりだけが残る",
  "note": "音が消え、演者が中央で止まる。",
  "lightingIntent": {
    "version": 1,
    "objective": "暗闇から人物が現れるのではなく、暗闇の中に最初からいたことへ観客が気づく。",
    "audienceFocus": "顔ではなく、止まった身体の輪郭と足元の狭い範囲を見る。",
    "layers": {
      "performer": {
        "intent": "silhouette",
        "note": "表情は読ませず、身体の外形だけを残す。"
      },
      "background": {
        "intent": "conceal",
        "note": "背景の具体物は判別できない程度に沈める。"
      },
      "space": {
        "intent": "reveal",
        "note": "演者の足元から奥へ、細い奥行きだけを感じさせる。"
      }
    },
    "transition": {
      "triggerType": "action",
      "triggerNote": "演者が中央で完全に止まった瞬間。",
      "change": "fade-in",
      "tempo": "breathe"
    },
    "mood": "静止した時間の中で、身体の境界だけが浮く。",
    "referenceNote": "Stage Sketch用の検討例。書籍の再現ではない。",
    "implementationNote": "逆光または高い横方向からの光を候補に比較する。会場と照明担当者による確認前。",
    "safetyStatus": "not-assessed",
    "sourceRefs": [
      {
        "kind": "book",
        "label": "ステージ・舞台照明入門",
        "locator": "PDF pp.2–4の基本三照明比較"
      },
      {
        "kind": "user",
        "label": "今回のシーン意図",
        "locator": "2026-08-09"
      }
    ]
  }
}
```

このJSONは仕様例であり、現行アプリへ読み込んでも保持されない。現行の `normalizeScene()` は定義済み項目だけを返すため、実装前に保存・読み込み・正規化・MCPスキーマを一緒に更新する必要がある。

## 8. UI仕様

### 8.1 配置

- シーン編集領域の「シーンの説明」に近い位置へ置く。
- 照明駒一覧の中には置かない。
- 初期状態は、1行の要約を見せる折りたたみ表示とする。
- 未入力時は「光で何を起こしたい？」の一問だけを見せる。

### 8.2 カードを開いた状態

上から次の順で配置する。

1. 何を起こしたい？
2. 観客はどこを見る？
3. 演者／背景／空間
4. いつ、どう変わる？
5. 雰囲気・参照・実装候補（任意）

3レイヤーは一般的な同型カードを並べるのではなく、舞台断面の順序に近い「演者／空間／背景」の帯として見せる。既存の正面図・平面図との関係が理解しやすくなるためである。

### 8.3 折りたたみ時の要約

以下を一文へ圧縮して表示する。

> 身体の輪郭へ視線を集め、背景を沈める。演者の静止を合図に、呼吸する速さで現れる。

自動要約が意味を変えないよう、初期実装ではルールベースで組み立てる。生成AIによる自由要約はMVPに含めない。

### 8.4 既存照明プリセットとの接続

- カードを保存しただけでは照明駒を自動追加しない。
- 「配置案を試す」を明示的に選んだ時だけ、現在のプリセット候補を表示する。
- 候補には「意図と一致する保証はない」と表示する。
- 適用後もカードを保持し、意図と配置を並べて比較できるようにする。

## 9. AI編集との接続

AIによる光の意図カード編集も、既存方針と同じ境界を守る。

> 指示 → 構造化された編集案 → 差分確認 → 明示承認 → リビジョン一致確認 → 適用 → JSON書き出し

### 必須条件

- AIがブラウザの状態を直接書き換えない。
- `update_scene_fields` を拡張する場合は、`lightingIntent` の全差分を表示する。
- 既存値の削除は、空文字への置換ではなく、削除操作として明示する。
- 「暗く」「幻想的に」など解釈が大きく分かれる指示では、一度に一問だけ確認する。
- 照明配置の提案と、意図カードの変更を別操作として表示する。
- 古いリビジョンに対する編集案は適用しない。

### AI差分表示例

```text
場面「ひとりだけが残る」
  観客の視線:
    変更前: 演者全体
    変更後: 顔を見せず、身体の輪郭と足元へ集める

  背景:
    変更前: unspecified
    変更後: conceal — 具体物を判別できない程度に沈める
```

## 10. 現行データとの互換性

### 確認済みの現状

- 2026-08-09の実装直前再確認では、ブラウザ版の現行書き出し形式は劇場データを同梱する `{ "kind": "shosai-stage-sketch", "version": 4, "project": { ... }, "venues": [...] }`。
- MCPの下書き・編集計画・読み込み用JSONは引き続きversion 3を使用する。
- ブラウザ内部状態の正規化はversion 3を基礎にしているが、書き出し時にversion 4文書へ包む。この内部状態と交換形式を混同しない。
- `newScene()` は `lightingIntent` を持たない。
- `normalizeScene()` は既知のシーン項目だけを返すため、未知の `lightingIntent` は失われる。
- MCPの `sceneSchema` と `update_scene_fields` にも `lightingIntent` はまだない。

### 推奨方針

`lightingIntent.version: 1` を持つ任意のシーン拡張として、ブラウザ版version 4とMCP版version 3の双方へ同時に実装する。光の意図の追加だけを理由に、どちらの文書形式も新しい版へ上げない。次の経路すべてで保持できることを確認する。

- 新規シーン作成
- ブラウザ内保存
- JSON書き出し
- JSON読み込み
- 「別のショーとして開く」
- Undo／Redo
- MCP読取
- AI差分作成・適用

一つでも経路が項目を落とす場合は、その経路を対応させるまで公開しない。将来、構造が非互換になった場合だけ、ブラウザ版またはMCP版の次の文書バージョンを別途設計する。

## 11. 安全と技術の境界

このカードから、次を確定事項として出力してはならない。

- 灯体・卓・回路・DMX・電源の適合
- 吊り位置、支持方法、荷重、落下防止
- 色、照度、スモーク、レーザー等の安全性
- 会場規程、消防、法令、保険への適合
- 演者・観客・スタッフの視認性や避難安全
- 歴史資料にある火、煙、粉じん、水、圧縮空気、旧式電気、重量物、可動機構の再現手順

UIには常に次の境界を短く表示する。

> 演出意図のスケッチです。実施方法と安全は、会場・照明担当者・専門家へ確認してください。

## 13. MVPの受け入れ条件

- シーンごとにカードを0件または1件保持できる。
- 必須4項目を、専門用語なしで入力できる。
- カードを閉じても意図の要約が一行で読める。
- 演者・背景・空間の役割を別々に記録できる。
- 動作、台詞、音、時間等の変化の契機を記録できる。
- 照明駒を置かなくてもカードだけ保存できる。
- カードの作成・変更・削除をUndoできる。
- JSONの書き出し→「別のショーとして開く」→再書き出しで値が保持される。
- 既存version 3／version 4のショーを読み込んでも、既存内容を変更しない。
- AI編集では変更前後を項目単位で確認できる。
- 既存の `scene.note`、照明駒、プリセットを上書きしない。
- `safetyStatus` は `not-assessed` のみを許可する。
- 日本語・英語の双方でラベルと境界説明が表示される。
