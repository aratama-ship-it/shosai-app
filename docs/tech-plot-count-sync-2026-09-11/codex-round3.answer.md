### 1. 比較と推奨

**B「場面内キーフレーム」を推奨します。** 場面を演出・共有・帳票の単位として保ち、その内部に時間を加える構造です。

| 案 | 波及・保存・Undo・iPad |
|---|---|
| **A 子場面** | 既存補間を呼びやすい。ただしカウント間隔を秒へ変換する必要があり、`cueSeconds`の範囲も含め「そのまま」では済まない。共有・FPV・演者ビューアは既存の場面切替を使えるが、親子関係を追加し、香盤表では子をまとめる処理が必要。子場面群の一括Undo、一覧の肥大化対策も要る |
| **B 場面内キーフレーム** | 保存に配置列を追加。既存補間から位置計算を再利用するが、再生制御は分ける。共有へ再生位置・状態・操作権を追加し、FPVと演者ビューアにも途中配置を渡す。香盤表の場面数は維持。配置点単位のUndo、iPadでの点選択＋舞台上編集に適する |
| **C 別モード「フォーメーション譜」** | 独立データにすると、通常場面との配置・ID・保存・Undoの対応が増える。共有・各ビュー・香盤表への変換も必要。専用操作を広く取れる利点はある。ただし、**Bを編集する別画面**ならBと両立する |

Aは初期実装が軽く見えて、場面の意味を各機能で補修する負担が残ります。Bなら「同じ場面の、この瞬間を別の席から見る」が自然です。

### 2. 最小モデルと再生

提案フィールド：

```text
track: { countBpm, firstCountSec }
scene: { trackId, arrivalCount, pieces,
  motion: {
    keyframes: [{ id, count, poses: { pieceId: {u,v} } }]
  }
}
```

`arrivalCount`は、**場面の先頭配置が成立する曲内カウント**。場面内`count`は1始まりとし、1の配置は既存`pieces`を使います。後続点は対象演者全員の配置を記録し、同じ駒IDを参照。初期は直線移動だけです。

場面内カウント`k`の音楽位置は：

`firstCountSec＋(arrivalCount＋k−2)×60/countBpm`

音楽位置から途中配置を計算し、全ビューが同じ結果を描きます。毎フレームの位置を保存データへ書き戻さず、Undoは配置点の追加・移動・削除を対象にします。

この文脈の「自動送り」は、**音楽に沿って場面内の配置を連続表示すること**です。初期は最後の点で音楽と動きを停止し、次場面へは手動。`cueSeconds`は場面間専用とし、前場面の最終配置→次場面の先頭配置を結びます。途中で場面を飛ばす場合の扱いは別途決めます。

### 3. 舞台スケッチらしい入口

まず通常の場面を開き、「この場面に動きをつける」で下部に短いタイムラインを展開。点を選び、舞台上で駒を動かして配置を記録します。時間欄を閉じても、現在カウントは残します。

iPadでは細い点のドラッグを必須にせず、「前／次の配置」「現在位置に追加」とカウント数値編集を用意します。

差別化の軸は二つです。

- **同じ瞬間を客席・正面・FPVで比較**し、映像面や大道具による見切れまで検討する。
- **会場を替えて動きを再検討**する。演者の相対配置と機材の実寸を保ち、修正すべき場所を見つける。

### 4. 段階の組み直し

S＝局所的、M＝複数機能への統合、L＝新しい再生・同期・互換性を伴う規模です。

**①映像面〔M〕→②ヒアリング〔S〕→③音楽の錨〔M〕→④占有駒〔M〕→⑤参照／書き出し〔M〕→⑦場面内キーフレーム〔L〕＋⑨場面内再生〔L〕→⑧曲線・多点経路〔L〕→⑥MVR〔L・需要次第〕**

②は①の前から資料収集を始めます。⑤はPDF参照と配置図出力に限定した見積りです。

⑦⑨は、一場面・一曲・少人数・直線移動・単端末で一緒に試作。その後、共有と演者ビューアへ広げます。⑧では「途中の形を作りたい」のか「到達時刻を増やさず経路だけ曲げたい」のかを分け、キーフレームと経路点を混同しません。

### 5. 次に聞く三問

1. **最初に再現したい動きは、床上の移動だけですか。それとも高さ・乗降・空中動作も必要ですか。**  
   保存する姿勢と補間方法が変わります。
2. **最優先は一人での演出確認ですか、複数端末で同じ瞬間を見る稽古ですか。**  
   共有再生を初期範囲へ入れるかが変わります。
3. **動きのある場面を開いたとき、先頭配置と代表的な見せ場のどちらを表示したいですか。**  
   `pieces`を先頭配置とする案で足りるか、代表位置の指定が必要かが変わります。
