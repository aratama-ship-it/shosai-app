## 1. 批評：方向は賛成、Phase2は分割すべき

現状は提示された事実を前提に評価しました。コード未読、Git使用・ファイル変更なしです。過去メモは正本とGOを分ける設計原則のみ参照しました。

**「カウント錨」と「自動送り」は別機能です。** 前者は場面を音楽のどこに対応させるかという注釈。後者は進行を時計に委ねる再生エンジンです。横長の画面がなくても、後者には実質的な時間順序モデルが入ります。

不採用理由が「横長UIの操作性」なら自動送りは両立し得ます。しかし「作品を固定時間に従属させたくない」なら、元案は決定の迂回です。理由が確定するまで、**自動送りを既定のロードマップに入れるべきではありません。**

見落としは次の点です。

- **秒とカウントは単純な併記では済まない。** BPMだけでは数え始め、弱起、途中の数え直し、テンポ変化が決まらない。「3×8+1」も「第3エイトの1」か「24拍後の1」か曖昧。初期は固定テンポ＋第1カウントの秒位置に限定し、どちらを基準に編集するか決める。
- **到達位置と変化開始を区別する。** 指定カウントで配置が完成するのか、転換を開始するのか。`cueSeconds`との関係が未定です。一つの配置中に複数の光・音の変化があるたび、同じ場面を複製する構造も避けたい。
- **自動送りには停止・巻戻し・飛越し・手動GOとの優先関係が必要。** 共有セッションでは進行権限、各端末の音源対応も増える。準備条件を持つ転換を、時刻到達だけで進めるのは設計上衝突します。
- **「技術仕様なし」は削りすぎ。** バックラインの占有寸法や映像面の高さ・向きは見え方に不可欠。会場変更で位置を正規化しても、機材の実寸まで伸縮させない規則が必要です。
- **「プロットは作らない」というLPと、プロットPDF・入力表作成は矛盾。** 「演出の配置と見え方を共有する」を主語にし、対応範囲を具体的に説明した方が将来を閉じません。

## 2. 別角度の案：四つ

1. **カード追加より映像面を先に。** 初期形は位置・実寸・向き・静止画像。任意席からの遮蔽や見切れに直結します。投射距離・明るさ・実際の投影成立性は別問題として扱う。
2. **カウントは「そこから稽古する」入口に。** 場面を選び、対応音楽位置から再生するところまで。自動送りを試すなら、後日、単端末の明示的なプレビュー機能として独立採否する。
3. **連携はPDF・画像の参照から。** 他ツールの図面を場面・会場に紐づけ、版と作成者を残す。MVRは灯体位置を眺めるだけで誰の仕事が減るかを先に検証する。仕様には階層内の位置・向き・尺度があり、単なる座標列の取込ではありません。[MVR仕様](https://gdtf-share.com/help/developers/mvr_1_6/file-format-definition/index.html)
4. **駒は汎用の占有物＋名称から。** ドラム等の専用モデルや入力表は保留し、既存駒の寸法指定で必要性を試す。入力表は位置から推定せず、PA担当の確定資料を参照する形も候補です。
