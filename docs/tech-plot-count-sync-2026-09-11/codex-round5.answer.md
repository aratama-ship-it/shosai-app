### 1. 推奨は(b)の段階採用

**単体で制作を完結できる別入口を作り、データ規約を先に共有、本体への接続を後にします。**

| 形 | 評価 |
|---|---|
| (a) 完全独立 | 本体の並行編集と干渉しにくい。反面、保存変換・描画・iPad対応を二重に保守する |
| (b) 別入口 | 制作画面を絞れ、導入時も同じ動きデータを使える。ただし共通コードの変更は本体担当との調整が必要 |
| (c) 本体内モード | 導入処理は少ないが、単体アプリの検証と本体改修が絡み、今回の順路に合わない |

(b)でも「既存機能を全部すぐ共有できる」とは置きません。本体JSには初期化と機能がまとまっています。まず専用ディレクトリで進め、座標・演者識別・動き評価の契約を固定。描画の切出し、音源保存API、PWAのキャッシュ・保存領域は本体担当と調整します。

保存は`schemaVersion / dancers / stage / track / scene`を持つ単体用の包みを用意し、**`scene.motion`は導入先と同じ仕様**にします。キーフレームだけでは演者・寸法・音源を復元できません。

### 2. v0.1の範囲

**入れるもの**

- 名前・色・向きを持つダンサー、舞台の幅・奥行き、正規化座標。
- 一作品一曲、固定`countBpm`＋`firstCountSec`、8カウント格子。
- 先頭配置、配置点の追加・複製・移動・削除、Undo／Redo、床上の直線補間。
- 再生・停止・任意位置再開・区間反復、`heroCount`による代表画像。
- 自動保存、版付きJSON保存・読込、音源の別添／再選択。音源未接続でも配置編集は可能。
- iPadの駒ドラッグ、複数選択、拡大縮小、数値での時点編集。
- ホスト音源＋無音ゲスト追従。編集・再生操作はホストのみ。

**後回し**は曲線経路、テンポ変化、空中動作、身体の振付、同時共同編集、各端末での音声同期です。

Web Audio再生では、開始時刻と音源オフセットから音楽位置を求め、描画時に位置を評価します。`requestAnimationFrame`の回数で時間を積算しません。出力時刻との対応には`getOutputTimestamp()`を利用し、停止・シーク時に基準を更新します。[W3C仕様](https://www.w3.org/TR/webaudio/#dom-audiocontext-getoutputtimestamp)  
Vision Pro版とは時計の原則を合わせ、Swift実装の移植は前提にしません。

### 3. 単体での固有性

- **「この瞬間、客席にどう見せるか」から作る。** 平面編集と客席側プレビューを並べ、代表配置から動きを組み立てる。
- **同じ作品を違う広さで試す。** 相対配置は保ち、人の寸法は伸縮させず、間隔や移動距離の変化を見直す。
- **8カウントと演出意図を一緒に残す。** 「第3エイト・1で中央を空ける」のように、時点と短い指示を結ぶ。

競合にないと断定する機能一覧ではなく、演出家の制作手順を中心に据える差別化です。

### 4. 舞台スケッチへの導入

初期は**フォーメーション一本＝場面一つのmotion**。曲のセクションは内部の目印とし、照明・セット・演出上の区切りが必要な場合だけ複数場面へ分けます。

取込時には次を対応付けます。

- ダンサーID→`castId`と配置駒ID。名前一致だけで確定しない。
- 元舞台寸法→対象会場。`u,v`を保持した結果をプレビューする。
- 音源参照→既存／新規の楽曲ID。別編集版の曲を誤対応させない。

取込は一括Undo可能な操作にし、元作品ID・改訂を保持。再取込は差分確認を挟みます。導入後も別入口を専用編集画面として残し、同じデータを両画面から同時に書き換えない契約にします。

### 5. ロードマップ

- **M1〔S〕**：実際の一曲・配置メモを収集し、座標・カウント・保存契約を決める。
- **M2〔L〕**：単体で配置作成→音楽再生→修正→保存まで完成。実iPadで検証。
- **M3〔L〕**：客席プレビュー、無音ゲスト追従、オフライン・復帰を検証しv0.1成立。
- **M4〔L〕**：本体担当と共通化・取込・演者ビューアを接続。

早期検証は「半拍や待ちをどう書くか」「配置を直す頻度」「曲差替え」「指とペンの操作」「共有の遅れが稽古を妨げるか」です。

2. 最初の対象人数・曲の長さと、共有する端末数はどの程度ですか。
3. 共有稽古は同じ部屋が中心ですか、離れた場所からの参加も初期に必要ですか。
