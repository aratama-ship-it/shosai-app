第7ラウンド。フォーメーション記録アプリ（試作は完成に近い）の、記録フォーマットの設計相談です。

これまでの経緯:
- 時間の扱いは完成。`track = { name, countBpm, firstCountSec, firstSet, anchors:[{count,sec,locked}], meters:[{fromCount,beatsPerBar,beatUnit}] }`。
  anchors は「合わせ直しの点」で、点の間を線形按分して カウント⇄秒 を決める（曲はぴったり一定テンポではないため）。拍子は4/4のみ記録。
- 配置は `frames: [{ id, count, poses:{dancerId:{u,v}}, note, travel }]`。count=カウント（1始まり・0.25刻み可）、
  poses=正規化座標、travel=「何カウント前から動き始めるか」（それまで前の位置で待つ）。
- 舞台スケッチ（導入先）の場面は `scene = { id, title, pieces:[駒], cueSeconds(転換の長さ), note, 機構, 照明, audioTrackId, ... }`
  で、第3ラウンドでは「場面内キーフレーム `scene.motion.keyframes=[{count,poses}]`」を推奨とした（1曲＝1場面の前提）。

**本人の新しい指摘（これが今回の主題）**:
「フォーメーションごとに、状況によっては舞台スケッチのシーンがそれぞれに当てはまる可能性があるので、その可能性を考慮した上でのフォーマットにしたい」
＝ 1曲の中の各フォーメーションが、舞台スケッチの「場面」に1対1で対応することもあれば、1場面の中のキーフレームに過ぎないこともある。両方を1つの形式で扱いたい。

依頼（2,000字以内・見出し付き）:
1. フォーマット案。frames に何を足せば両方を表現できるか（例: asScene フラグ／sceneRef／グループ化）。
   「どのフォーメーションを場面にするか」を後から変えられること、変えても記録が壊れないことを重視。案を2つ比較して推奨を。
2. 場面の切れ目と時間の関係。舞台スケッチの `cueSeconds`（場面の転換の長さ）と、こちらの `travel`（何カウント前から動き始めるか）をどう対応させるか。
   場面をまたぐ移動と、場面内の移動で扱いが変わるか。
3. 場面にしたときに要る付随情報（タイトル、メモ、照明や機構の有無）。フォーメーション側で持つべきか、取り込み時に舞台スケッチ側で足すべきか。
4. 書き出し（JSON）の形。舞台スケッチへ渡すときの構造と、再取込（同じ曲を作り直したとき）に既存の場面と対応づける鍵。
5. この設計で見落としやすい落とし穴を3つ。
6. 本人へ聞くべき質問を最大2つ（答えで設計が変わるものだけ）。
