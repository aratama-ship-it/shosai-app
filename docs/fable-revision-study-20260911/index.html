1. 要約

  • 現状、届け直しの仕組みは製品にありません。正本（場面・人物・配置）はローカルファーストで、発行と受領の概念が入っているのは演者向け「事前学習リンク」だけ（明示公開・版番号・過去50版保持・個人メモは本人だけ）。台本・Q・転換・担当・役割別メモは docs 内の試作と契約の段階で、製品には未接続です（§2）。
  • 所有境界は4層に分けます。舞台の正本（演出・舞台監督が編集）／発行版（番号付き・不変・現場が読む）／部門共有メモ（部門が所有、チーフが集約）／個人メモ（本人だけ）。記録は「閲覧」「受領」「実行記録」「GO」を別物として扱い、R1 が持つのは受領だけです（§3）。
  • 変更の種類ごとに「保持するもの」と「受領を求める相手」を規則にしました。Q番号変更は意味の確認を失効させませんが、番号は舞台監督とオペの接点なので受領は必要、など「意味の確認」と「受領」を別状態にすると矛盾が消えます（§4）。
  • 推奨は「発行版＋受領票」。共同編集は不要です。現場が必要とするのは「共に書く」ことではなく「変わったところを自分の担当で読み、読んだと返す」ことで、既存の正本・注釈・共有セッションの契約とも矛盾しません（§5）。
  • 反証15件のうち矛盾が出た規則は5つで、いずれも規則側を直して解消しました：受領は「最新」でなく版へ結ぶ／発行済み版は取り消さず戻し版を出す／差替えはIDを保つ／道具は契約に無いので未確定扱い／未確定は全員でなく舞台監督へ集約。合成データによる結果で、現場実例による確認はまだです（§7）。

3. 所有境界（4層）と、混同しない4つの記録

層1 舞台の正本

場面・人物・セット・Q・アンカー・予定・担当。編集できるのは演出・舞台監督（オーナー）だけ。ローカルファーストのまま。MCP／AI 編集は既存の revision・承認経路を使う。現場の担当はここを直接編集しない。

層2 発行版（edition）

正本から明示操作で切り出す番号付きの不変スナップショット。変更票（何が・どの範囲で変わったか）と影響対象を一緒に持つ。現場が読むのはこれ。追記専用で、取り消さず「戻し版」を出す。系譜（親の版・正本ハッシュ）を持つ。

層3 部門共有メモ

照明・音響・舞台の各部門が所有。ID（cueId・sceneId）を参照し、番号や場面名は表示時に解決する。チーフはここだけを集約して読む。発行版には入らない（版を進めない）。

層4 個人メモ

本人の端末または本人のアカウントだけ。チーフにも代役にも見えない。渡すのは本人の明示操作。既存の事前学習リンク・注釈契約と同じ境界。

4つの記録を別物にする
記録意味R1 での扱い混同したときに起きること
閲覧確認画面を開いた記録しない。「開いた＝読んだ」ではないため自動既読が受領に化け、舞台監督が「届いた」と誤認する
受領自分に関わる変更票を読んだ、と本人が返したこれだけ持つ。版に紐づく（self／proxy）。項目ごとではなく版ごと—
実行記録卓へ反映した、稽古で通した、本番で実行した持たない。契約上も範囲外受領済みが「反映済み」に読まれ、未反映のQが見過ごされる
GO本番の合図の発信・受信持たない。アプリは合図を発火しない（既存契約）受領操作や台本スクロールが合図に見える

権限の要点: 発行できるのは層1のオーナー（複数端末は同一人物）。受領できるのは影響対象に含まれる本人。代理受領（紙で手渡した等）はチーフが「誰が」を残して記録し、本人受領とは別に表示する。部門共有メモの作成者は部門の担当、閲覧は部門とチーフ。個人メモの閲覧は本人だけ。

未確定の扱い（ハイブリッドの中核）: 相手を1人でも計算できた変更は、その相手にだけ受領を求め、未確定の理由（担当枠 null、部門未設定、参照切れ）を舞台監督の「要確認」へ集約する。誰一人計算できない変更だけ全員へ届け、「対象未確定」と明示する。これで対象だけ通知の見落とし（S04b・S05・S12）を塞ぎ、全員通知の疲弊（S12）も避ける。副作用として、未割当の予定が場面に残っていると変更のたびに要確認が付く（S04a）。これは未割当を解消する圧力として妥当と判断した。

5. 方式比較 — 発行版・差分承認・共同編集

評価軸A 版ごとのスナップショット共有B 変更差分の承認と再配布C 共同編集推奨 A＋（受領票）
最小の現場価値「いま読むべき版はどれか」が確定する。差分は版間の比較で作れる変更1件ごとに承認と配布ができ、精度は最も高い配布の遅れが無い。ただし「正本」と「読む版」の区別が消えるA に「版ごとの変更票」と「本人受領」を足す。舞台監督が「版7の関係者で未受領は誰か」を答えられる
オフライン・復帰版は不変なので、復帰後に版番号で突き合わせるだけ未承認差分の順序と依存が端末間でずれる競合解決（CRDT または手動マージ）が必須。現場で解決させられない受領票を版に結ぶ（S07）。系譜の違う正本からの発行は止める（S08）
既存資産との整合事前学習リンクの「明示公開・版番号・過去版保持」と同型。MCP の revision／history とも整合AI 編集計画（plan／apply／expectedRevision）と同型だが、それは AI→本人の承認用で、本人→現場の配布には重い注釈契約は「同時編集は上書きせず競合」、Supabase 同期は凍結、共有セッションは揮発でホスト権威。全て C と逆向き既存契約を1つも変えずに載る
誤配の型版単位なので関係ない変更も一緒に届く（変更票で絞る）承認待ちが詰まると現場が旧版のまま動く誰が何をいつ変えたかが現場で追えない。代役が正本を書き換えうる変更票の影響対象で絞り、未確定は要確認へ（§4）
実装量（R1）小。版・変更票・受領票の3レコードと導出2つ中〜大。全実体の差分エンジンと承認 UI大。同期基盤と競合 UI。ライセンス・外部スクリプト禁止の制約とも衝突しやすいA と同じ規模

共同編集が不要な理由

  1. 現場の要求は「共に書く」ではない。本人が確認した要件は、役割別の画面で自分の操作と前後関係を読むこと、部門メモをチーフが集約すること、確認欄を実行記録・GO と分けること（dev-preferences 2026-09-09、3件）。いずれも読む側の要求で、正本の編集権を広げる要求ではない。
  2. 正本の所有境界を壊す。代役や部門オペが正本を編集できると、発行版の系譜と受領の根拠が崩れる。部門メモ・矢印・付箋は既に「正本と別レコード」と決まっており、共同で書きたいものはそちらで足りる。
  3. 既存の決定と逆向き。注釈の同時編集は競合扱い、クラウド同期は凍結、リアルタイム共有はホスト権威で揮発。C を採るとこれらを全て再設計することになる。

案 B を捨てない部分: 版の中の「変更票」は B の差分の考え方そのもの。承認フローだけを外し、差分は舞台監督が発行時に分類する（自動差分は R1 では行わない）。

8. 推奨（条件付き）

「発行版＋受領票」を採り、R1 は製品に触れない局所試作から始める

  • 層1〜4 の所有境界と、閲覧／受領／実行記録／GO の分離（§3）を先に固定する。
  • 変更の分類と影響対象の規則（§4）を発行時の舞台監督の操作にする。自動差分は後段。
  • 通知はハイブリッド（§6）。未確定はチーフの要確認へ集約し、誰にも計算できないときだけ全員。
  • 受領票は版に紐づく self／proxy の2種だけ。発行版は追記専用で、戻すときは supersedes 付きの戻し版。

条件（これが変わったら結論を見直す）

  1. companion workflow か本体統合か（WORKFLOW_IO_AUDIT 着手条件2）が未決。発行版は companion file と同じ「別ファイル」として置けるが、本体統合が選ばれた場合は edition／receipt の保存位置を再検討する。本研究は本体へ統合しない。
  2. 転換1件の実例照合（HANDOFF_STAGE_TRANSITIONS §6）が未実施。実例で「受領を求める相手」の規則が現場の理解と違えば §4 を直す。
  3. 製品化レビュー D1〜D3（_reviews/2026-09-10、提供形態＝公演単位の仮案）が未決。公演単位の提供なら「公演回スコープの代役」（S06 の将来課題）が優先度を上げる。
  4. 台本試作側の保存基盤（PDF asset store、書出し bundle）が未決。発行版に PDF バイナリを含めない前提は companion 契約と同じ。
  5. UI 修正（R01〜R36）と監査（段0 BLOCKED）は並行中。R1 の局所試作はどちらにも依存しないが、製品接続はそれらの完了状態を再確認してから。
