## 実機QAで見つかった不具合と修正（2026-08-24・デプロイ済み）

**症状（実機iPad）**: ①ホーム画面PWAのアイコンが、緞帳の絵ではなく黒地に「舞」の一文字の
代替タイルになる。②機内モードでPWAを起動すると「認証が必要です。」が出る。

**原因（1つ）**: `worker.js` の401レスポンスに `Cache-Control: no-store` が無かった
（同ファイルの503には最初から付いており、付け忘れ）。Safariが401をHTTPキャッシュへ保存し、
アイコンURLの401が再生されてアイコンを取得できず、機内モードではページの401が再生されていた。

**修正（Version ID `b4f22804-159f-43ba-8dd8-174ce53d642c`）**:
1. 401に `Cache-Control: no-store` を追加。
2. `/icons/*.png|svg` と `/直下.webmanifest` だけを認証の手前で返す
   （`isPublicAppShellAsset()`）。iOSがアイコンを本体と同じ認証文脈で取れない場合への備え。
   **fail-closedの境界に開けた唯一の穴。条件を広げないこと。**
   公開されるのはロゴ画像とアプリ名・色だけで、資料棚・名簿・ショーデータは認証の内側のまま。
3. 回帰テスト `tests/worker-public-assets.test.mjs` を追加（6件）。
   境界が広がったら落ちる。テストは446→452件へ。

**本番で検証済み**: アイコン200／manifest200／401にno-store／
中身11パスすべて401／パス細工5パターンすべて401。

**★デプロイ時の重大な注意（2026-08-24に実際に踏みかけた）**:

### 続き: PWAだけオフラインが効かない（2026-08-24・Version `1f088b7e-38f8-4afe-bbbf-e4b67da3f539`）

上のアイコン修正でアイコンは直ったが、**ホーム画面PWAの機内モード起動は依然失敗**した。
実機で切り分けた結果:

| 試験 | 結果 | わかること |
|---|---|---|
| Safariタブで機内モード再読み込み | **表示できた** | Safari文脈ではSWが正常に入っている |
| PWAをオンライン起動 | **認証を聞かれ、入れたら開いた** | PWAはSafariと**別の認証文脈**を持つ |
| PWAで機内モード起動 | 失敗 | PWA文脈にSWまたはキャッシュが無い |

**判断**: PWAでもページは表示できた＝**ページ文脈の取得には認証が効いている**（style.css も
stage-sketch.js も200で取れた証拠）。効いていないのは**Service Worker文脈の取得だけ**。
install中の `cache.addAll(APP_SHELL)` が401で拒否され、**addAllは1件でも失敗すると全体を捨てる**
ため、SWのインストールごと落ちていたと判断した。

**対処（認証方式も公開範囲も変えずに済む道を選んだ）**:
- `stage-sw.js`: installを `Promise.allSettled(APP_SHELL.map(url => cache.add(url)))` へ。
  取れたものだけ保存し、失敗しても完了する。**★ここをaddAllへ戻さないこと。**
- `stage-sw.js`: 保存先と一覧をページへ返す `message` 窓口を追加（一覧の出どころを一箇所に保つ）。
- `stage-pwa.js`: 登録後に `warmAppShellCache()` で、**認証が効くページ文脈から**取得して
  同じキャッシュへ充填する。時間切れ3秒・1件の失敗で止まらない・既存は取り直さない。
- 版: `CACHE_NAME` v132→v133、`stage-pwa.js` ?v=3→?v=4（`build_stage.py` と
  版を直に固定していたテスト2件も更新）。テストは452→459件。

**検証の限界（正直に記録する）**: ブラウザペインでは**空のSWすら登録できない**ことを確認したため、
**ローカルでの動作確認はできていない。** 保証できるのは構文・テスト459件・版の整合まで。
実機での確認が要る。

**再テストの作法**: アイコン削除 → Safariのデータ消去 → 再追加 → 認証 →
**充填(22件)が終わるまで数秒待つ** → 機内モード。待たずに機内モードへ入るとキャッシュが不完全になる。

### さらに続き: 上の修正が新たなロックアウトを生んだ（2026-08-24・Version `fc9d4d43-a44a-47d2-9eeb-454dade046bc`）

### さらに続き: 真のオフラインでまだ開かない → 307のredirected印が原因（2026-08-24）

v135のデプロイ後、Wi-Fiも切った真のオフラインで再試験 → **まだ「ページを開けません」**。
2つの原因を特定・対処し、**Version `26594d9c-0c87-4d5a-95fb-4d9abb15efaf` としてデプロイ済み**。

1. **検証手順の不備（Claudeの指示ミス）**: v135デプロイ後、オンラインでPWAを一度
   起動してもらう手順を飛ばした。SWの更新はオンライン起動時に取り込まれるため、
   オフライン試験が**古いSWのまま**行われた可能性が高い。
2. **307リダイレクトとキャッシュの相性（本命・本番で証拠あり）**: Cloudflareの静的配信は
   `/stage.html` を `/stage` へ**307で送る**（curlで実証済み。パスワード露出事故の
   ときに見えた `307 -> .../stage` がまさにこれ）。この経路で保存した応答には
   **redirectedの印**が付き、**ブラウザは画面遷移への応答に印付きの保存物を使うことを
   仕様で拒む**。キャッシュは有るのに「ページを開けません」になる——症状と一致。

**対処（v136）**:
- 保存時に印を剥がした素の写しを作って入れる（`putCleanCopy()`。SWのinstallと
  ページ側`warmAppShellCache()`の両方）
- navigate経由の保存も `response.ok && !response.redirected` のときだけ
- リダイレクト後の姿 `/stage` も同じ画面として扱う（`STAGE_PATHS`。ただし2entryだけに
  保つことをテストで固定——増えたら資料棚への介入範囲が広がっている印）
- テスト487件全通過。本番境界も再確認済み

**★オフライン再試験の正しい手順（v136用。順番が肝）**:
1. **通信ありの状態で**PWAをアイコンから起動 → **20秒待つ**（新SWの取り込み＋充填）
2. PWAを完全終了 → もう一度起動 → 10秒待つ（新SWでの開き直しと保存を確実に）
3. 完全終了 → 機内モード＋**Wi-Fiがグレーであること確認** → 起動

### ★★完全解決（2026-08-24・本人がiPad実機で最終確認）

v136で、正しい手順（オンライン起動20秒→再起動10秒→完全終了→機内モード・Wi-Fiオフ→起動）
により**真のオフラインでPWAが起動した**。これで一連の症状はすべて実機確認済み:

| 症状 | 原因 | 解決 |
|---|---|---|
| アイコンが黒地「舞」の代替タイル | 401のキャッシュ＋アイコンが認証内 | no-store＋アイコン/manifestを認証の手前で返す |
| Safariを閉じるとPWAが「認証が必要です」 | iOSのBasic認証はSafari終了で資格情報が消える | クッキーログインへ移行（90日・HttpOnly・__Host-） |
| 真のオフラインで「ページを開けません」 | ①navigator.onLine誤判定 ②307由来のredirected印をブラウザが拒否 | 実fetchで判定＋保存時に印を剥がす（v136） |

**得た教訓（すべてコード内コメント＋回帰テストに焼き込み済み）**:
- Service Workerは認証ダイアログを出せない。Basic認証とnavigate横取りは両立しない
- `navigator.onLine` は通信可否の判定に使わない
- redirected印付きの保存物は画面遷移に使えない。保存時に剥がす
- `cache.addAll` は1件の失敗で全損。`Promise.allSettled`＋個別putで
- SW更新はオンライン起動で届く。オフライン試験の手順には必ず「先にオンラインで開く」を入れる
- iOSの機内モードはWi-Fiが残り得る。オフライン試験は**Wi-Fiがグレーであること**まで確認する
  （この落とし穴は本人が発見。これが無ければ偽の「解決」で終わっていた）

残: パスワード変更（下記・本人対応待ち）。変更するとその場で全トークンが失効するので、
変更後に各端末で一度ログインし直せばよい。

**★要対応（急ぎではない）**: curlの `%{redirect_url}` が認証情報を含むURLをそのまま

上の壁（Basic認証の資格情報がSafari終了で消える）を越えるため、**クッキーの会話へ移行した。**
クッキーはアプリの再起動をまたいで残り、Service Workerからの取得にも付く。

**判定順序**（`worker.js` の `fetch` 本体。この順を崩さないこと）:

1. `isPublicAppShellAsset` … アイコンとmanifestは認証の手前で返す
2. 設定不備なら503
3. `/sign-out` … クッキーを捨てて入口へ
4. `/sign-in` … ログイン画面（**認証の外**。でないと入る手段が無くなる）
5. **クッキー** … `readSessionToken()`
6. **Basic認証** … `matchBasicAuth()`。既存の道具（curl・MCP）の入口を残す。
   通ったらクッキーも配り、次からはクッキー側で通る
7. どちらも無い場合 … 画面遷移は `/sign-in` へ302、**副資源は401**
   （副資源にHTMLを返すとService Workerが中身として保存してしまうため）

**トークン**: `base64url(JSON{u,e}).base64url(HMAC-SHA256)`。
鍵は**その口座のパスワードから導出**（新しいSecret不要。パスワードを変えれば
その口座のトークンだけが自動失効）。改竄・期限切れ・別口座の鍵・未知の利用者名は全部落とす。

**クッキー**: `__Host-shosai-session`。`HttpOnly` `Secure` `SameSite=Lax` `Path=/` `Max-Age=90日`。
`__Host-` 接頭辞で置き場所を狭めている。

**安全側の作り**:
- **Basic認証を残した。** ログイン画面に不具合が出ても curl 等から入れる＝ロックアウトを構造的に防ぐ
- `WWW-Authenticate` は**あえて付けない**（ブラウザ標準ダイアログがログイン画面と競合するため）。
  Basic認証自体は受け付け続けるので `curl -u` はそのまま使える
- 戻り先（`next`）は同一オリジンのパスのみ。`//evil.example` や制御文字は `/` へ落とす

**ログイン画面**: 書斎の意匠で作成（`signInPage()`）。暗い客席にごく薄い緞帳の襞、
紙の上だけに明かり。入力欄は枠で囲わず下線のみ。**外部リソースを一切参照しない**
（認証の外に出る画面のため。CSSは埋め込み、絵は公開済みの `/icons/` のみ）。
写し: `docs/signin-preview.html` / `docs/signin-preview-error.html`（**正本は worker.js**）。

**テスト**: `tests/worker-session-login.test.mjs` を追加（24件）。461→**485件全通過**。

**未デプロイ。実機確認が必要な項目は下記「クッキー移行後の実機確認」を参照。**

**未対応の小さな指摘**: `worker.js` 自体が静的アセットとしてもアップロードされている
（`.assetsignore` に無いため）。認証の内側なので公開はされないが、**ゲスト口座で認証すれば
worker.jsを読める。** 認証情報は環境変数なので秘密は含まないが、認証の実装が見える。
