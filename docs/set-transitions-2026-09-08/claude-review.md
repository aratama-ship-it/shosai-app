# セット転換強化・独立設計レビュー（Claude Code Fable / 助言担当）

## 1. 結論

急ぐ核は手順表（誰が・いつ・何を）であり、前後場面の差分アニメは既に beginSceneAnim がかなりの水準で持っているため、入口としての「転換」タブ＋手順表（案1・2）を主軸に賛成する。ただし「差分生成→手順化」は現行 twinOf の照合仕様（setId の先勝ち一致）のせいで同一セット複数台で確実に誤対応するので、生成前に照合の一対一化を直すか、生成結果を必ず下書き扱いにして対応付けを手で直せるようにしない限り破綻する。時間については案5の「転換の予定尺へ統合する方向」に反対で、第1版では転換の合計秒は手順から導出される見積もり表示に留め、保存上の正本を増やさないほうがよい。また案6のデモ「屏風を同時に回転」は現行コードでは表現できない（通常セットの facing は補間対象外）ため、第1版の必須実装項目として明記が必要。

## 2. 確認した事実（ファイル/行）

- **twinOf は setId の `find` 先勝ち**（stage-sketch.js:15559-15564）。同じ setId の駒が複数あると全員が最初の1台に対応付き、beginSceneAnim も deriveRoutes/movedPairs（16796-16809）もこれに乗っている。Codex 報告に無かった重要な穴。
- **beginSceneAnim の補間対象**は u/v・beam・glow・base/pose の三区間・MACHINERY_ANIM_KEYS の機構値のみ（15612-15814）。**facing の補間は存在しない**。演者の入り・はけは袖歩き（15667-15711）だが、**セットの消失は即時消滅**で、exitPieces も「装置は対象にしない」と明記（16778-16783）。Codex 報告どおり。
- **手運びは差分から消える**：heldBy の駒は normalizeHolds が route を null にし（3792）、movedPairs も heldBy を除外（16800）。持ち手が運ぶ小道具は手順候補に一切出ない。
- **時間は既に3系統**：cueSeconds は到着場面の表示尺 0.2-10 秒（14904-14921、tests/stage-machinery.test.mjs:96-104）、sceneAnimMs は共通表示速度、rehearsal.transitionToNextSeconds は出発場面の稽古時間（3027-3030）。WORKORDER 88-94 行と VISION_PRO 100-101・304-329 行が「混ぜるな」「sceneAnimMs は時間情報ではない」と明文契約している。
- **正規化はホワイトリスト方式**（3927 以降）。project 直下の未知フィールドは読み込み→保存の往復で黙って消える。transitions[] は stage-sketch の正規化と mcp-server の validateDocument（project-store.js:246）・schemas 両方への追加が必要で、追加しても**旧版アプリで開いて保存すると transitions が消える**（version は 3 のまま無条件書き出し）。PROJECT_LIMITS（3048-）への上限追加も要る。
- cloneScene は piece.id を配り直し originId を残す（16737-16756）。転換を fromSceneId に紐づけるなら、手順が出発場面の piece.id を参照するのは整合的（複製場面は別の転換になるだけ）。

## 3. 案への判定

- **案1・2（平面図維持＋転換入口＋手順表）: 採用**。ゼロから要る能力は順序・担当・同時性であり、既存資産（動線曲線、袖ゴースト、機構補間）は再生側で流用できる。
- **案6のデモ: 修正**。「屏風を回転」は facing 補間（spin と同じ最短弧、animFacing）の新規実装が前提。「机を搬出」もセット用の袖歩き（演者 exits 15667-15690 の写しパターン流用）が前提。第1版仕様に両方を明記すること。
- **差分生成: 修正**。twinOf を originId 優先＋setId は距離最短の一対一マッチへ直すのが本筋（既存アニメの品質も上がる）。少なくとも生成結果は「下書き」表示＋対応付けの入替 UI を必須に。手運び・往復・途中待機は生成対象外と割り切り、手順の手動追加で受けるのが正しい（生成で頑張らない）。
- **案5（時間統合の方向）: 保留→縮小**。第1版では手順の所要秒合計を「見積もり」として表示し、rehearsal.transitionToNextSeconds と食い違えば並記するだけにする。正本の移行は実測運用が見えてから。cueSeconds は上限 10 秒の表示尺で実転換（数十秒〜）を表せないので、統合先候補ですらない。
- **案3の倍速: 削減候補**。スクラブ＋手順送りがあれば 0.5/2 倍は初版不要。
- **staffId 新設: 保留**。小劇団では転換要員＝演者が多いはず。第1版は castId 参照＋自由記述の役割名（配列）で足り、staff 名簿の正規化・UI 追加を丸ごと後送りできる。

## 4. 第1版仕様と検証

仕様：transitions[]（id, fromSceneId, toSceneId, steps[], 各 step は対象参照＝出発場面 piece.id＋表示用 setId、動作種別（移動/回転/搬出/搬入）、担当（castId または自由記述）、順序（前の完了後/同時）、予定秒、メモ）。参照切れ（場面削除・並替え）は削除せず「要再確認」バッジ。再生は beginSceneAnim の補間器を step 単位に分割して流用し、animFacing とセット袖歩きを追加。編集場面への書き戻しはしない。

検証（既存テスト様式で書ける小さなもの）：(a) transitions 入り JSON の正規化往復で値が残る、(b) 同一 setId×2 台で twinOf が一対一に対応する単体テスト、(c) 「後/同時」から開始時刻列を出す純関数のテスト、(d) 場面並替え後に要再確認フラグが立つ、(e) mcp-server validateDocument が transitions を通す。合否＝案6のデモ手順が編集→保存往復→再生→手順表表示まで通ること。

## 5. 要確認（ユーザー判断・実例）

1. 実際の劇団が使っている転換表・Qシートの実物（紙で刷るのか、袖で見るのか）——手順表の列設計はこれ無しで確定すべきでない。
2. 対象機器（稽古場でのタブレット利用か PC のみか）。
3. 転換要員は演者兼務か専任スタッフか（staffId 後送りの妥当性が決まる）。
4. 旧版アプリとの JSON 往復運用があるか（transitions 消失リスクの重さが決まる）。
5. 実転換の典型尺（予定秒の入力レンジと再生 UI の設計に効く）。

**解釈の明示**：「手順表が核」は、既存能力の偏り（前後アニメは有る・手順は皆無）からの私の推論であり、劇団の実際の要望の重心は未確認。上記 1 の実例入手を最優先に勧める。
