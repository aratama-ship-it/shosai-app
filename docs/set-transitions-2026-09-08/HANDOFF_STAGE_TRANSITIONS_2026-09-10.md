## 2. 本人が確認した要件

- 転換の中心は、平面図と手順表。担当、順次・同時、合図を扱う。
- 待機中に担当者が別作業へ回ることがあり、担当交代は柔軟に起こり得る。離れる、戻る、一部交代、全員交代を表せるようにする。
- 「セットを置く」と「担当を離れる」は別。手渡しの場合は、受渡しが終わるまで旧担当と新担当の両方を拘束する。
- 演者に加えて裏方も人物として扱う。一人が演者と裏方を兼ねる場合は同一人物として予定を重ね、二人分に数えない。
- 台本キュー、出番、移動、着替え、転換、待機、次の仕事を、人物ごとのタイムスケジュールで確認できる方向。
- 大道具の運搬・設置・固定などの所要に対して転換枠が短ければ、「入力した所要では何秒不足か」と根拠工程を示したい。
- 未定値を0秒や空き時間として扱わない。見積りによる不足を「物理的に不可能」と断定しない。
- アプリは担当や順序を勝手に最適化しない。警告と修正候補を示し、採用は人が決める。
- 現場GOの送受信・実行記録は今回の範囲外。局所試作の合図操作は「条件が揃ったとして試す」ためのもの。
- 本番用UI・UXの作り込みは、実例で意味と必要機能を確かめた後に行う。現段階でも、入力者・判断者・警告後の行動に関わる操作要件は記録する。
- Codex側の主担当モデルはAstra。Claude Code Fableは節目での独立レビュー役として使った。

## 3. 固めた意味の契約

正本は [SHARED_PEOPLE_CUES_TIME_CONTRACT_2026-09-09.md](SHARED_PEOPLE_CUES_TIME_CONTRACT_2026-09-09.md)。これは局所試作v1の意味の契約であり、製品の保存形式ではない。

### 人物・担当

- `personId` はショーに参加する実際の一人。演者・裏方・兼務のタグを複数持てる。
- `castId`、`roleId`、`staffId` は、既存の演者登録、台本役、名前付き担当枠への参照。同名やIDの種類だけで実在人へ自動統合しない。
- 1工程の1担当枠を `assignment` として扱う。未確定は `personId:null` / `resolution:unresolved` のまま残す。
- 同じ人物の排他的な予定が重なる場合に警告する。未入力の予定があるだけで「空いている」とは判定しない。

### 予定・台本・転換の関係

- 予定1回はプロジェクト内で一意の `activityId` を持つ。
- 台本、転換、個人予定のいずれかが正本となり、人物別予定や台本注釈は同じ `activityId` を参照する。同じ作業を二重保存・二重計上しない。
- 台本のPDF位置と予定は分離する。PDFアンカーの付替えだけで担当や時間を推測しない。
- 共通の `cueId` は合図定義であり、秒数や発生時刻そのものではない。

### 時間・待機・不足

- 内部単位は整数ミリ秒。未知は `null`、矛盾は無効として区別する。
- 時点は確認した起点からの相対時刻、先行工程後、複数条件の最遅、未知を区別する。
- 区間は `[開始, 終了)`。同じ時刻に終わる作業と始まる作業は時間重複にしないが、必要な移動や持替えは別工程として明示する。
- 担当を保持した待機はその人を拘束する。離脱後の待機には旧担当を含めない。
- 転換枠の終了は、達成すべき完了工程のうち最も遅い時点。順次工程は足し、実際に並行できる工程は全部を足さない。
- 不足は `max(0, 完了 - 締切)`。担当競合、時間不足、予備時間不足、未確認を同時に表示できる。
- 余裕0は「入力上は枠内／余裕0秒」。予備時間の不足とは分ける。
