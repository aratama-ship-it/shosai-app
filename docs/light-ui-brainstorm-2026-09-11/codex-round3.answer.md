## 1. 証言の重み付け：何を覆すか

［証言］天平さんは照明ソフトの利用を試み、使いにくさから出演動画の切り抜きへ切り替えています。単なる「こんな機能が欲しい」より強い情報です。**目的のために既に時間を使い、代替手段も選んでいる**からです。

［提案・推測］これによって、次の判断を覆します。

- **変更前**：動く光の作成は、静止図と参照で不足が確認されてから。
- **変更後**：まず動く光を作れる最小体験を試し、動画切り抜きと比較する。

一方、次はまだ確定しません。

| 証言が裏づけること | 証言だけでは裏づけないこと |
|---|---|
| 少なくとも一人に、既存ソフトでは満たせなかった需要がある | 同様の需要の広さ、競合不在 |
| 動画は本人が選んだ有効な説明手段である | 自作アニメーションが動画と同程度に伝わること |
| 操作を覚える負担が利用を妨げた | 指でなぞる操作が最適であること |
| 新しい手段を試す理由がある | 二分以内で完成すること |

「自分の舞台の動きを自分で作りたかった」は、文脈に合う有力な解釈です。ただし、転記された発言だけからは、既存照明ソフトで具体的に何を作ろうとしたかまでは分かりません。

**「決定事項に見える」懸念は、再生をやめる理由から、出力の意味を設計する条件へ移します。** 動きは明確に見せ、その中の何が希望で何が例示かを明記します。

なお、競合の「見つからなかった」は維持してよいですが、「ない」には進めません。Captureの公式紹介でも設計・文書化・可視化を扱っており、今回の一覧をすべて「卓操作前提」と一括するのは粗い整理です。操作負担の比較には別途実機評価が必要です。[Capture公式概要](https://www.capture.se/Products/Capture/Overview)

## 2. L〜Qの批評

### L：三つのプリミティブはよいが、定義を直す

［提案］**「光の形／動かし方／時間」の三つなら成立します。** ただし、現在のbeam＋pathでは、サーチライトの見え方を決める情報が一つ欠けています。

**足すものは「光線の向きがどう変わるか」。**

点が通り道を移動するだけでは、次を区別できません。

- 同じ場所から出た光が、向きを振る。
- 向きを保った光の帯が、横へ移動する。

必要なのは灯体のパン／チルトではなく、**絵としての光線の両端や向き**です。「光の先を動かす」「光全体を動かす」を区別すれば、機材をモデル化せずに扱えます。最初のサーチライト用途には前者を優先します。

**削るものは、必須の「拍」モデル。**

音楽の錨、カウント、曲の秒数、手動の合図は同じものではありません。最初は「動く速さ」「繰り返すか」「始めと終わり」で再生できるようにし、音楽との接続は必要な場合だけ開きます。

また、**未指定の出どころを客席上方などに黙って補う案には反対**です。図を成立させる仮の出どころは使えますが、「図の仮位置」として見せ、会場内の設置候補には変換しません。未指定の意図と描画上の既定値は分けます。

### M：「なぞって、再生」は有望。ただし最短とは限らない

［提案・推測］単純な往復なら、自由になぞるより、**始めと終わりを置いて「往復」を選ぶ方が速く修正しやすい**可能性があります。

最初の入口は次を推します。

> 光を置く → 光の先を始め・終わりへ動かす → 再生 → 速さを変える

自由になぞる操作は、曲線を描きたい場合の追加手段です。

iPadで考慮すべき落とし穴は次のとおりです。

| 落とし穴［推測］ | 対応案 |
|---|---|
| 指で光の先が隠れる | 光線本体より大きな操作点。触れている位置を補助表示 |
| 舞台の移動・拡大と描画が競合する | 「動きを描く」を明示。描画中に視点を動かさない |
| 手ぶれや迷いまで動きになる | なぞる操作は基本的に形だけを採り、速度は別に設定 |
| 平滑化で意図した角や停止が消える | 勝手に丸めすぎず、取り消し・描き直しを一手で |
| 3Dで触った点の奥行きが分からない | 最初は固定した正面図。奥行きの操作は見送る |
| 指を離した瞬間に予期せず再生する | 明示的な再生ボタンを使う |

［確認］ブラウザではパン・ズームと独自の指操作の扱いを決める必要があり、操作途中のキャンセルも発生し得ます。描画途中の線を完成扱いにしない処理が必要です。[W3C Pointer Events](https://www.w3.org/TR/pointerevents3/)

**二分以内かは未検証です。** 特に、舞台を作る時間、参照を探す時間、出力する時間を除いた計測だけでは、動画切り抜きとの比較になりません。

### N：三点セットは有効。ただし「三つ作る」操作にしない

［提案］同じスケッチから、次を一括生成するなら有効です。

1. 動きを読む短い動画
2. 範囲と前後を確認する一枚図
3. 守りたい点・変更可能な点を伝える一文

**動画を編集し、別に図を描き、別に文章を整えるなら、二分目標から離れます。** 一枚図は再生データの代表時点から生成し、意味を変えずに選び直せる形にします。

最初の動画形式はMP4を候補とし、GIF併設は後回しにします。ただし、iPadからの生成・保存と、LINEで受け取ったスマホでの再生まで確認してから採用します。ブラウザの形式対応判定だけでは出力成功は保証できません。[W3C MediaStream Recording](https://www.w3.org/TR/mediastream-recording/)

ループにも注意が必要です。**一度だけの演出を説明用に繰り返すことと、演出自体が反復することを区別**します。書き出し時に勝手に終点から始点へ光を戻してはいけません。

### O：「案」をラフさで担保する案は捨てる

［提案］**手描き風は任意の見た目であり、合意状態の表現には使いません。**

動きの滑らかさが要望の中心なのに、案らしくするために線を揺らしたり再生を粗くしたりすれば、伝えるべき内容を壊します。ラフな動画でも「この通りに」という指定には読まれます。

担保するのは画質ではなく、次の明示です。

> **光の動きの案**  
> 往復の範囲と速さを相談したい。出どころ・色・本数は変更できる。

動画単体で転送されても分かるよう、短いラベルは動画にも残します。照度や実際の光線可視性を再現したような数値・表示は付けません。

### P：再利用に賛成。ただし「同じ時間軸が既にある」は未確認

［確認］今回読んだコードには、音源のシーン割当と、同じ曲なら再生位置を保つ処理があります。一方、その箇所では再生位置を保存・Undoしない設計が明記されています。[現在の音楽処理](</Users/arata/Library/Mobile Documents/com~apple~CloudDocs/claude code files/show-creative-ideas/shosai-app/stage-sketch.js:4772>)

**音源を再生できることと、編集・保存・書き出しに使える共通時間軸があることは別です。** 音楽錨との接続やシーン内キーフレームの製品実装は、今回の限定した読み取りでは確認できていません。構想を完成済みの資産として工数から差し引かない方がよいです。

［提案］既存の描画や曲線計算は再利用しつつ、動く光にはまず短い説明区間の時間を持たせます。音源や合図には参照で接続し、未確定の合図へ勝手に秒数を与えません。

### Q：本体モジュール化に賛成。単独利用は入口の違いにする

［提案］「演目だけで開く」は有効ですが、最初から別製品として成立させる必要はありません。

同じモジュールを、既存シーンからも、最小の一場面からも開けるようにします。保存形式や共有方法を二つ持つ構成は避けます。

## 3. 「照明を作れるアプリ」の定義

［提案：説明文案］

> **舞台の絵の上で、見せたい光の形や動き、変わるタイミングを作り、再生できます。動きの動画と図、短い説明を照明担当者へ渡して、実現方法を相談できます。作るのは演出意図のスケッチです。灯体・回路・DMXの設計、実際の明るさや照射可否の検証、照明機器の操作は行いません。**

「照明を作れる」だけを単独で見出しにすると、実際の照明設計・制御まで含むように読まれます。主表示は **「光の見え方と動きを作って伝える」**程度まで具体化することを推します。

## 4. 統合案：最初から本体のモジュールを推奨

| 観点 | 別アプリから後で組み込む | 最初から本体のモジュール |
|---|---|---|
| シーン・舞台データ | 仮の舞台形式と後日の変換が必要になりやすい | 既存シーンを参照できる |
| 音楽錨・動線 | 独自の時間管理を作って重複しやすい | 接続先の契約を先にそろえられる |
| コード分離 | 別アプリでも密結合は起こる | 描画・再生・編集・出力を分けて独立検証できる |
| 公開単位 | 公開・保存・配布の経路が増える | 本体内の限定機能として段階的に出せる |
| 単独利用 | 専用入口を作りやすい | 最小の一場面を渡す入口で対応できる |

［提案］**本体用の独立モジュール＋開発用の小さな試験画面**が最適です。試験画面は動作確認用で、別製品にはしません。

データの境界は次のようにします。

- シーン・演者・セット・音源は、既存の正本を参照する。
- 光の動きは、シーンの意図カードに属する案として保存する。
- 音楽や合図へ接続するときは、元の識別子を参照する。
- 動画と一枚図は、同じ版のスケッチから生成する。
- 返答記録は案に対応させ、返答によって案を自動変更しない。

再生と動画出力が同じ時刻の状態を描く仕組みにすれば、「画面では合っていたのに動画では違う」を検証しやすくなります。

## 5. MVPの再定義：二週間で試すもの

**前回の「相談欄→出力→返答→動く図」という順を組み替えます。今回は「作る→再生→スマホで受け取る」を先に通します。**

以下は工数保証ではなく、二週間の試作を絞るための優先順位です。

### 最優先：書き出しの成立を早期に確認する

最初に仮の一本を動かし、対象iPadで短い動画を生成・保存し、受け手側のスマホで再生確認します。

出力を最後に回して、編集だけ完成した状態を作らないためです。外部送信の実操作は本人に行ってもらいます。

### 第1週：一場面を作って渡せるようにする

| 優先 | 最小機能 | 範囲 |
|---|---|---|
| 1 | 既存シーンから開く | 正面図を使用。舞台を作り直させない |
| 2 | 一本の光を振る | 始め・終わり、往復、速さ、太さ・色 |
| 3 | 再生して直す | 再生・停止・頭へ戻る・Undo。少ない操作で範囲を修正 |
| 4 | 動画を書き出す | 短い区間。案の表示と一文を付ける |
| 5 | 図を自動生成する | 始め・折り返し等を同じ再生データから切り出す |

一本から始めるのは検証を小さくするためです。天平さんの対象場面が複数光線を必須とするなら、**二本の交差・同時再生までを最小範囲へ入れ替えます**。一本しか動かない試作で複数光線の要望を検証したことにはしません。

### 第2週：本人の操作で不足した点を直す

- 天平さんに実際の一場面を作ってもらい、途中で教えずに観察する。
- 引っかかった操作を直す。自由なぞりは、端点操作で足りなかった場合に追加する。
- 既存の相談3欄と打合せ用出力へ接続する。動画作成の前には全欄入力を要求しない。
- 音楽との正確な関係が対象場面の核心なら、対象区間への接続を優先する。
- 返答はまず質問に対応する短い打合せメモで記録する。状態管理の拡張は後にする。

前回のP0.5だった「図上の動き」は主機能へ昇格します。一方、全種類の動作、3D編集、音楽のカウント編集、GIF併設、独立アプリ公開は初回試作から外します。

### 「動画切り抜きより速い」の検証方法

［提案］比較対象は機能数ではなく、**照明さんに渡せる説明を完成させる作業全体**です。

1. 天平さんが説明したい一場面を決める。
2. 普段の「出演動画を選ぶ・切る・説明を添える」方法で準備してもらう。
3. 同じ意図を試作で作ってもらう。舞台・素材の準備時間も別途記録する。
4. 照明プランナーに両方を見てもらい、方向・範囲・速度・光どうしの関係・未決事項を読み取ってもらう。
5. 天平さんに一箇所変更してもらい、直して渡し直す時間も比較する。

**二分は「既存シーンを開いてから、渡せる出力ができるまで」の暫定目標**とし、初回の準備時間を別表示します。本人の意図がまだ固まっていない時間も区別します。

成功は「二分で何か動いた」ではありません。**準備・修正が負担にならず、照明さんが重要な動きを同じ意味で読み取れたか**です。初回は動画に負けても、参照動画にない動きの作成や変更で価値が出る可能性があります。

## 6. 逆張り：動画切り抜きを中心にした最小案

［提案］別の動画編集ソフトを作らず、既存の切り抜きにStage Sketchが文脈を足す案です。

> 切り抜き動画を選ぶ → 自分の舞台図で範囲を示す → 「動画のどこを、ここで使いたいか」を一文で書く → まとめて渡す

初期機能は次だけで足ります。

- 切り抜き済み動画の取り込み、または参照先と区間の記録
- 舞台図への範囲・矢印の注記
- 「参照する点」「変更したい点」の一文
- 動画と図の対応が分かる出力

この案が勝つのは、**本人が適切な映像を既に持ち、動きの質感が重要で、舞台固有の違いを注記で説明できる場合**です。実写には光線、煙、身体、衣装の関係が含まれ、簡略アニメーションでは伝えにくい情報があります。

ただし、前例のない動きを考えるときや、「この光だけ逆へ動かしたい」と変更するときには弱い。したがって、**既存映像の説明を速くする道具と、新しい動きを作る道具は、比較しつつ両方残せます。**

## 7. 本人に確認すべき未決事項

1. **最初に天平さんが作りたい一場面は、一本の往復で説明できますか。それとも複数の光の交差・時間差が不可欠ですか。** 最小の再生機能が変わります。
2. **その場面では、動く感じを見せれば十分ですか。それとも実際の音楽の特定の音に、折り返しや交差を合わせて渡す必要がありますか。** 音楽接続と動画への音声同梱の優先順位が変わります。
3. **天平さんは舞台スケッチの既存シーンから始められますか。それとも舞台を登録せず、すぐ一場面を作る入口が必要ですか。** 二分目標に含める準備と、単独利用の入口が変わります。

今回の提案は、アニメーションを中心に据え直すところまでです。未確認なのは作成速度、出力互換性、照明プランナーの読み取り精度です。次は**対象の一場面を決め、その場面だけ作成・再生・受け渡しできる試作の仕様を固める**ことを推します。おすすめモデルはSolです。
