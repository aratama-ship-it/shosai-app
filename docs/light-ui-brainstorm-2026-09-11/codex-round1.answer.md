**私の推奨は、「振る舞い」を新しい駒の単位にせず、既存の絵と意図カードを“照明さんが解釈して返せる状態”にすることです。** Claude案ではBを縮小して採用、C・Dを修正して採用、A・Eを保留、**Fの自動的な専門語への置換は捨てます。**

「合意の記録」は必要ですが、それを中心にすると、舞台の見え方を共有する道具が確認業務の管理画面になる懸念があります。

指定のAGENTS.md、開発方針、意図カード仕様、照明まわりの文言を読みました。ファイルは変更していません。以下、**［資料確認］は公開一次資料、［一般知識］は慣行についての整理、［推測・提案］は今回の設計判断**です。現場での発生頻度や改善効果は実測していません。

## 1. 照明さんの側から見た批評

### プランナーとオペレーターでは、助かる情報が違う

［一般知識］照明プランナーには、作品全体の流れ、見せたい対象、見せ方の理由、変更できる条件が必要です。オペレーターには、識別できる合図、変化の内容、到達する状態、前後関係が必要です。同じ人が両方を担う場合もあります。

［資料確認］照明会社プルーブは、作品下見・打合せから図面とシートを作り、仕込みとフォーカスを経て、リハーサルで場面のつながりや変化の時間・タイミングを確認する工程を公開しています。**最初の要望だけで操作内容まで完成するわけではない**と読めます。[プルーブの業務工程](https://prove1997.jp/works.html)

［推測・提案］そのため、「演出家が一度入力すれば照明さんがそのまま実行できる」は目標にしない方がよいです。目標は、**何を相談すべきかが早く分かり、照明側の提案を受けて更新できること**です。

### 実在する受け渡し文書と、混同しやすい点

| 文書 | 用途・根拠の種類 | 起こりうる齟齬［推測］ |
|---|---|---|
| 照明要望書・イメージシート | ［資料確認］出演者側が希望をまとめる実例がある | 「青く」「明るく」が、背景の色なのか顔の見え方なのか不明 |
| きっかけ表・きっかけ記入済み台本 | ［資料確認］変化する箇所を台詞や動作に対応させる | 「台詞で変える」が、言い始め・言い終わり・その後の間で分かれる |
| 照明Qシート・操作表 | ［資料確認］操作のきっかけやレベル・変化量などを記録する | 要望一覧の番号を、そのまま卓のQ番号だと思われる |
| 香盤表 | ［一般知識］演劇では場面と出演者の対応などに使う。分野で用法が異なる | 登場していることと、その瞬間に光を当てる対象であることが混同される |
| 各場面のラフ図・平面図 | ［一般知識／資料確認］位置関係や舞台構成を伝える | 床上の円では、顔・全身・空中の身体・飛ぶ道具のどれを見せたいか分からない |
| 照明仕込み図 | ［資料確認］機材位置などを伝える技術資料 | 演出家の配置スケッチが、仕込みの指定図として読まれる |

照明要望書と写真を使う取り組みは、舞台スタッフのStage Crew Networkが公開しています。同社は言葉だけで生じる見え方のずれを課題として挙げています。ただし、公開記事は試作の紹介であり、改善効果の検証結果ではありません。[実務者による事例](https://scn55.com/現場の合間に、打ち合わせや新たな試作品。/)

きっかけを番号付きの明かり一覧と台本に対応させる実例は、舞台製作団体Boy Meets Girlが公開しています。操作表と仕込み図の役割は茨城県高等学校文化連盟演劇部の用語集でも区別されています。[きっかけ台本の制作例](https://bmg-web.com/hasegawa-howto-works/enzyo/)、[舞台用語集](https://www.engeki.koubun.ibk.ed.jp/160library/library_term.html)

また、ブディストホールでは舞台平面図と照明仕込み図を別に提出する案内があります。これは一会場の運用ですが、**Stage Sketchの要望出力で技術図面を代替しない方針**と整合します。[ホール利用案内](https://buddhisthall.com/facility/)

### 困る要望を、助かる要望に変える

以下は［推測・提案］です。

| 困る形 | 助かる形 |
|---|---|
| 「ここはムービングで追って」 | 「Aが中央から上手へ移る間、全身を見せ続けたい。光の移動自体を見せる必要はない」 |
| 「最後はゆっくり暗転」 | 「最後のキャッチ後に暗くなり始め、退場するまでに客席から姿が見えなくなる」 |
| 「この写真と同じに」 | 「参照したいのは背景から身体が分かれる見え方。色と灯体位置は合わせなくてよい」 |
| 「全部必須」 | 「道具が見えることを優先。色と光の形は変更できる」 |
| 「照明、確認済み」 | 「9/11の打合せで、Aの移動範囲を広く照らす案が出た。演出側の採否は未決」 |

サーカスでは特に、**観客が見る対象と、演者が見る必要のある対象を別に書けること**が重要だと考えます。「観客には身体の輪郭だけ見せたい」と「演者は投げた道具を見続けたい」は、同じ「見せ分け」欄にまとめると衝突が埋もれます。

## 2. Claude案A〜Fの批評

| 案 | 意思疎通への効果 | 作りすぎ・整合性 | 判定 |
|---|---|---|---|
| **A：振る舞い軸** | 「移動中も人を見せたい」などの入口には有効 | 止まる／追うは対象との関係、色変化・点滅は時間変化、光線が見えるは見え方。同列の種別ではなく併存する属性。色変化などは意図カードとも重複 | **分類し直して保留** |
| **B：打合せシート** | 既存情報を相手が読める順にまとめるので効果が期待できる | 全項目を一枚に押し込むと読めない。別帳簿にすると更新が二重化。「口頭説明の代わり」は言いすぎ | **縮小して採用** |
| **C：NGを図上に** | 言い落としやすい条件を位置・対象と結べる | 暗くしたい場所、演者の視認条件、機材の設置禁止は別概念。方向矢印だけでは姿勢・高さ・時間が抜ける | **条件と理由を付けて採用** |
| **D：返答・状態** | 質問と回答が同じ対象に残るのは有効 | 「できる／できない」は条件を落とす。「確認済み」は意味が広すぎる。`safetyStatus`の転用は既存原則と明確に矛盾 | **別の打合せ記録として採用** |
| **E：人への追随描画** | 対象との関係を素早く示せる可能性がある | 対象、追い始め、追い終わり、対象変更などが必要。既存の光動線と編集主体が競合する。床の円の追随では空中芸を十分に表せない | **MVPから外す** |
| **F：専門語の自動併記** | 同義語の補助表示には効果がある | 「走る→パン」「見える光線→ヘイズ」は言い換えを越えた実施方法の選定。既存i18nと同じ扱いにはできない | **自動置換案を捨てる** |

### A・Eの根本的な問題

［推測・提案］「この人を追う」には、少なくとも二つの希望があります。

- **人を見せ続けたい。** 光の移動は目立たなくてよい。
- **人を追う光そのものを見せたい。** 光が遅れる、先回りする、といった関係が演出になる。

ここを分けずに「追う光」を置くと、最初から後者の絵を提示してしまいます。機材名を消しても、実現方法への誘導は残ります。

まずは既存カードに「Aを移動中も見せる」と書き、対象を図で示せればよい。独立した動く光のモデルは、その表現では足りない実例を確認してからです。

### Cは「NG一覧」より「条件と理由」

［推測・提案］「空中芸だから前明かりNG」を標準テンプレートにするべきではありません。個別の演者・技・姿勢についての条件が、ジャンル全体の規則に見えてしまいます。

表示例は次のようにします。

> **演者が見るための条件**  
> Aが上を向いて道具を追う区間。本人から、正面上方の光が視界に入るという申告あり。場当たりで確認したい。

「暗く保つ」は演出希望、「機材を置かない」は配置条件として別に扱います。安全認定の状態は追加しません。

### Dは「返答」と「採用」を分ける

［推測・提案］照明さんが「別案なら可能」と返したことと、その案を演出家が採用したことは別です。

最初は、**質問／返答・条件／演出側の採否**を区別すれば十分です。回答者・日付・対象の版を残し、要望を変更したら「返答後に要望変更」と示します。共有済み、GO、実施済み、安全確認済みには読み替えません。

### Fで残してよい範囲

［資料確認］パン／チルトは灯体を位置づける制御項目です。[ETCの操作資料](https://www.etcconnect.com/webdocs/Controls/ElementOnlineHelp/en-us/Content/03_System_Basics/ML_Controls.htm)

［推測・提案］したがって「光が走る」を自動的に「パン」と出力するのは不適切です。残すなら、意味の説明や、照明担当者が自分で書いた用語の保持まで。実現候補も自動で併記せず、入力された候補だけを書き出します。

## 3. 別角度の案を5個

以下はすべて［提案］です。

| 案 | 誰が・いつ・何を入れて・誰が受け取るか |
|---|---|
| **① ムービングをモデル化しない「見せ続ける対象」** | 演出家が構想・稽古時に、対象と見せたい区間を既存の図とカードへ記入し、照明プランナーが受け取る。 |
| **② 意図カードの「変えてよい部分」** | 演出家が初回打合せ前に、守りたい結果と変更可能な色・方向・範囲を書き、照明プランナーが代案の条件として受け取る。 |
| **③ 写真・動画の「ここを参照」** | 演出家または照明さんが打合せ時に、参照画像や動画の時刻と着目点を記入し、相手が見え方の比較材料として受け取る。 |
| **④ 前後の絵と変化を読む** | 演出家がシーンを並べる際に、前の状態から何を変え、何を残すかを記入し、照明さんと舞監が流れとして受け取る。 |
| **⑤ 照明さんからの「こう解釈した」** | 照明さんが打合せ後に、要望に対応するラフ・参照・短い解釈を注釈として返し、演出家が意図との差を確認する。 |

**①＋②を第一候補、③を補助、⑤を次段階**に推します。

③は画像を並べるだけでは不十分です。「何を参照するか」を添える点を採用します。固定の写真パターンから選ぶ方式は、今回の自由な舞台構成では表現を狭めるため、主導線にはしません。

④は有望ですが、**シーン境界と照明変化の境界が一致するとは限らない**点に注意が必要です。一シーン内の変化を表すためだけにシーンを量産させてはいけません。

## 4. 逆張り：照明UIが増えるほど、関係が悪くなるとしたら

［推測］問題は、演出家が詳しく要望すること自体ではありません。**アプリの整った図と選択肢が、相談中の案を決定事項に見せること**です。

例えば、追随する光が滑らかに再生され、出力に「ムービング／フォロースポット」と載れば、照明さんには「この動きをこの機材で再現してほしい」と読めます。本人は単に「移動中も演者を見せたい」と思っていたとしてもです。

最小限に残すのは次の四つです。

- 見せたい対象と見え方
- 変わる瞬間・区間
- 守りたい条件と、その理由
- 照明側が解釈・提案できる余地

あえて作らないものは、灯体の自動推薦、追随精度の指定、機材能力による可否判定、演出家が照明さんを「承認済み」にする仕組みです。専門語を使える人の自由入力は残しますが、専門語を必須の入口にはしません。

**「お任せ」「まだ分からない」も、欠落ではなく意図的な回答として扱う。** すべての欄を埋めさせると、本人にない判断まで作らせてしまいます。

## 5. 最初の1〜2週間のMVP

［提案］**演出家が作り、打合せで見せ、返答を本人が記録するところまで**を最初の範囲にします。新しい共同編集基盤を含めない前提の優先順位であり、工数を検証済みの見積もりではありません。

### P0：既存の図と意図カードを、一続きの操作にする

**画面**

既存の側パネルに「照明の相談」を設けます。別の文書編集画面は作らず、現在のシーンと中央の図を保ったまま使います。

**入力**

既存の意図・視線・見せ分け・変化を再利用し、重複入力を作りません。新規項目は必要なときだけ開く次の三つに絞ります。

| 追加項目 | 具体的な入力例 |
|---|---|
| 守りたい条件 | 「Aが移動する間、道具と両手が見える」 |
| 変えてよいこと | 「色と光の形は相談したい」 |
| 相談したいこと | 「背景を沈めたまま道具を見せられるか」 |

条件は演者・道具・場所のいずれかと結べるようにします。図上の位置指定だけで意味が決まった扱いにはせず、短い文章を添えます。全項目の入力完了を保存条件にしません。

**図の扱い**

正面図・平面図のどちらを説明に使うか選べるようにします。身体の高さや輪郭は正面図、移動範囲は平面図で説明できるようにし、選んだ図を出力にも引き継ぎます。新しいビーム描画は足しません。

### P0：既存データから「照明打合せ用」を出力する

**出力内容**

シーン順に、図・意図・合図と変化・条件・質問をまとめます。公演名、対象会場、作成日、版を付けます。

- 入力されていない合図は「未記入」のまま出す。
- 一枚に収めるために文字や図を過度に縮めない。
- 既存の点灯／消灯／強さの表は、必要に応じて併記する。
- 要望の識別番号を卓のQ番号と混同させない。
- 明示的に共有対象とした内容を出し、個人メモは混ぜない。

まず既存の印刷経路を使い、PDF保存へつなげます。共有リンクは既存の共有経路で同じ内容を扱える場合に接続します。新たな送信・共同編集機能をMVPの前提にしません。

### P1：打合せの返答を、その要望の下に残す

**入力**

「質問」「返答・条件」「回答者・日付」「採用／保留」の小さな記録を置きます。本人が口頭の返答を入力した場合は「打合せメモ」と表示し、照明担当者本人が入力した回答のように見せません。

変更後も過去の返答を残し、「返答後に要望変更」を示します。照明側が直接返せる機能は、役割別ビューと注釈の共有仕様へ合流させます。

### iPad側パネルの情報設計

［提案・実機未検証］初期表示は次の程度に絞ります。

```text
シーン 04   ← 前へ  次へ →

照明の相談
Aの全身と道具を、移動中も見せたい

変わる合図
最後のキャッチ後から暗くする

守りたい条件　1件
相談したいこと　1件

［詳しく編集］ ［打合せメモ］
```

- 現在の要約と前後移動を上部に保ち、詳細は一項目ずつ開く。
- 「演者／背景／空間」の意味は保ち、細い三列にはしない。
- 図への対象指定と文章編集を同じ場所から往復できるようにする。
- 保存操作やキーボードで、次のシーンへ進む導線を隠さない。
- 日本語は「守りたい条件」など意味のあるまとまりで改行する。
- パネル幅は既存値を基準にし、幅を広げて解決する前に入力時の高さと中央図を確認する。

### MVPの判定方法

［提案］実際の短い演目を一つ使い、静止・移動・空中の場面を含めて照明さんに見てもらいます。

確認するのは「欄が埋まったか」ではなく、**見せたい対象と区間を同じ意味で説明できるか、質問を該当箇所へ返せるか、条件を守った別案を提案できるか**です。ここで不足が「動きの説明」と判明した場合に、A・Eへ進みます。

## 6. 本人に確認すべき未決事項

1. **最初の受け手は誰ですか。** 作品を一緒に作る照明プランナー、会場の照明担当者、当日のオペレーターのうち、誰とのやり取りを最優先にしますか。
2. **ムービングの要望が出た具体的な一場面では、何を伝えられませんでしたか。** 人を見せ続けること、動く光そのもの、空中の光線など、実例で確認したいです。
3. **一つのシーンの中で、照明はどの程度変わりますか。** 一場面一つの意図カードで足りるか、同じ場面内の複数の変化が中心かで設計が変わります。
4. **照明さんにはアプリへ直接入力してもらう想定ですか。** それとも、紙・PDF・対面での返答を本人が記録する運用が中心ですか。
5. **照明さんへ渡す駒の配置は、どの程度変えてよい案ですか。** 見え方が守られれば配置は任せるのか、光の方向や動き自体に演出上の指定があるのかを確認したいです。

未確認なのは、受け手本人の評価とiPadでの操作性です。次の一手は、**実際の一場面を今回の最小項目で表し、照明さんが何を聞き返すかを見ること**を推します。比較・整理の継続にはSolが適しています。
