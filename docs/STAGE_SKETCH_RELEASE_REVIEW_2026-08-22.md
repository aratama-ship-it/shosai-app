## 結論

楽曲を読み込み、シーンごとに割り当てて再生するMVPはローカル実装済みです。PC、iPad用PWA、スマホ閲覧UIの実描画確認と自動テストも通っています。

ただし、公開前に解消すべきデータ保護・認証・端末UIの問題が残っています。特に、Workerの認証設定ミス時の挙動、作業データを失う可能性がある導線、Mac AI編集の競合、実機iPad/iPhoneでの最終確認がリリース阻止項目です。現時点では「ローカル候補版」であり、公開可能判定ではありません。

## 今回実装した楽曲MVP

### 利用者から見える動作

- MP3、M4A、AAC、WAVを読み込めます。
- 1ファイル150MBまで、1プロジェクト24曲までです。
- 読み込み直後、その曲を現在のシーンへ自動で割り当てます。
- 音楽パネルで曲を選び、複数シーンへまとめて割り当てられます。
- シーンに曲を割り当てない設定も可能です。
- 同じ曲を割り当てたシーン間では、再生位置を保ったまま流れ続けます。
- 別の曲のシーンへ移ると曲を切り替え、曲なしのシーンへ移ると停止します。
- PCでは再生、一時停止、先頭へ戻る、シークができます。
- iPad PWAでは専用シーンバーと音楽ドロワーから操作できます。
- スマホでは下部の簡易プレーヤーから再生できます。スマホは閲覧・再接続中心で、曲の管理操作はPC/iPad向けです。

### 保存方式と安全設計

- 音声本体は `localStorage` やプロジェクトJSONに埋め込まず、端末内のIndexedDBへBlobとして保存します。
- プロジェクトには曲名、長さ、種類、曲IDと、各シーンの曲IDだけを保存します。
- 別端末や別ブラウザでは音声本体が存在しないため、「この端末に音源がありません」と表示し、同じファイルを再接続できます。
- 再接続時は曲名と再生時間を照合します。再生時間が5%または2秒を超えて異なる場合は、上書き前に確認を出します。
- 読み込んだファイルは、保存前にブラウザで実際に音声として開けるか検査します。
- 曲を削除してもUndoで復元できるよう、その場ではBlobを消しません。参照されなくなったBlobは次回起動時に整理します。
- 単一のaudio要素を使い回し、シーン移動ごとに再生要素が増えない設計です。

### 共有セッションでの扱い

- 共有されるのは曲のメタデータとシーン割り当てだけです。音声ファイルと再生位置は共有・同期されません。
- 各参加者は自分の端末で音源を再接続する必要があります。
- 同じ曲IDのまま共有文書が更新された場合、ローカル再生を不必要に止めないようにしています。
- 現段階の再生は演出確認用です。複数端末を同期した本番送出機能ではありません。

### MVPに含めていないもの

- シーン内の開始秒数・終了秒数
- フェードイン・フェードアウト
- 曲ごとの音量
- 複数端末の同期再生
- 音源を含むプロジェクト一括書き出し
- 本番用の厳密なキュー進行・誤操作防止

## リリース阻止項目

### P0: 公開前に必須

#### 1. Worker認証が設定不備時にfail-openになる

`worker.js` は認証用Secretが未設定、または片方だけ設定された場合に保護を無効化します。配信構成によっては、非公開ショー情報や名簿復号用データが認証なしで到達可能になるため、設定事故の影響が大きい問題です。

対応案:

- 本番環境では認証設定が不完全なら503で停止するfail-closedへ変更する。
- 非公開アセットを公開アセット群から分離する。
- deploy前のSecret・配信ファイル検査を必須化する。
- すでに公開された可能性がある鍵は、公開履歴を確認した上でローテーションする。

#### 2. `?fresh` を開くだけで端末データを削除できる

`stage-sketch.js` の `?fresh` 導線は、確認なしのGETで複数の保存キーを消去します。誤リンクや共有URLでも発動し得るため、公開版から削除するか、localhost・開発モードだけに限定する必要があります。

#### 3. 共有セッション参加前の退避失敗を見落とす

現在の参加処理は、既存作業の退避が容量不足などで `false` を返しても参加を続行できる経路があります。その場合、退避されていない作業をホスト文書で上書きする可能性があります。

対応案:

- 退避処理の成功・失敗を呼び出し元まで返す。
- 失敗時は参加を中止し、書き出しや容量整理へ案内する。
- 容量不足を再現する自動テストを追加する。

#### 4. Mac AI編集が新しい正本を古いブラウザ状態で上書きできる

Macブリッジは、外部MCP等で正本が更新された後でも、古いブラウザ状態を全置換で書き戻せます。expected revisionやNode側と共通のlockがなく、競合を検出できません。加えて、ブリッジの注入対象・navigation・origin制限も強化が必要です。

対応案:

- 書き込み時にexpected revisionを必須化し、不一致ならマージ確認へ進む。
- ブラウザとMCPで同じlock/commit経路を使用する。
- ブリッジを許可originと対象ページだけへ限定する。
- 外部ページへ遷移したmain frameからAI実行できないことを検証する。

### P1: リリース候補作成前に解消

#### 5. `stage-shows.local.js` の配信仕様が環境ごとに異なる

このファイルはHTMLから常に参照されますがgitignore対象で、Service Workerのapp shellにも含まれません。GitHub Pagesでは404、ローカルCloudflare buildでは含まれる、といった差が起こり得ます。

- 公開版に含めないのか、限定配信するのかを決める。
- 公開/非公開それぞれの正規build手順を分ける。
- deploy対象一覧と404をpreflightで検査する。

#### 6. iPadの機能到達性がPCと一致していない

iPad専用メニューには機構・3Dなど一部機能への入口がありません。また、Safariの通常タブではPWA専用UIが有効にならず、幅によっては長い単一カラムになります。

- PC/iPad/スマホごとの機能表を作り、意図的な非対応と欠落を区別する。
- Safari通常表示とホーム画面PWAの両方を実機確認する。
- 最低限必要な本番操作へ、常に到達できる導線を用意する。

#### 7. スマホで編集・自動保存できる一方、保護操作が隠れる

スマホではノートを編集・自動保存できますが、バックアップ、書き出し、保存警告、Undoが見えません。閲覧専用に寄せるか、編集するなら最低限の復旧・書き出し導線が必要です。

#### 8. importが確認前に会場ライブラリを書き換える

version 4 importでは、プレビュー確定前に会場ライブラリへ書き込む経路があります。Cancelしても残り、再試行で重複する可能性があります。kind、version、schema、ファイルサイズ、切り捨て件数の検証も不足しています。

#### 9. 壊れたショー棚を空として扱い、次回保存で上書きし得る

保存JSONが壊れている場合に黙って `{}` へ落ちるため、次の自動保存が棚全体を現在の1件だけで置き換える可能性があります。壊れた原文を隔離保存し、自動保存を止め、復元案内を出す必要があります。

#### 10. Macの書き出しキャンセルを成功として扱う

Save Panelでキャンセルしても、最終書き出し時刻と未書き出し変更数を成功扱いで更新する経路があります。ネイティブ側から確定結果を返し、成功後だけ状態を更新する必要があります。

#### 11. 公開アセットへ内部資料が混入する可能性がある

ルート配信時の `.assetsignore` が内部ログ・レビュー資料等を十分に除外していません。実際のWorkers bundle dry-runが未確認のため、配信対象一覧を生成し、許可リスト方式で確認する必要があります。

#### 12. 音源は現在のバックアップ対象外

既存の「端末データを書き出す」はlocalStorageだけを対象とし、IndexedDB内の音源を含みません。プロジェクトJSONにも音声本体は入りません。UIではローカル音源であることを表示していますが、別端末移行を重要視するなら音源込みパッケージが必要です。

## 推奨リリース順序

1. Workerをfail-closed化し、非公開アセットと公開buildを分離する。
2. `?fresh`、セッション参加前退避、壊れた保存データ、書き出し成功判定のデータ損失経路を塞ぐ。
3. Mac AI編集へrevision競合検出、共通lock、origin制限を導入する。
4. iPad/スマホの機能表を確定し、物理端末で縦横・PWA・Safariを確認する。
5. Wrangler bundle dry-run、オフライン更新、公開URLでのremote確認を行う。
6. 上記結果を記録してから、リリース可否を再判定する。

## 音楽機能の次段階案

次の拡張は、曲全体の割り当てを壊さずに、シーン単位のキュー情報を追加する形が安全です。

```json
{
  "trackId": "track-id",
  "startSeconds": 32.5,
  "endSeconds": 58.0,
  "fadeInSeconds": 1.0,
  "fadeOutSeconds": 2.0
}
```

優先順は次を推奨します。

1. シーンごとの開始位置
2. 「シーンに入ったら自動再生」か「待機して手動GO」かの選択
3. 終了位置と停止
4. フェード
5. 誤操作防止を含む本番キュー画面
6. 音源込みパッケージの書き出し・読み込み

同期再生や本番音響卓の代替は、遅延、端末スリープ、Bluetooth、ブラウザの自動再生制限まで要件化してから別機能として設計すべきです。
