台本PDF / Qシート / 舞台転換 / 人物・時間

台本と転換を、
同じショーとして安全に残す。

平面図は既存projectの正本に置いたまま、台本の位置・Q・人物の予定・転換をIDで結びます。PDFを差し替えても、紙面上の位置だけの変更で時間や担当を勝手に作り直しません。

今回の判断:

今は既存のv4 project exportへ新しい保存項目を混ぜません。現行の正規化処理には未知のproject項目を保持する保証がないためです。まずは対応する workflow companion file を定義し、全ての読書き経路を監査した後にだけ本体へ統合します。

この契約が防ぐこと

PDF差替えでQを失わない

新しいPDFは新しいdocumentとして追加します。旧anchorは残し、意味が確認できるまで「要付替え」として扱います。

紙面位置から予定を捏造しない

anchorはcueまたはsceneを指します。activity、担当、所要、GOは明示的な参照を追加した時だけ接続します。

端末ごとのPDF欠損を隠さない

PDFのBlobはJSONへ埋め込みません。別端末で見つからなければ位置とQを残し、「再接続が必要」と表示します。

古い保存経路で情報を落とさない

workflow対応前のbrowser、MCP、Mac、sessionは、workflowを含む書込みを正規化前に止めます。

3つの保存境界

同じショーを扱っても、平面図の正本、進行のmetadata、端末内assetは役割が違います。矢印はID参照であり、内容の複製ではありません。

既存 Stage Sketch project

  • sceneId / castId / setId
  • 平面図・動線・装置
  • 既存のv4書出し

workflowは座標やrouteを複製しない。

↔

workflow metadata

  • cueId / anchorId
  • activityId / personId
  • 時間式・確認revision

project bindingが一致した時だけ有効にする。

↔

端末内 asset store

  • PDF Blob
  • ページ描画の一時cache
  • assetIdだけをmetadataへ返す

別端末で欠けてもmetadataを消さない。

現行の音源と同じく、重いバイナリはmetadataと分離します。ただしPDF用の実store名・移行コードは、製品統合時に共同監査して決めます。

workflowに入れる、最小の関係

一つの紙面ラベルは一つのcueまたはsceneを対象にします。同じQを複数箇所へ置く場合はanchorを分け、同じ転換作業を台本・転換表・人物表で見る場合は同じactivityを参照します。

1. cue

2. script anchor

3. activity

改訂時に、何を残して何を見直すか

変更残す要確認へ戻す範囲
Q番号・人物名・PDFの表示名ID、意味、時間条件なし。表示だけ更新
紙面位置だけを動かし、意味が同じcue、activity、時間条件紙面位置の確認だけ
PDF版を追加旧document、旧anchor、Q新しい版への付替え候補
cueの意味・主GO・予定の開始/完了元データ、過去review依存する予定、時間枠、担当確認
PDFがこの端末にないanchor、Q、activity、所要再接続が必要。0秒や空きへ変更しない
base projectのhashが違うcompanion workflow全体要照合。自動マージしない

確認済みは、表示名ではなく意味・時点・所要・担当など判定に効く入力revisionに結びます。計算結果と人が確認した条件を一つの状態に混ぜません。

本体へ統合するまでの順序

  1. 入出力監査: browser normalizer、show shelf、ファイル読込・書出し、Mac、session、MCPが未知情報をどう扱うかを固定する。
  2. validatorとfixture: ID重複、参照切れ、頁/矩形、asset非埋込み、review revisionを検証する。
  3. 読み取り専用表示: Q → 紙面 → activity → 転換表をたどれるようにする。この時点では製品保存を有効にしない。
  4. 同一端末保存: metadata更新とasset参照追加の失敗時に以前の状態を残し、asset欠損を明示する。
  5. 外部version更新: 全経路が対応した後に requiredFeatures:["workflow-v1"] を持つ新しいexport versionへ進む。
この順序を採る理由

現行browser exportはv4、MCP exportは別のv3経路であり、現行のbrowser normalizerは既知fieldを再構成します。新フィールドを先に入れると、ある経路で読めても別の経路が保存時に落とす危険があります。先に検証可能な同伴ファイルとして関係を固定すれば、既存projectを壊さずに入出力監査を進められます。

根拠と、まだ決めないこと

確認した根拠

  • 台本試作はPDF Blob・Q・anchorを端末内復元できるが、本体project schemaとは未統合。
  • 人物・合図・時間の共通契約は、activityの所有元とID参照、改訂時の限定的な再確認を定義済み。
  • Stage Sketchの音源はmetadataと端末内Blobを分離している。PDFも同じ境界を採る。
  • 現行browser export v4とMCP export v3、未知fieldを落とし得るnormalizerを確認した。

この資料で決めないこと

  • 実際のIndexedDB store名、assetの上限、zip package、クラウド同期。
  • 実iPad、他端末、共同編集、競合アプリ独自形式、OCR。
  • GO送信、転換所要の自動見積り、PDF座標からの人物・時間推定。
  • 製品の外部version番号と移行コード。これは全読書き経路の監査後に決める。
