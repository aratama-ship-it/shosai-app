舞台スケッチ「AI作成マニュアル」— 各ユーザーが自分のAIに下書きを任せられるようにする設計計画

目的は、ユーザーが自分の使うAI（ChatGPT・Claude.ai・Gemini等）にマニュアルを読ませ、舞台スケッチの「保存 > 読み込む」で開けるショーJSONを吐かせられるようにすること。既存のローカルMCP（mcp-server/）は本人・開発者用に残し、配布しない。マニュアルはMCPではない（文書であり、検証・履歴・ロックは持たない）。その分、読み込み側の寛容さと、文書の正確さが成否を決める。

判断してほしいこと（8件）

  1. D1. 対象フォーマット。 AIに書かせるのは、ブラウザが読む形そのもの（kind:"shosai-stage-sketch"・数値 version:4・project・venues:[]）。MCP入力形（placements）は使わない。推奨: 採用（Claude・Astra一致）
  2. D2. 配布形態。 公開サイトに「AIに作らせる」ページ1枚（本文コピー／Markdown DL・見本DL・読み込み手順）＋アプリの保存パネルからリンク。推奨: 採用（一致）
  3. D3. 検証の置き場。 Claude案は「P1は文書の自己点検表のみ」。Astraは「P1から開発側の機械検証（構造・enum・参照整合・正規化前後の意味保持・保存往復）を必須に」。推奨: Astra案。理由: 読み込みは失敗せず「意図が黙って変わる」ので、文書だけでは欠落を検出できない（下の事実③④⑤）。アプリ内の点検表示は引き続き先送り。
  4. D4. 正本の責任分担。 Claude案「食い違ったら常にマニュアルを直す」は撤回。Astra案「ブラウザ入出力契約＝現行コード、創作の変換方針＝PLAYBOOK、配布本文＝その対象サブセット」＋enum・見本・本文の整合チェックをP1から持つ。推奨: Astra案
  5. D5. 照明の生成範囲。 ドラフトの「4種のlightKindをpieceに書く」は成立しない（lightKindはsets側、beam省略は真上6mに固定）。P1は照明駒を hang（真上）に限定し、横・前・床から当てたい意図は lightingIntent の文章で残す。4種を描画まで扱うのは別判断。推奨: hang限定で開始
  6. D6. 生成対象の種類。 列挙できる27種のうち、P1で「生成をサポートする」種類を明示的に選ぶ（案: performer / block / table / chair / bench / stool / wall / sphere / suitcase / light の10種＋高リスク装置は trapeze / tissue / cyrwheel / pole を「注意付き」で許可）。model・prop・舞台機構（seri/revolve/deck/curtain/pool）は対象外とし、noteで提案させる。推奨: この案で開始し、P2で拡張を判断
  7. D7. 新規下書き専用にする。 既存ショーの修正・再生成は扱わない（サブセットで再生成すると写真・注釈・音源・機構状態が失われる）。推奨: 採用
  8. D8. 公開時の契約文言。 「配置・照明・姿勢は検討用の図で、実施可能性や安全承認を表さない」「特定AIでの生成成功・秘密保持は保証しない」「共有セッション中はホストの変更が同期されるので、私的な検討は共有終了後に」「外部AIへ渡す素材はユーザー自身の判断」。推奨: この4点を最低限入れる

D1・D2・D7は両者一致で判断コストは低い。D3〜D6はAstraの指摘でClaude案を修正したもの。

確定した事実（コード確認・2026-09-11）

事実はClaudeが stage-sketch.js を直接読んで確認。Astra指摘・Claude未再確認はAstraが行番号つきで示したがClaudeは再確認していないもの。

事実影響・マニュアルでの扱い
事実① 読み込みは寛容。{project:{scenes:[…]}} または素の project を受理し、kind・version は検証しない。会場同梱を処理するのは数値の version === 4 のときだけ（importProject L18149〜、prepareProjectImportDocument L697〜）外枠は数値 version 4・venues:[] に固定。同梱会場はプレビューより前にライブラリへ保存され取り消せないため、AIに venues を書かせない
事実② 未知フィールドは黙って落ち、範囲外の数値は clamp、不正な色は既定色、不明な type は performer、不明な set.kind は block（normalizeScene L4001〜、normalizePiece L3669〜、sets正規化 L4229〜）AIが独自フィールドを足しても気づけない。機械検証（D3）が要る根拠
事実③ 姿勢IDはブラウザに48種（stand/walk/…/lie/supine/sidelie 等）。MCPの列挙にある lie_back / lie_front / lie_side はブラウザに存在せず stand に化ける（POSES L1757〜、L3710）ドラフトの姿勢一覧は誤り。マニュアルの enum はブラウザ側から採る（D4の根拠）
事実④ lightKind を保持するのは sets[] だけで、pieces[] の lightKind は捨てられる。beam 省略時は「対象の真上・高さ6m・床へ照射」に固定（normalizeBeam L3641、L4263）ドラフトの照明設計は不成立。D5の根拠
事実⑤ 駒の色は pieces[].color が正で、省略時は #a84b26。cast の色は読み込み時に駒へコピーされない（L3681）見本と本文で piece 側にも color を明示させる
事実⑥ 什器が演者の頭上に乗る既知問題は、現行コードで chair/table/bench/stool を支え候補から常に除外し、他は設置面積で除外するよう修正済み（supportUnder L6395〜）。配列順は依然として効くドラフトの「什器を演者より前に並べる」規則は一般化しない。「同一場面の駒は 什器→演者 の順を推奨」程度に弱める
事実⑦ 読み込みを止める条件は、ファイル読取失敗・JSON構文エラー・project.scenes が配列でない場合だけ（L18152〜18175）「読み込めた＝意図どおり」ではないと本文に明記
Astra指摘・未再確認⑧ u:null, v:null, size:null は Number(null)=0 により 0, 0, 55 になる（L3158・L3678）。scenes:[null] 等は正規化中の例外で、整ったエラーにならない「省略可」と「null可」を同義にしない。null要素を検査器の負のケースに入れる
Astra指摘・未再確認⑨ 未解決の castId/setId は読み込みを止めず文字列のまま残る。名前からの再接続はない。同一場面で同じ castId を複数回使うと場面間照合が曖昧になる（L3683・L16176）「同じ実体は場面をまたいで同じ登録ID、同一場面の別個体は別登録ID」を規則にする
Astra指摘・未再確認⑩ flown/wires を書かなくても trapeze/tissue は吊物になり、近接する演者はポール等へ自動的に取り付く（L4253・L6529）「危険な値を書かない＝安全な図」ではない。D8の文言の根拠
Astra指摘・未再確認⑪ 既存の check-object-on-performer.mjs は解析失敗でも exit 0 になり得る（L323・L330）P1の完了条件として単独で使わない

AIに書かせる範囲（統合版サブセット）

{
  "kind": "shosai-stage-sketch", "version": 4, "venues": [],
  "project": {
    "title", "venue"(5種のいずれか), "venueSize"(small|mid|large),
    "cast":  [{ "id", "name", "color", "heightCm"? , "note"? }],
    "sets":  [{ "id", "kind"(D6の許可種類), "name", "color", "note"?, "lightKind":"hang"(kind=lightのみ) }],
    "scenes": [
      { "kind":"section", "depth":0, "title" },                      ← 駒・beatは書かない
      { "kind":"scene", "depth":1, "id", "title", "note"(行為/規則/変化), "background"?,
        "beat": { "role", "energy"(1-5) }, "lightingIntent"?: { "objective", "audienceFocus", "mood" },
        "pieces": [
          { "id", "type":"performer", "castId", "u", "v", "color", "facing"?, "pose"?(ブラウザ48種), "size"? },
          { "id", "type":(set.kindと一致), "setId", "u", "v", "color" }
        ] }
    ]
  }
}

書かせない: route（動線）、strokes/arrows/notes/photo/screenTexts、heldBy/holdSide、base/supportId、beam、舞台機構の値、stashed/locked、flown/wires、venues[] の中身、rehearsal の秒数、mcpMeta/editSummary/appliedRevision。

本文に必ず入れる要素（Astra第4節を採用）

  • 出力形式の固定: UTF-8の単一JSON。説明文・コードフェンス・コメント・末尾カンマ・... やプレースホルダを入れない
  • 必須／任意／条件付き必須の表。「省略時に何になるか」「nullを許すか（許さない）」「置く階層」を併記
  • 参照の規則: performer は castId、それ以外は setId。set.kind と piece.type を一致させる。登録IDは場面をまたいで固定、scene/piece の id は明示し重複させない
  • 座標契約: 客席から見て u は左0→右1、v は奥0→前1。facing は度（0=客席）。size は100が基準、heightCm は cm。P1の生成範囲は u,v とも 0〜1
  • section の並べ方の具体例（平坦な配列で depth 0/1）
  • 生成上限（scene+section 合計60、1場面80駒）と、失敗時は理由と修正版の完全JSONを返す指示
  • 創作上の制約の入力欄: 人数・会場・場面数・使える道具・採用済み要素。実測値を捏造せず、仮定は note に明記。PLAYBOOKの6〜9ビートを場面数指定へ無条件適用しない
  • ユーザーの受け取り手順: PCは比較画面→「別のショーとして開く」、スマホは比較画面なしで即保存、保存失敗時の扱い、全場面を見てから判断
  • 入れない表現: 「自己点検済み＝読み込み保証」「読み込み成功＝意図どおり」「安全警告なし＝安全」
