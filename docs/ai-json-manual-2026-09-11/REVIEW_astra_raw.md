## 3

**追加で決めるべき事項は次のとおりです。**

1. **照明をどこまで生成するか。**  
   現在の「4種のlightKindを許可し、beamは禁止」は成立しません。推奨は、P1の駒は検証済みの `hang` に限定し、横・前・床から当てたい意図は `lightingIntent` に書くこと。4種類を描画まで扱うなら、登録側lightKindと種類別beamを一組の契約として許可する別判断が必要です。  
   根拠：`stage-sketch.js:3641`、`:1644`、`:13495`。

2. **列挙できる種類と、生成をサポートする種類を分ける。**  
   `model` はローカルモデル参照を必要とし、現サブセットにはその契約がありません。`prop` も形を省略するとboxです。`seri/revolve/deck/curtain/pool` は値を禁止しても種類を許可すれば既定状態で出現します。P1は試験済み種類を明示的に選び、未対応対象はnoteで提案する方針を推奨します。  
   根拠：`stage-sketch.js:3855`、`:4237`、`:3730`。

3. **「安全未確認」の意味と、見た目の自動補完。**  
   `flown/wires` を書かなくても、trapeze/tissueは吊物になり、ワイヤーは補完されます。近接する演者はポール等へ自動的に取り付きます。「危険な値を書かない＝床上の安全な図になる」ではありません。公開文言は「配置・照明・姿勢は検討用の図。実施可能性や安全承認を表さない」とし、対象場面にも注意を残すべきです。  
   根拠：`stage-sketch.js:4253`、`:4255`、`:6529`、`mcp-server/src/stage-model.js:633`。

4. **新規下書き専用か、既存ショー修正も扱うか。**  
   P1は新規下書き専用を推奨します。サブセットだけで既存ショーを再生成すると、写真、注釈、音源情報、機構状態等を失うためです。既存ショーの修正対応は、対象外フィールドの保持と差分適用を別途設計する必要があります。  
   根拠：`stage-sketch.js:4004`、`:4198`、`mcp-server/PLAYBOOK.md:64`。

5. **Mac版と共有セッションは、対象外でも境界説明が必要。**  
   Macのproject storeとAI採用経路はv3を要求します。v4ファイルの一般読み込みと、Macの「AI指示」を同一機能として案内できません。  
   また、共有ホストの変更は自動送信へつながるので、「別ショーとして開けば他人には見えない」とは言えません。私的な検討は共有を終了してから、という利用手順を推奨します。  
   根拠：`mac-app/Sources/StageSketchProjectStore.swift:209`、`stage-sketch.js:18709`、`:6074`、`stage-session.js:770`、`:697`。

6. **既存監査資料の共有経路説明は、現行コードと異なる。**  
   監査表は共有も正規化へ渡るとしていますが、現在の `applyDocumentString` は `state.project = project` と直接代入しています。したがって「共有受信でも直ちに未知fieldが落ちる」という説明は現在の根拠にできません。一方、通常の保存復元・ファイル読み込みで失われる問題は残ります。  
   根拠：`docs/project-contract-2026-09-09/WORKFLOW_IO_AUDIT_2026-09-09.md:23`、`stage-sketch.js:23657`、`:4335`。

7. **公開契約・データ送信・更新方針。**  
   「公開ページに載せる＝AI各社へ送信」は不正確です。公開する内容と、利用者がAIへ渡すマニュアル・素材を分けて説明すべきです。架空見本、送ってよい素材の確認、対応アプリ版、マニュアル改訂番号、既知の非対応機能、コピー・再配布条件を決めてください。**特定AIでの生成成功や秘密保持は、未検証のまま保証しない**方針を推奨します。  
   根拠：ドラフト `docs/ai-json-manual-2026-09-11/DESIGN_DRAFT_claude.md:85`、入力素材の境界は `mcp-server/src/schemas.js:126`。

## 4

**本文に必ず入れるもの**

- **出力形式を一つに固定する指示。** 「UTF-8の単一JSON文書。完成した `.json` の中身には説明文・コードフェンス・コメント・末尾カンマを入れない」。MCP入力、ビート表、ショーJSONを混ぜない。読み込みは直接 `JSON.parse` するためです。`stage-sketch.js:18160`。
- **必須／任意／条件付き必須を分けた表。** 「省略時に何になるか」「nullを許すか」「置く階層」をセットで示す。特にID、color、lightKind、beamは所有場所を明記する。`stage-sketch.js:3674`、`:4218`。
- **参照の規則。** performerはcastId、それ以外はsetId。対応先が存在し、set.kindとpiece.typeが一致すること。登録IDは場面間で固定、scene/piece IDは明示し重複させない。`stage-sketch.js:3865`、`:16176`。
- **座標・単位・範囲。** 客席から見てuは左→右、vは奥→前。facingは度、sizeは100が基準、heightCmはcm。P1のu/vを0〜1へ限定するなら、ブラウザ全体の許容範囲とは別の「生成範囲」と記載する。`mcp-server/src/stage-model.js:715`、`stage-sketch.js:3678`。
- **sectionの具体的な並べ方。** sectionをdepth 0、直下のsceneをdepth 1にするなど、平坦なscenes配列で例示する。sectionに駒やbeatを書かせない。`stage-sketch.js:3305`、`:4152`、`:4025`。
- **上限と失敗時の戻り方。** sceneとsection合計60行、1場面80駒などを生成上限として明記する。ブラウザ読み込みが超過分を必ず拒否するとは書かない。エラー時は該当箇所の理由と修正版の完全JSONを返す。`stage-sketch.js:3310`。
- **創作上の制約。** 人数・会場・場面数・使える道具・採用済み要素を入力欄として用意する。不明な実測値を捏造せず、仮定はnote等に明記する。PLAYBOOKの6〜9ビートを、3場面指定などへ無条件適用しない。`mcp-server/PLAYBOOK.md:30`、`:37`、`:75`。
- **ユーザーの受け取り手順。** PCは比較画面→別ショー、スマホは比較画面を省くこと、保存失敗時の扱い、全場面を見て判断すること。`stage-sketch.js:18195`、`:14048`。

**例示JSONの数と長さ**

推奨は、**本文内に短い完全例1本、ダウンロード見本は最小・標準の2本**です。本文の完全例は1演者・2場面を基本に、登録と参照を最後まで省略せず示します。標準8場面を本文へ丸ごと重ねる必要はありません。

6,000〜9,000字は目安にとどめ、必要な契約を削って合わせないでください。例の最適な長さが生成成功率を上げるかは**推測**であり、P2で比較する事項です。見本には、色の異なる人物、異なる姿勢、section、照明の許可範囲など、意味の保持を確認できる差を持たせます。

**入れてはいけないもの**

- ブラウザで開く例に `placements/assetName`、MCPツール呼び出し、`expectedRevision` を混ぜること。
- JSON例の中の `...`、`?`、`castId|setId`、説明用プレースホルダー。
- 「省略可」を「null可」と同義にする説明。
- 不明な種類をAIの判断で既知の種類へ黙って読み替える指示。
- `workflow/cues` や出典の独自構造を、保持される正式project fieldとして追加すること。
- MCPの姿勢列挙・範囲制限・既定値を、そのままブラウザ仕様と称すること。
- 「自己点検済み＝読み込み保証」「読み込み成功＝意図どおり」「安全警告なし＝安全」という表現。

最後の区別は実際に重要です。MCPの `validateDocument` は、不明なpiece.typeだけの文書をvalidとし得ます。  
根拠：`mcp-server/src/stage-model.js:601`。

## 5

**段階分けは妥当ですが、P1の完了条件は不足し、P4の発動条件は見直すべきです。**

| 段階 | 評価・修正案 |
|---|---|
| **P1** | 文書・見本・点検表を作る順序はよい。機械検証を任意から必須へ変更し、読み込み後の意味の保持と再保存・再読み込みを合格条件に追加する。 |
| **P2** | 3種×2課題は初期の問題発見として妥当。ただし6本の成功率だけで信頼性を一般化しない。同じ本文・課題・修正ルールで、初回成功、修正後成功、意味の欠落、手作業回数を分けて記録する。 |
| **P3** | コピー・DLに加え、配信された本文と見本の版一致、リンク先の対象UI、英語版とのenum一致を確認する。公開環境がP1で試した実装と同じかも記録する。 |
| **P4** | 「参照切れ・未知fieldの失敗が2件以上のみ」は反対。**意図の黙った変形が1件でも再現し、文書修正で防げない場合**は、公開前に点検表示か端末内チェッカーを検討する。 |
