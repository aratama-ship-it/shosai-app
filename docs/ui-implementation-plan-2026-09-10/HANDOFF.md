## 2. 設計の基準

1. 利用者と場面: 舞台の構成を考える本人/制作担当が、正面と平面を見ながら配置・動線・シーンを編集する。
2. 目指す操作感: どれを選び、何が変わるかをその場で把握でき、繰り返し操作で画面位置を見失わない。
3. 固有の核: 演者・舞台セット・小道具・照明の区別、場面順、前後の位置関係が制作の意味を持つ。
4. 構造の選択: 見た目だけ詰める案、説明を全部隠す案、目的ごとに入口をまとめる案を比較し、本人の指定に沿う3番目を軸にする。既存の机/紙の配色と既存部品を利用する。
5. 守る条件: PCのマウス/キー、iPadタッチ、4言語、Undo、旧データ、JSON往復、ゲスト等の既存権限と互換にする。

寸法の初版は [TOKENS.md](TOKENS.md)。製品の未確定値は「提案」と明示。資料そのものの数値と混同しない。

## 4. 複数選択と整列の実装案（R06/R07）

現在の主状態は selectedId。新しい選択集合をUI状態に持ち、既存の単体インスペクター用には主選択を残す案。
選択集合をプロジェクトJSONへ新規保存する必要はない。選択先は現在のシーンに実在するIDだけにする。

- 通常クリック: 単体選択。Shift+クリック: 集合へ追加/解除。空白クリック: 解除。
- 囲みドラッグは平面の選択モードでだけ開始。動線ハンドル・配置物の移動・ズーム時のパン・自由矢印・ピンチの開始と排他にする。
- タッチは上部の複数選択入口から明示モードへ入る案。外付けキーボードのShiftも利用可能にする。
- 囲み範囲と判定はCanvas表示の座標変換経路を利用する。CSS寸法だけで判定しない。逆方向の囲みも正規化する。
- 整列の処理入口は対象配列を明示的に受け取り、画面上の全performerを中で再抽出しない。
- 混在する演者/物の中心位置をそろえる案。現在の位置順を尊重する方針を保持する。選択外の内容は完全に不変。
- 0/1件選択では整列しない。未選択時に全員を勝手に並べない。
- シーン切替・削除・JSON読込・Undo/Redo後に消えた選択IDを掃除する。
- 選択しただけでは履歴を増やさず、整列1回をUndo1回にする。

回帰例: 5人とセット2個のうち2人+セット1個を選択して整列。選択外の位置、各ID、持ち物関係が不変。
矩形選択・Shift解除・ズーム・表示モード切替・日本語入力中を確認する。
複数移動/複数削除は今回の明示要件ではないため、整列対応と一緒に必須化しない。

## 5. パネルモードの実装案（R10/R11）

語の衝突を防ぐため「1列/2列」はツールパネル側の列数として扱う。正面/平面を何枚出すか、上下入替、3Dモードとは別設定。

概念上の設定例（新しい保存キーを確定したものではない）:
- panelMode: single / dual / ipad
- singlePanelSide: left / right
- 各モードの順序/開閉/幅: 現行の配置保存に対応付け、他モードへの切替で消さない。

1列では利用可能なパネルを選んだ側へ集約。2列では左右へ配置。本人が非表示指定したパネルは集約時にも復活させない。
iPadモードは既存tabletUiのレール/ドロワーを再利用する。
ユーザーエージェントや「standalone PWA」のフラグを偽装して認証/キャッシュ/スマホ閲覧制約まで切り替えない。
実際のiPadでの初期挙動は既存を保ち、表示設定を明示した場合の優先順位を定義する。
キー入力中のモード切替、狭幅からの復帰、リロード後の配置復元を確認する。

## 6. 追加・分類・再利用の実装案（R18〜R24）

追加 → 演者 / 舞台セット / 小道具 → 種類・画像 → 名前・必要な設定 → 追加確定。

既存の stage-kind モーダル、名簿追加処理、stage-set-builder.js を接続する。単に現在の入力DOMをモーダルへ移すだけで、
種類を選んだ瞬間に実データへ追加されないかを確認する。モーダルの中はドラフトとし、確定時に一度だけ変更する。
キャンセル時は既存オブジェクト、モデル、選択中シーンの内容を保つ。

3分類は一覧と追加メニューの階層。舞台セットを小道具へ分類変更しても座標順や所有関係が変わらない設計にする。
表示名だけからtypeを決めず、既存のtype/kind/小道具分類の正規化を先に整理する。
「自分で作る」は舞台セット分類の種類一覧へ置く。ビルダーを閉じて元の追加画面へ戻れる。

JSONは stage-set-model.js の serializeLibrary / parseLibrary と stage-set-builder.js の既存入出力を利用する。
既存は全ライブラリ出力。「作った物の再利用」が満たせることを先に往復確認し、単品出力は追加案として扱う。
出力物のID/寸法/部品と、別プロジェクトに配置した結果を照合する。通常のショーJSONとモデルライブラリJSONを取り違えない説明にする。

壁画像はR22の別サブタスク。新しい画像フィールドの形や制限値を無検証で確定しない:
- 画像を紐づける正本はカタログの壁定義か、シーン内インスタンスかを既存データに照らして決める。
- 仮案は壁定義へ画像を紐づけ、同一の壁は次シーンでも同じ表示。異なる内容は複製した壁で表現。
- 再読込後も表示できる永続化と、複数画像を重複保存しすぎない仕組みを設計する。
- 他プロジェクトへJSONで持ち出すときの画像同梱/参照欠落の扱いを明記する。data URLを上限なく複製しない。
- JPEG/PNG/WebPを現行の背景画像と照合して扱う。比率はcontainを初期候補、引き伸ばしを無条件にしない。
- 3Dだけでなく正面・画像出力を確認し、Canvas出力不能や保存容量超過を画面内で案内する。
- ファイルサイズ/画像寸法の上限は保存経路を測ってから設定。動画再生は今回の要件外。

1Passwordの原因は未確定。profile-nameは現状もtext入力なので「パスワード型だった」と断定しない。
フォームや自動入力属性の調査→最小の修正→拡張有効環境で再確認、の順にする。
照明も同じドラフト確定方式を使い、既存の配置/種類/色/プリセットの意味を保つ。

## 8. 動線と次シーンの不整合解消（R25）

最低対象は舞台上の演者。同一演者を名前一致で推定せず、既存twinOfのcastId/originId等の照合を調べて使う。
オブジェクトへの対象拡張は演者の要件に黙って混ぜない。

概念上の流れ:
Aの動線編集を確定 → nextSceneOf(A)で次の実シーンBを取得 → 対象を照合 →
不一致一覧を作る → 行ごとの選択/全件選択 → 適用直前に再照合 → 1回の履歴で変更。

一覧の各行:
対象名・識別子 / 前シーンと次シーン / 動線終点 / 次シーン立ち位置 / 差 / 優先する側。
「次のシーンを優先」「前のシーンの動線を優先」は未選択で開始する案。
一括操作は全行へ選択を入れるだけとし、最後の「適用」まで実データを変えない。

- 次シーン優先: Aのroute終点をBの位置へ移す。直線の制御点は再計算し、曲線は終点以外の意図を保つ。
- 動線優先: Bの対応演者をAのroute終点へ移す。B→Cがある場合、Cまで無言で連鎖移動しない。
- キャンセル: ダイアログを開く前の状態を保つ。直前に本人が確定した動線編集自体を勝手に取り消さない。
- 適用: 選択した矛盾だけをまとめて更新。全件をUndo1回で戻せる。
- A/Bが編集・並替・削除された場合: 古い一覧を適用せず、再検出を案内する。
- 次シーン不在・退場・新規登場・舞台外待機は単なる位置不一致と分離。対応先を勝手に作成しない。
- ドラッグ中に毎フレーム開かない。確定時に同じペア/同じ変更を重複通知しない。

現在のsyncRouteFromPrevはFOLLOW_M=0.6m、WARN_M=2.5mで自動追従/通知する。
これは新しい不整合判定の許容誤差として流用しない。初版案は幾何誤差用epsilon=0.01mで、
既存丸め・座標変換・会場寸法を調べて採用する（業務上許される位置差と混同しない）。
同関数がダイアログより先にデータを変えないよう、対象ペアの追従経路を統合する。
前→次だけでなく、次の位置編集、整列、フォルダー移動による隣接変更からの再照合経路を確認する。

必須データテスト:
A/B共通2人の片方だけ不一致 / 全件不一致 / 直線と曲線 / 同名別人 / 不在・退場 /
次シーンなし / セクション行を挟む / 行別混在 / 一括2種 / キャンセル /
再表示 / 編集中の順序変更 / Undo/Redo / JSON保存再読込。
