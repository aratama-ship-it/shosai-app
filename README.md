# 制作の書斎（Phase 0 プロトタイプ）

ショー・演出リファレンスを、制作の問い・場面案・ビジュアル試作へつなぐ個人用の作業空間。

- メイン: **資料棚** — 作品データベースの閲覧（一覧・検索・詳細＋関連作品/関連表現の自動集約）
- サブ: **制作会社**（公式根拠つきの探索地図）／**名簿**（アーティスト＝要合言葉／制作・技術スタッフ＝作品クレジット索引）／**制作机**（場面スタディ・ビジュアル比較）／**スクラップブック**（種火を配る＋紙面へ貼って残す。自炊本25冊から変形した100件を含む）／**場面問答**（判断のエクササイズ）

## アプリ境界（2026-09-12）

- **制作の書斎**は `index.html`。舞台スケッチの画面、ナビゲーション、モーダル、実行スクリプトを含まない
- **舞台スケッチ**は `stage.html`。単独で起動し、`db.js`・`app.js`・`roster.js` など書斎の実行コードを読まない
- `stage.html` を舞台スケッチHTMLの正本とする。`index.html` からの生成は廃止した
- `python3 build_stage.py` は `stage.html` の必須要素と書斎との分離を検証し、派生する演者Viewer用 `study-frame.html` だけを更新する。`--check` は書き換えずに検証する
- リポジトリ、Worker、共通CSSは現時点では共有基盤だが、ブラウザで動く2つのアプリと各データの所有境界は分離する

## 資料棚と名簿の役割分担

- **資料棚は作品から読む場所**。人物での絞り込み・人物名からの作品逆引きは持たない
  （出典メモなど本文に書かれた人名は作品の記述そのものなので、全文検索から消していない）
- **名簿は人を探す場所**。索引は二冊に分かれる。自動で同一人物として統合はしない
  （同姓同名・別表記・グループ名がありうるため）
  - **第一冊 アーティスト** … 暗号化されたスカウティングレポート由来。合言葉で解錠する（下記）
  - **第二冊 制作・技術スタッフ** … `db.js` の `persons` と作品別 `people` から組み立てる作品クレジット索引。
    **合言葉は要らない**（公開済みのクレジット情報しか出さない）。実装は `roster-crew.js`
- 制作・技術スタッフの部門判定は `roster-crew.js` の `DEPARTMENTS` 一か所に集約。
  正本の `role` は書き換えず、作品別 `credit_label` に職名が明記されている場合だけ部門へ加える
  （舞台監督が `director`、Props Master が `set_designer` へ暫定対応されている例を救うため）。
  括弧内は注記とみなして判定から外す（「…Disney+映像版…」で映像部門へ入れない）
- 連絡先・SNS・写真・調査文はアーティスト名簿だけの資産。制作・技術スタッフ側へは混ぜない。
  在籍・依頼可否などの状態も推定表示しない

## 名簿タブ・アーティスト（個人情報を扱う）

- データは**書斎側に置かない**。同一オリジンの `scouting-report-app/data/data.enc` を読み、合言葉で復号する。週次タスクでシートが更新されればこちらにも反映される
- 防御は画面を隠すことではなく**暗号化そのもの**（AES-256-GCM / PBKDF2-SHA256 15万回）。合言葉がなければ `data.enc` を直接落としても読めない
- 合言葉の端末保存キー `scout_pass` はスカウトアプリと共有する。どちらかで解錠すればもう一方も開く。**この共有があるため、書斎アプリへ外部スクリプト（CDN・解析タグ）を持ち込まない**

### 合言葉を毎回入力しない設定（2026-08-20）

サイト全体が `worker.js` のBasic認証で守られるようになったため、書斎を開けた時点で本人かチームのゲスト。
名簿の合言葉を毎回聞く必要がなくなったので、**鍵をサイト側に置いて自動解錠**する。

- `roster-key.example.js` を `roster-key.local.js` としてコピーし、`SHOSAI_ROSTER_KEY` へ合言葉を書く
- `roster-key.local.js` は **`.gitignore` 済み**（このリポジトリは公開）。`.assetsignore` には**入れない**（Cloudflareへは載せる必要がある）
- 置けば合言葉欄は出ない。ファイルが無い・鍵が違うときは、これまでどおり合言葉欄が出る
- **`data.enc` の暗号化は外していない。** 実体は scouting-report-app の GitHub Pages にあり
  Basic認証の外＝誰でも取得できるので、あれを守れるのは暗号化だけ。
  合言葉を追跡対象のファイルへ書くと、公開リポジトリ経由で誰でも復号できることになる
- ゲスト（`GUEST_USER`）にも名簿は見える。チーム内部用という前提（2026-08-20 本人確認済み）
- `file://` では動かない（fetchがブロックされる）。名簿タブだけは公開URLから開く
- 名簿は読むだけ。ここから編集・追記はしない（元アプリとシートが正）

## 使い方

制作の書斎は `index.html` をブラウザで開く（静的・依存なし）。入口は資料棚。

舞台スケッチは別アプリの `stage.html` を開く。右列の「場面スタディ」から
「時をほどく研究室」の固定8ビートを別ショーとして開ける。各ビートは通常の場面なので、
配置・姿勢・メモを個別に直せる。元のショーは「ショー一覧」に残り、どちらもこのブラウザ内だけに保存される。

Vision Proの実寸・一人称稽古を拡張として統合する方針と、version 3から稽古用JSONへの変換契約は
[`docs/VISION_PRO_REHEARSAL_EXTENSION_HANDOFF.md`](docs/VISION_PRO_REHEARSAL_EXTENSION_HANDOFF.md) を参照。

iPad実機での通しQAは未実施（2026-07-28議論の優先度2位）。チェックリストは
[`docs/IPAD_DEVICE_TEST.md`](docs/IPAD_DEVICE_TEST.md)。

## 事前学習用リンク（ローカル実装・未デプロイ）

舞台スケッチ本体 `stage.html` に、明示更新する閲覧スナップショットとオーナー宛てメモを追加。制作の書斎 `index.html` は対象外。
公開体験版 `try.html` は対象外。ベータでは `STAGE_BETA_ACTIVE="true"` と `STUDY_ALLOW_ANONYMOUS="true"` により、招待リンクだけでログインせず閲覧できる。メモ・ペンはそのブラウザに保存し、端末間では同期しない。共有ボタンで送った表示名・メモ・図だけがオーナーへ届く。管理APIは既存の認証済み作成者だけに限定。
本家のアカウント必須構成（匿名閲覧フラグなし／false）では、無料の演者アカウントで招待リンクから複数オーナーのショーを自分の一覧へ追加できる。
アカウント利用時は自分用の文章・ペンを本人のアカウントへ自動保存し、PC・スマホで同期する。オーナーには「この画面をオーナーへ共有」を押した内容と認証済み表示名だけを送る。
保存は1アカウント10ショーまで。オーナーはメモ全削除、失効後の新token再発行、失効済みデータの完全削除で容量とショー枠を回復できる。
`python3 build_stage.py` が隔離描画ページも生成する。Cloudflareには `STUDY_LINKS` と `v3-study-links` migration の適用が必要。
演者認証と保存には `STUDY_READER_AUTH` / `STUDY_READER_ACCOUNTS`、`v4-study-reader-accounts` migrationも必要。Google設定は未登録。リンクのみのベータ閲覧・端末メモにはGoogle設定は不要。
共有モーダルの「フィードバックを見る」から全ショーの受信内容をショー・場面・表示名で絞り込める。演者の未共有メモは表示しない。
公開更新時は以前の舞台図を最大50版・32 MiB保持し、上限では更新を拒否する。個人メモは場面IDと図の内容で対応付け、削除・変更場面の文章と線を履歴から選んでコピーできる。原本は自動削除しない（場面ごとの履歴32件、既存の保存サイズ上限内）。同じショーの新しい招待はサーバー確認済みのノートIDで再接続する。旧tokenの端末保存も残す。
演者Viewerの「メモ」道具から、正面図・平面図に自分用の付箋を貼れる（1場面16枚・1枚200字）。ドラッグまたは矢印キーで移動し、文字は側面で編集する。既存の個人ノートへ保存し、明示共有した画像だけがオーナーへ届く。以前の付箋は履歴から1枚ずつ引き継げる。追加migrationなし。
付箋の確認記録: [図へ貼る自分用メモ](docs/study-links/sticky-notes-2026-09-10.html)。

## データ

- `db.js` は正本データ（`../show-reference/data/*.json`、リポジトリ外）から生成した読み取り専用の索引
- `book-seeds.js` は自炊本の確認済み内容要約を出典にした、100件の未完成な一行場面。本文の転載ではなく、書名・分野・変形メモを持つ抽象化データ
- `stage-scene-study-data.js` は `../direction-knowledge/examples/time_lab_future_scene_study.json` から舞台スケッチに必要な固定項目だけを同梱したデータ。舞台スケッチは実行時に書斎・知識ベースを読まず、単独で動く
- 正本更新後の再生成: `python3 build_db.py`
- 制作の書斎のコード変更時は `index.html` 内の `?v=` を上げる。舞台スケッチのコード変更時は `stage.html` と `stage-sw.js` の該当 `?v=` を揃える
- **舞台スケッチのHTMLは `stage.html` を直接編集する。**変更後は `python3 build_stage.py` と `python3 build_stage.py --check` を実行し、必須要素、書斎との分離、派生Viewerの整合を確認する
- **コード変更のコミットと、索引再生成のコミットは分ける**（履歴でコードの変更を追えるようにするため）
- 索引を何度も再生成した後は `git gc` で回収する（looseオブジェクトが溜まると .git が数十MBに膨らむ。gc後は全履歴込みで約5MB）

## 状態

Phase 0: 制作机と場面問答の内容は固定サンプル。書斎ではスクラップブックをブラウザ内へ自動保存する。

別アプリの舞台スケッチはショーをブラウザ内へ自動保存し、Codex／Claude Code共通のローカルMCPを持つ。AI案は直接ブラウザへ書かず、
`.stage-sketch-mcp/` の下書きと履歴へ残す。AI編集のJSONは、指示・概要・場面ごとの差分・警告を
読み込みモーダルで確認してから、既定の「別のショーとして開く」で元のショーを残したまま取り込める。
設定・使い方: [`mcp-server/README.md`](mcp-server/README.md)
AIによる既存ショーの編集を、差分確認・承認つきで進めるための実装前設計:
[`docs/AI_EDITING_HANDOFF.md`](docs/AI_EDITING_HANDOFF.md)
